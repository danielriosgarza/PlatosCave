# Package session (Phase 5)

Trigger: the owner types **"continue package development"** in a local Claude Code session on the owner's machine, opened in the working copy of `danielriosgarza/PlatosCave`. The session that receives it is a **package session** and does exactly what this skill says. The phrase starts nothing else: the Opus and Fable helpers that a package session launches work inside it.

Phase 5 makes Parallax installable and pluggable as `docs/needed_specs.md` states it (N1 to N10); Parallax as built does not change. The work is 25 units, `P5-01` to `P5-25`, in 4 close-ended sessions. Package development is local (owner decisions, 2026-10-12): no cloud session is launched, the hourly orchestrator is stopped for the whole of it, and the Delivery status issue (#3) carries `paused`. No package session removes that label; removing it is the owner's decision once package development has ended.

Where things are, all read from `origin/main`:

- This skill is the procedure (section 3 of the plan).
- `docs/plans/2026-10-12-package-development.md` is "the plan": its section 4 has the Sessions table, section 5 the owner's decisions (answered in issue #559, `[P5-OD1]`), section 6 the rules that bind every unit, and "Steps" the unit entries.
- `docs/delivery/plan.md`: once P5-02 has merged, its section "Phase 5" holds the unit entries (`### P5-nn`) and the Sessions table. From then on a unit's entry and the Sessions table are taken from there.
- `docs/delivery/README.md` gives the labels, the merge rule and the limits. Where it or another skill names the orchestrator or a cloud session, the Phase 5 rule written beside it applies; "Helpers and tools" below says how to read the rest.

## What a session does

1. **Finds the procedure.** `CLAUDE.md`, loaded into every session, names this skill. Run `git fetch origin`; if the working copy is behind `origin/main`, read this skill from `origin/main`.
2. **Computes progress** from `origin/main` only.
   - **y** is the number of Phase 5 units: the count of `### P5-` headings in `docs/delivery/plan.md` (`git show origin/main:docs/delivery/plan.md | grep -c '^### P5-'`). It is 25 once P5-02 has merged and one more for every item added later. While P5-02 has not merged the count is 0, and y is 25: the units of the plan's Steps.
   - **x** is the number of those units whose `docs/delivery/done/<ID>.txt` is on `origin/main` (`git ls-tree --name-only origin/main docs/delivery/done/ | grep -c '/P5-'`). Each unit's own pull request adds that file, and a pull request reaches `main` only under the merge rule, so a unit counts only after Fable approved it.
   - Work in flight is read from GitHub: the unit's issue and pull request, their labels, the `Review verdict:` comments and the records defined below. There is no second dashboard and nothing is read from an earlier chat, so every fresh session gets the same two numbers, on the first run and after an interrupted one.
3. **Selects the session:** the lowest-numbered session that has a unit not done; a further session written with a letter (`2a`) comes directly after the session it is named for. Its list is fixed: the session's row of the Sessions table, together with the added items whose `Session:` line on `main` names it. Nothing is added to a list once its session has started. If every unit still open in that session is labelled `needs-human`, it reports that it waits for the owner, with "x of y done", and stops.
4. **Checks** that it runs as Opus 5.5, on the owner's machine and not as a cloud session; that `[P5-OD1]` (#559) is closed and #3 carries `paused`; that Fable can be launched (the Agent tool offers the model `fable`); and, for a session with a planning run (sessions 1, 2 and 3), that the command and its tools are installed (`~/.claude/commands/collab-independent-plan.md` and `~/.claude/bin`). If one of these checks fails it says why, reports "x of y done" and stops. It also lists which local tools of the plan's row P-d are present: Node 22.12 or later, pnpm 10.33.0, Go 1.24, `gh` signed in, `node_modules`, Docker Desktop (PostgreSQL for the integration and e2e suites) and Playwright's Chromium. A missing one stops nothing: the suite that needs it runs in CI only, and the report names it.
5. **Works the list** in dependency order with at most three units in flight (README limit), each by the unit procedure below. A resumed unit continues from its state: approved and green, merge; changes requested, Opus fixes; no verdict on the head, a new Fable review; issue without pull request, start; no issue, create it; `needs-human`, skip.
6. **Stops** at the end condition: every unit of the session is done (its done file is on `origin/main`; session 4 also needs the issue `Phase 5 summary`), or labelled `needs-human` with an escalate record. It reports, for example, `Session 2 of 4 closed. 13 of 25 done. Next: session 3 (P5-14 to P5-21).` and ends. The report names every unit left at `needs-human`, and the next trigger then selects the same session again. It never starts a unit of the next session, even with time left. With all units done it reports "25 of 25 done" (y of y, if items were added) and does nothing else.

## Unit procedure

One unit is one issue and one pull request of at most 600 changed lines (plan §0). A unit whose diff would pass 600 is split, never enlarged: the surplus becomes an added item. A unit is done when it passes the checks of its own entry and the done-check **D**: (1) `pnpm check` green locally and CI green on the head; (2) tests titled with the listed scenario IDs exist and fail without the change; (3) `docs/delivery/done/<ID>.txt` lists exactly those IDs and `pnpm scenarios` passes; (4) the latest `Review verdict: APPROVED` comment, by Fable, names the head SHA; (5) no existing test file is deleted and no `.skip`, `.only` or `.todo` is added; (6) after the merge the done file is on `origin/main`.

- **Issue.** `[P5-nn] Title`. The session whose list holds the unit creates it when work on the unit starts; the issue of an added item is created by the session that found it. No Phase 5 issue or pull request is created unless #3 carries `paused`. Labels `plan`, `phase:5`, `model:opus` (`model:fable` for the design units P5-03, P5-04 and P5-05, which README defines as a design item implemented by Opus at maximum effort), `security` where the entry says so, and one status label (`status:in-progress`, then `status:in-review` once the pull request is open). The body is the plan entry with `Depends on:` and `Touches:` lines.
- **Simple unit** (P5-01, 02, 10, 11, 24, 25). Opus implements it directly, following `.claude/skills/implement-issue/SKILL.md` steps 1 to 4 (tests first, done file, pull request with `Closes #`).
- **Complex unit** (the other 19). It is planned with `/collab-independent-plan` and then implemented by Opus. Five runs plan all 19 complex units (table below). The unit that owns a run executes the command first; the other units of that run start only after it has landed, and implement its plan. The session runs the command exactly as `~/.claude/commands/collab-independent-plan.md` defines it, in its default mode judged by Jev, with the TASK text of the run and no flags. `/collab-independent-plan` is never given `--judge classic` or any other flag that turns Jev off. If Jev's preflight fails, or Jev drops out later, the session tells the owner and asks before any classic fallback; without the owner's yes the unit is labelled `needs-human`. If one of the command's two authoring sides is unavailable, the session stops that unit and says so; it never substitutes a side. The landed plan (`docs/plans/<date>-<slug>.md`) is committed in the unit's pull request.
- **Implementer.** Always Opus: the session itself, or an Opus subagent that the session launches on the same machine, in its own worktree, on the branch `claude/p5-nn-<short-slug>` cut from `origin/main`. No cloud session is launched. No other model writes Phase 5 work. A failed attempt is retried with Opus, the third time at maximum effort, then `needs-human`. Attempts are counted as README counts them, fresh or continuing an open pull request: the session records each implementer start as a comment on the issue whose first line is `<!-- package-session launch role=implementer item=<ID> attempt=<n> at=<ISO> -->`, and a later session counts the records newer than the issue's latest escalate record.
- **Review.** When CI is green on the head, the package session sets `review:in-progress` and launches a fresh Fable reviewer, one per review round, as a local subagent in its own worktree. It starts from `main` and follows `.claude/skills/review-pr/SKILL.md`: it runs the checks, posts findings and a `Review verdict:` comment naming the head SHA, sets the review label, and never pushes. Fable runs at maximum effort on every unit, which covers README's rule for pull requests that touch `.claude/`, `.github/`, `CLAUDE.md`, `docs/adr/` or `docs/delivery/README.md`, and with `/security-review` for `security` units. Opus fixes the findings; Fable never does. An optional finding about a later unit whose issue does not exist yet stays in the verdict, and the package session copies it into that issue when it creates it. No other model reviews: a third `CHANGES REQUESTED` becomes `needs-human` instead of going to an arbiter, and if Fable cannot be launched the unit waits, labelled `needs-human`.
- **Merge.** The package session squash-merges under README's merge rule as it stands (approved verdict on the head, up to date with `main`, CI green, issue not `needs-human`); the owner allowed it on 2026-10-12 (issue #559, row P-b). It checks each approved pull request afresh, lowest number first: `gh pr update-branch <n>`, then, if `main` was merged in, `gh pr checks <n> --watch` until CI is green on the new head, then `gh pr merge <n> --squash --match-head-commit <head SHA> --subject "<PR title> (#<n>)"`. It confirms that the issue closed and that the done file is on `origin/main`. A conflict with `main` goes back to Opus, who merges `origin/main` into the branch (never a rebase or a force-push), and the new head gets a new Fable round. If the permission system refuses the merge, or the owner withdraws the permission, the session does not work around it: each approved, green pull request waits for the owner's merge, the session goes on with the units that do not depend on it and, when none is left, reports that it waits for the owner's merge and stops.
- **Escalation.** A unit is labelled `needs-human` together with an escalate record: a comment on its issue whose first line is `<!-- package-session escalate at=<ISO> -->`, followed by the reason and what the owner should decide. Besides the cases above, a commitment beyond N1 to N10 and the owner's answers in #559 is escalated, never decided by a session. Only the owner removes `needs-human`; a unit whose label the owner removed starts again with a fresh attempt count.
- **Scope and added items.** Work found outside a unit becomes a new plan item (`P5-nna`, or `P5-AUDn` when the audit raised it) with its own issue. It is never added to the open pull request's work or to the running session. Before work on it starts, the item gets its own `### P5-` heading in `docs/delivery/plan.md` on `main`, which raises y by one, with its class (simple, or complex and its run), `Depends on:`, and two lines that assign it: `Session:` and `Boundary:`. `Session:` names the session that takes it: always one that has not started, after every unit the item depends on and no later than the first unit that needs it. Within those limits it is the earliest session of the table that keeps to the size rule with the item added (a session holds at most 8 units, at most 4 units in one dependency chain, and at most 3 planning runs), and where there is none a further session, written with a letter after the session it follows (`2a`) or, after session 4, numbered 5, then 6. `Boundary:` names the dependency or size limit that puts the item there; the running session is closed to it because its list was fixed before it started. If no session meets these conditions, for example because a unit of the running session needs the item, the item takes the further session that follows the running one, and the unit that cannot be finished without it is labelled `needs-human`: only the owner changes a fixed list. The heading is committed, as plan lines only, in the pull request of the unit that found it (P5-25's pull request for an audit finding), and that pull request is not merged without it. The heading therefore reaches `main` together with that unit's done file, and no report says "y of y done" while such an item is open. A report that announces a further session states the new total of sessions.
- **Audit.** Session 4 closes with it. When every other unit is on `main`, the package session launches Fable, as it launches a reviewer, with `.claude/skills/phase-audit/SKILL.md` for phase 5 on `main`. Fable verifies A37 to A52 and the rules of the plan's section 6 across the merged units, writes the issue `Phase 5 summary` and files `[P5-AUDn]` issues, each marked blocking or not by the definition of `review-pr` §3; it fixes nothing. P5-25 then fixes what fits one pull request, and its plan entry says how the remaining findings are counted.

## Helpers and tools

A package session is local. It has the Agent tool and the `gh` CLI, signed in as the owner, and none of the GitHub MCP or Claude Code Remote tools that the older skills name.

- **Opus implementer:** Agent tool with `model: "opus"` (Opus 5.5, `claude-opus-5-5`) and `isolation: "worktree"`. Maximum effort is `effort: "max"`: for a `model:fable` design unit and for a third attempt. The prompt names the issue and tells the helper to follow `implement-issue` steps 1 to 4, to wait for CI on its head (`gh pr checks <n> --watch`) and then to stop without merging or reviewing.
- **Fable reviewer or auditor:** Agent tool with `model: "fable"` (Fable 5.1, `claude-fable-5-1`), `effort: "max"` and `isolation: "worktree"`. The prompt names the pull request (for the audit: phase 5 and `phase-audit`) and tells the helper to run `git fetch origin` and `git switch --detach origin/main`, to read `review-pr`, `CLAUDE.md` and `docs/delivery/README.md` there before it checks out the head, and never to push.
- **Tool names in `implement-issue`, `review-pr`, `steward` and `phase-audit`** are read as their `gh` equivalents:
  - `issue_write` with `labels` becomes `gh issue edit <n> --add-label <new> --remove-label <old>` (`gh pr edit` for a pull request), which changes only the labels it names.
  - `add_issue_comment` becomes `gh pr comment <n> --body-file <file>` or `gh issue comment`; a verdict stays an issue comment, never a pull-request review.
  - Reads become `gh issue view`, `gh pr view`, `gh pr diff` and `gh pr checks`; creating an issue or a pull request becomes `gh issue create` and `gh pr create`.
  - "Subscribe to the PR's activity" becomes `gh pr checks <n> --watch`: nothing wakes a local helper.
  - `get_session` and the orchestrator's launch comment have no equivalent: the "Ownership" check of `implement-issue` does not apply, because the package session owns the unit.
- "The orchestrator" in those skills means the package session for a `phase:5` issue or pull request: it launches the helpers, reads the verdict and merges.

## Never

- Start a unit of another session, or add a unit to a list that was fixed.
- Launch a cloud session, let a model other than Opus implement, or let a model other than Fable review or audit.
- Merge a pull request that fails the merge rule or that is not Phase 5.
- Remove `needs-human` from an issue or `paused` from #3 (only the owner does).
- Skip, delete or weaken a test or a gate, or decide a commitment that belongs to the owner.
