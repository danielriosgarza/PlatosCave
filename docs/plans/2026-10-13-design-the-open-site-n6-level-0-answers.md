# Plan

## Goal

Design the open site, level 0 of N6, on the owner's answers Q17 to Q21. `parallax build` at `level: 0` turns a site's course folders into plain files for two host names, and a viewer shell in `apps/web` shows slides, readings and rendered notebooks from those files: no server, no database, no sign-in, no request to `/api`. This is planning run R3, owned by P5-05. It gives the ADR-0002 amendment in full, the design that P5-05 writes into `docs/design/open-site.md`, and scope, files, tests and a size under 600 changed lines for P5-05, P5-14, P5-15, P5-16 and four added items (P5-14a, P5-14b, P5-14c, P5-16a). Parallax as built does not change, and nothing is decided beyond N1 to N10 and the recorded answers.

## Approach

Terms: the **build** is `parallax build` at level 0. The **shell** is the level 0 viewer in `apps/web/src/open/`. An **object** is a file of untrusted content (a PDF, an image, an SVG, the HTML document of a notebook output, the notebook file composed for download). The **site host** and the **content host** are the hosts of `origins.app` and `origins.content`. A **course reference** is a course as `classes[].course` spells it: `<course>` in instructor mode, `<name>/<course>` in school mode. Facts about the repository were checked at `9e22334a`. `packages/cli` does not exist yet, so names of P5-06 to P5-09 are those of `docs/design/site.md` and `docs/design/course-folder.md`; where a unit finds another name on `main`, it uses what exists.

**1. Shape and trust boundaries.**

```text
 author's machine   parallax build, level 0 ─▶ readCourseForSite ─▶ upload rules ─▶ convertRevision ─▶ publicationReport
                      └▶ one write path ─▶ .parallax/open/{site,content} ─▶ audit of every file ─▶ dist/site   dist/content
 static hosting     site host    ◀─ dist/site      index.html at every address, assets/ (compiled shell), JSON data files
                    content host ◀─ dist/content   o/<sha256>.<ext>: every object, and nothing else
 visitor's browser  shell ─GET *.json, site host─▶ the existing viewers ─img, frame with sandbox="", PDF bytes─▶ content host
```

| Part | Trusted for | Limits |
| --- | --- | --- |
| course folders | nothing: untrusted content that may hold hidden material | read only through `readCourseForSite`; every file passes the upload rules, the renderers and the sanitisers of level 1; no file under `exercises/`, `tests/` or `private/` is opened |
| the site's `src/` and logo | the owner's own code, compiled into the shell as at level 1 ([site design](../design/site.md) §1) | cannot import a course file (P5-07's resolver), and the audit of §4 finds a course file's bytes under `site/` |
| `dist/site` | the shell and data that passed a schema | holds no object; the three app-origin surfaces arrive as HTML strings in JSON and pass `sanitizeReading` before insertion |
| `dist/content` | nothing | objects only, each named by its digest; no page, script or data of the site |
| the static hosts | serving files | they enforce nothing: no token, no expiry, no date, no header of ours (Risks) |

**2. Output and addresses.** The build writes into the git-ignored work folder `.parallax/open/` and, after the audit, replaces the content of `dist/` with the two trees. A build that stops leaves `dist/` as it was.

```text
dist/site/                                      for the site host
  index.html                                    the shell; also the address /
  assets/…                                      the compiled shell and the site's own pages
  <page>/index.html                             one copy of index.html per site page (about/index.html)
  courses/index.html      courses/catalogue.json                        the catalogue (openCatalogue)
  courses/<ref>/index.html      courses/<ref>/course.json               a course's topic index (openCourse)
  courses/<ref>/<topic id>/<tab>/index.html                             five addresses per topic
  courses/<ref>/<topic id>/topic.json                                   the lists of the five tabs (openTopic)
  courses/<ref>/<topic id>/<resource id>.json                           one deck, reading, notebook or Shiny app (openResource)
dist/content/o/<sha256>.<ext>                   for the content host
```

- *Addresses.* The catalogue is `/courses`, a course `/courses/<ref>`, a topic `/courses/<ref>/<topic id>/<tab>`, and `?resource=<resource id>` picks a resource of a tab (`&page=<n>` a slide). `<ref>` is the course reference, each folder name percent-encoded in an address and written as the listing spells it on disk. A topic and a resource are named by their **folder id**, as level 1 names them by id: a link survives a renamed file or topic folder, and no rule for slugs is added. A course has no id in a folder ([course folder design](../design/course-folder.md) §4.2), so it is named by its folder, the name the catalogue already carries.
- *Plain files.* Every address has its own `index.html`, a byte-identical copy of the shell's, so a link straight to a topic needs no rewrite rule and no fallback page, and a site page keeps the address it has at levels 1 and 2 (`/about`, from `about/index.html`). Beyond serving the files written, the host is asked for one thing, which static hosting gives: a folder's `index.html` answers the folder's address (Risks). Routes of 1, 2, 3 and 4 segments under `/courses` are disjoint (course in instructor mode, course in school mode, topic in instructor mode, topic in school mode), so the shell needs no mode to route.
- *One path, one output.* Two outputs at one path, also when they differ only in case, stop the build and name both (a course folder called `catalogue.json`, for one).
- *Reserved addresses.* `/courses` and one to four segments under it belong to Parallax at every level: P5-16a adds the patterns `OPEN_ADDRESSES` to the conflict rule of `packages/cli/src/site/pages.ts`. A site page then stops the build at the same addresses at level 0 and at levels 1 and 2: an address of the generated route list or under `/api`, `/assets` or `/content`, as today ([site design](../design/site.md) §6.3), and an address of `OPEN_ADDRESSES`, which adds, at levels 1 and 2, addresses under `/courses` that are no screen today (`/courses/intro`). So a site whose pages build at one level build at the other.
- *Objects.* `contentType → ext` is a fixed table in `openSite.ts`: `application/pdf` pdf, `application/x-ipynb+json` ipynb, `image/png` png, `image/jpeg` jpg, `image/gif` gif, `image/webp` webp, `image/svg+xml` svg, `text/html; charset=utf-8` html. A static host picks the content type from the extension, so the table is what stands in for the type a content token carries. Any other type stops the build; no JavaScript type is in the table.

**3. Static data: `packages/contracts/src/openSite.ts` (P5-14a).** Four strict schemas (`z.strictObject`) for the data files the shell reads, and a fifth, `openNotebookFile`, for the notebook file a visitor downloads; no Node built-in. Ids are the folder id schema that `siteManifest` uses.

| Schema, file | Built from | Keeps | Drops | Replaces |
| --- | --- | --- | --- | --- |
| `openCatalogue`, `catalogue.json`: `{ mode, instructors: [{ name, courses: [{ ref, title }] }] }` | no student view exists (`listCourses` lists a person's classes); the shape is `siteCatalogue` of P5-07a | instructor display names, course titles | has no field for an address, a class, a count or a topic | `classId` and `courseId` by `ref`, the course reference |
| `openCourse`, `course.json`: `{ title, instructors, topics: [openTopicEntry] }` | `getClassTopics.response` and `classTopic` | `course.title` as `title`, `instructors`; per topic `topicId`, `number`, `title`, `objective`, `estimatedMinutes`, `presence`, `firstTab` | `release` (id and version), `course.id`, `cohort` (a class), `resume` and `savedTab` (saved positions), `reviewed` (progress), `state`, `availableAt`, `requires` (a lock needs an account or a date) | `topicId` is the topic's folder id |
| `openTopic`, `topic.json`: `{ slides, reading, notebooks, exercises, tests }`, each a list | `deckSummary`, `readingSummary`, `notebookSummary`; for Exercises and Tests `releasedResource` | `title`; a reading's `kind`; a notebook entry's `type` (`notebook` or `shiny`) | `revisionId`, `position`, `lastRevisionId`; of `releasedResource` also `id`, `type`, `tab`, `position`, `visibility`, `releaseAt`, `credit` | `resourceId` is the resource's folder id. An exercise or test entry is `{ resourceId, title }` and nothing more |
| `openResource`, `<resource id>.json`, a union on `type` with four branches | `slides`: `getSlides.response`. `reading`: `getReading.response`. `notebook`: `getNotebook.response` with `notebookView` as it is. `shiny`: `getShiny.response` | `title`, `pdf.pageCount`, `web.slides`, `kind`, `html`, every field of `notebookView`, a Shiny app's `url` and `origin` | `revisionId`, `status`, `error` (only converted material is written), `pdf.expiresAt` (an expiring token link), `sourceKey` (a storage key) | `pdf.url` and every output `url`: a permanent address on the content origin. A notebook's `sourceKey` by `file`, the address of the notebook file composed for download (`openNotebookFile`), not of the stored `.ipynb`. A Shiny `url` is always there (Q19), and `origin` is null when `origins.shiny` does not list it |

There is no branch of `openResource` for an exercise or a test, and no file is written for one. The writer serialises the **parse result**, never its input, so a key that a nested non-strict schema (`notebookView`) does not name cannot be emitted, and a key that a strict schema does not name stops the build. The file also exports: `courseRef(mode, instructor, course)`; `openPaths` (`catalogue`, `course(ref)`, `courseData(ref)`, `topic(ref, topicId, tab)`, `topicData(ref, topicId)`, `resourceData(ref, topicId, resourceId)`), which the build and the shell both use; `OPEN_ADDRESSES` (`/courses`, `/courses/$a`, `/courses/$a/$b`, `/courses/$a/$b/$c`, `/courses/$a/$b/$c/$d`); `objectExtension(contentType)`; and `viewNotebook(stored, urlFor, html)`, the read-time step of the notebook route (`notebookView` in `apps/server/src/http/routes/notebooks.routes.ts`, which imports `db/` and cannot be loaded by the tool) restated without the server. A test in the server package holds `viewNotebook` equal to what the server does. No policy function is exported: `index.html` carries no content security policy (§9).

`openNotebookFile` is the schema of the one notebook file the build writes: a notebook in nbformat 4.5 composed from the rendered view (`notebookView` after `viewNotebook`), strict at every level. A Markdown cell holds the sanitised rendered HTML with image addresses on the content origin, a raw cell its text, and a code cell its source with `execution_count: null` and `outputs: []`; each cell keeps its id; `metadata` is empty except the language name. The schema has no field for an attachment, for other metadata or for a stored output's payload, so the download holds none, a JavaScript payload included.

**4. The build: `packages/cli/src/open/` (P5-14b, P5-14c, P5-14).**

- `origins.ts`: `assertSeparateHosts({ app, content })`. Host names are compared in lower case, without port, scheme or a trailing dot. `127.0.0.1` and `localhost` differ (the development pair of ADR-0002); `localhost:4310` and `localhost:4311` do not.
- `output.ts`, the one write path: `createOutput({ workDir, contentOrigin })` returns `object(bytes, contentType)` (writes `content/o/<sha256>.<ext>`, returns its address on the content origin), `data(path, schema, value)` (writes `JSON.stringify(schema.parse(value))` at a `.json` path under `site/`), `shell(path, bytes)` (a file of the compiled shell), `address(path)` (a copy of the shell's `index.html`), `untrusted(sha256)` (the digest of a course file the build opened) and `finish()`. Only `object` takes content bytes, and it can write only under `content/`. `finish()` is the audit: it reads every file of the work folder again. Under `site/` a file must be a recorded shell file with the recorded bytes, an `index.html` equal to the shell's, or a data file that still passes the schema its name gives; no file may have the digest of an object or of a course file; every object address in a data file (`pdf.url`, `file`, an output's `url`, a `src` in an HTML string) must be on the content origin at a path the build wrote. Under `content/` a file must be `o/<its own sha256>.<ext of the table>`. Any failure is a `BuildStop` that names the file. `placeOutput(workDir, distDir)` runs only after it.
- `course.ts`: `buildCourse({ dir, ref, instructors, shinyOrigins }, out)` for one course folder. (a) `readCourseForSite(dir)`; an error problem stops the course with the reader's lines, as `parallax check` prints them. (b) The upload rules of `courseFiles.ts` on every file the manifest lists, data files included. (c) For each resource, `revisionPayload` and `convertRevision`. (d) `publicationReport(manifest, derived, { approvedShinyOrigins: shinyOrigins, runtimes: [] })`. (e) Data and objects through `out`. Image sources in HTML are set by `resolveReadingImages` of `apps/server/src/content/reading.ts`, loaded through `paths.ts` like the conversion entry; notebooks go through `viewNotebook`, and a notebook's `file` is the object that `notebookDownload` gives. `presence` comes from the resources of the manifest, which holds the visible ones only (§5), and `firstTab` from the rule of §4 of the specification (`tabs.find`). `buildCourse` writes every resource the manifest hands it and selects none: it has no filter for visibility or for dates (§5).
- `download.ts`: `notebookDownload(view: NotebookView): OpenNotebookFile`, the notebook file a visitor downloads, composed from the rendered view as `openNotebookFile` states it (§3). `buildCourse` writes `JSON.stringify(openNotebookFile.parse(…))` through `out.object` with the type `application/x-ipynb+json`. The notebook's own `.ipynb` is read for conversion, its digest goes to `out.untrusted`, and its bytes are written nowhere.
- `build.ts`: `buildOpenSite(site, { shell })`. It checks the hosts, builds every course of every instructor folder (`src/site/folders.ts`), prints every problem of every course and stops if one is an error, writes `catalogue.json`, calls `shell(site, out)`, writes the address copies (the screens of §2 and each page that `src/site/pages.ts` finds), runs `finish()` and places the output. It is called from the level switch of `packages/cli/src/commands/build.ts`.
- `shell.ts`: the type `ShellCompiler` and, in P5-14, `noViewerYet`, which stops with the message and exit code that P5-07 gave the level 0 stop. P5-16a adds `compileOpenShell` and switches the command to it.

*Storage keys and object ids.* There is no course row, so the key of a file is `open/objects/<sha256 of its bytes>`, the form `objectKey` gives with the prefix `open`, and `open` is the prefix handed to `convertRevision` for a notebook's output objects. `io.read(key, maxBytes)` answers from the reader's `open(file)`, with the size limit a storage read has. The build writes an object from its own read of the file, because a conversion may take the buffer it was given. There is no object row, so no object id: `revisionPayload` is called for a notebook **without data files**, the form of a notebook that has none, and the notebook's bytes are the file's own. Those bytes go to conversion only: the file a visitor downloads is composed (§3).

*A notebook's data files.* They are checked by the upload rules, so the same folder is accepted or refused at both levels, and they are not converted, not written and not listed: the student view of level 1 has no field for them, and they reach a student only inside a connected session. Whether a level 0 site should offer them is an open question.

*A topic with only exercises and tests.* `publicationReport` on a site manifest reports it as `empty_topic`, a warning. The build drops that warning for a topic that lists an exercise or a test, builds the topic like any other, and keeps the warning for a topic with no visible resource, which is built too. The topic index marks Exercises and Tests as present, `firstTab` is the first populated tab, and the three material tabs show the existing empty lines.

*What stops a build.* Exit code 1 for each.

| Rule | Enforced in | Tests |
| --- | --- | --- |
| The two origins share a host | `siteConfig` (P5-07a), when any command loads the configuration; again `assertSeparateHosts`, the first step of `buildOpenSite` | `origins.test.ts` (P5-14b); `A45 a level 0 build without a distinct content origin stops` (P5-14) |
| An untrusted object would land under `site/` | `output.ts`: the write path, and the audit in `finish()` | `output.test.ts` (P5-14b); `A45 untrusted objects are written only under content/, and a build stops when one would land under site/` (P5-14) |
| An object of a type outside the table, a JavaScript type among them | `object()` | `output.test.ts`; `A45 no JavaScript output is in a level 0 build` (P5-14) |
| An answer-bearing file in a tree declared public; any other reader error | `readCourseForSite` | `A43 parallax build at level 0 refuses a public tree that holds a definition, as parallax check does` (P5-14) |
| A file the upload rules refuse; an error of publication's report | `courseFiles.ts`; `publicationReport` | `course.test.ts` (P5-14c); `A40 a level 0 build stops with the report of the existing validation and writes no site` (P5-14) |

These are checks of the tool's own configuration and its own output. No command and no test contacts a deployed host or reads a response header of one.

**5. What a build leaves out.** The list is in the amendment (§9). It holds by structure, in three places: the reader's site entry hands the build no definition and no hidden resource; the schemas have no field for a definition, an answer, feedback, a hint, a solution, a check, a rubric, a release date, a class, an account or a grade; and no file is written for an exercise or a test. Hidden and dated resources have the paragraph below. Practice exercises checked in the browser are not built: no checking code and no answer reaches the output. A notebook's own `.ipynb` is not written: the page shows its stored outputs through the rendered view, and the file offered for download is composed without outputs, attachments or metadata beyond the language name (§3), so the download holds no stored output, and a payload that the renderer does not store, a JavaScript output's among them, is in no emitted file. The build runs no notebook cell: `convertRevision` imports a notebook with its stored outputs, and a static host runs nothing, so no notebook code runs where the site is served. Moving a site from level 1 to level 0 is a change of `level` and `parallax build`: the build reads the folder, and no step of this plan exports or publishes anything from a database into a site (Q21).

*Hidden and future-dated resources: the build has no filter of its own.* The reader's site manifest holds the visible resources only, so a resource marked hidden in `topic.yaml` is never handed to the build, and a folder states no release date, so there is no resource to leave out by date ([course folder design](../design/course-folder.md) §7). The build therefore adds no check of visibility and none of dates: it takes no build time and does not call `openToStudent` of `apps/server/src/content/availability.ts`, and no unit of this run edits `packages/cli/scripts/vendor.ts` to pack that file or any other. About release dates the build does nothing, because a folder states none. No date field is added to the folder: no unit adds a key to `topic.yaml` or to any other file of a folder, and the reader's schemas are not edited. The amendment (§9) says that the date rule binds any later form of the folder that states one. That a hidden resource is left out is shown on the output by a named test of P5-14c in `packages/cli/src/open/course.test.ts`, `test('a resource marked hidden in topic.yaml has no entry, no data file and no object')`: the fixture's hidden resource, a PDF reading, is in no list of `topic.json`, no `<resource id>.json` exists for it and no object under `content/` has the digest of its file, while the visible PDF reading beside it has all three. The A43 leak test of P5-14 plants sentinels in the same resource's title and file and finds them in no emitted file.

No text claims that something was saved, connected or submitted; "Saved outputs" is the existing label for the outputs a notebook file was stored with.

> ## Amendment: Open site (level 0)
>
> Added 2026-10-13 (P5-05) for requirement N6, on the owner's answers Q17 to Q21 (issue #559; plan §8). The Decision above is not changed. It stays the whole rule for every installation that has a server (levels 1 and 2): a scope on every route, 404 for non-members, content tokens on the content origin. Detailed design: [docs/design/open-site.md](../design/open-site.md).
>
> **No server and no scope to resolve.** A level 0 site is what `parallax build` writes for a site whose configuration says `level: 0`: plain files for static hosting. It has no server, no `/api`, no database, no account, no session and no cookie. Nothing is read on a person's behalf, so there is no principal, no membership and no scope to resolve, and `registerRoute`, the scope resolver and the isolation matrix have nothing to guard there. They are not weakened or bypassed: no code of a level 0 site reaches them. What stands in for authorisation is omission when the site is built: a level 0 site holds only what anyone may read. The build reads course folders and nothing else. It reads no database and runs with `DATABASE_URL` unset. Moving a site to level 0 is a change of `level` and a rebuild from the folder; nothing is exported or published from a database. The viewer makes no request to `/api`, offers no sign-in, provider button or class control, shows no note, highlight, sketch or discussion control, and keeps nothing in the visitor's browser.
>
> **What a build leaves out.** A level 0 build reads a course folder only through the reader's site entry (`readCourseForSite`) and writes its data only through the strict allow-list schemas of `packages/contracts/src/openSite.ts`: what is written is the result of parsing, so a key that a schema does not name is refused or dropped and never written. Neither has a place for any of these:
>
> - every test definition: questions, checks (public and hidden), code files, rubrics and grading settings;
> - every exercise definition: steps, answers, feedback, hints and solutions. Exercises are not checked in the browser, and no checking code is built;
> - every resource that is not visible to students: the reader's site entry hands a build the visible ones only, and a build has no filter of its own;
> - every resource whose release date is in the future, because a static host cannot enforce a date. A course folder states no release date today, so a build has none to compare, and none is added; the rule binds any later form of the folder that states one;
> - the private overlay and every file under a topic's `exercises/` and `tests/` folders. The build opens none of them, and in a tree declared public a file there stops the build, as it stops `parallax check`;
> - the uploaded Markdown or HTML source of a native reading (only its ingested HTML is written, as under **Readings on the app origin**), a web deck's Markdown, a notebook's data files, and a notebook's own `.ipynb` file with its stored output payloads, metadata and attachments (the download is composed without them, below);
> - completion rules, prerequisite locks, saved positions, notes, highlights, sketches, discussion, attempts, submissions, grades, accounts, memberships, classes, enrolment codes and audit events, and an instructor's address (the display name is written).
>
> The Exercises and Tests tabs list titles, and no file is written for an exercise or a test.
>
> **The equivalent of the content origin.** The build writes two trees for two host names: `site/` for `origins.app` and `content/` for `origins.content`. Untrusted content is notebook HTML outputs, images (notebook outputs, cell attachments, and images of readings and slides), SVG, uploads and PDFs, and with them the notebook file that the build composes for download. It is written only to `content/`, as content-addressed files `o/<sha256>.<extension>`, and the site names each one by its address on the configured content origin; two uploads are not written at all, a notebook's data files and its own `.ipynb` file (above). The extension comes from a fixed table of eight content types (PDF, notebook file, PNG, JPEG, GIF, WebP, SVG, HTML with its charset). A type outside the table stops the build, and the table has no JavaScript type. So the content host holds no page, script or data file of the site, and the site host holds no untrusted object: a document or image opened on the content host, in a frame or on its own, has another origin than the site. Conversion is the conversion of level 1 (`convertRevision` over the same renderers and limits): HTML outputs are cleaned with `outputSchema` and SVG with `sanitizeSvg`, and the viewer frames HTML outputs with `sandbox=""` as today. The three app-origin surfaces keep both sanitisers, each of which alone must stop script: `readingSchema` when the build converts, and DOMPurify (`sanitizeReading`) in the browser, held to the one allow-list. Their HTML travels in JSON data files on the site host, as it travels in API replies on the app origin at level 1. JavaScript outputs are never served: the notebook renderer never stores one, the build has no way to write one, and a test asserts on every emitted file that none holds one. A notebook's own `.ipynb` file, which can hold such a payload as text, is not written. The download is a notebook that the build composes from the rendered view: Markdown cells hold the sanitised rendered HTML with image addresses on the content origin, raw cells their text, and code cells their source with no execution count and no outputs; its metadata is empty except the language name. The page still shows the stored outputs. The composed file is written to `content/` and is never shown as a page or run.
>
> **The rule that stops a build.** `parallax build` at level 0 stops, says why and leaves `dist/` as it was in two cases. (1) The host names of `origins.app` and `origins.content` are equal, compared in lower case without scheme, port or a trailing dot. The configuration schema refuses this, and the build checks again. (2) An untrusted object would land under `site/`. All output goes through one write path, in which only the compiled viewer and JSON that passed its schema can be written under `site/`. Before anything is put in place every file of the output is read again. Under `site/` a file must be a file of the compiled viewer, a copy of its `index.html` at an address, or a data file that still passes its schema; none may have the bytes of a course file or of an object; and every object address in a data file must be on the content origin. Under `content/` a file must be named by its own digest, with an extension of the table. A build also stops where conversion stops at level 1: on what the folder reader, the upload rules and publication's report refuse. A warning of that report stops no build, at level 0 as at level 1: a topic whose only resources are exercises and tests is built and listed, and a Shiny app on an origin that the configuration does not list is written with its external link and is not framed.
>
> **What the build checks, and what it cannot.** The tool checks only what a build can know: these rules, on its own configuration and its own output. It contacts no host and checks no response header of a deployed host. A static host mints no token, so an object's address is permanent and public; that is sound only because a level 0 site holds nothing private. A static host also does not send what the content origin sends at level 1 (`Content-Security-Policy: sandbox`, `X-Content-Type-Options`, `Content-Disposition`) unless its operator adds them. The site host likewise does not send the policy header of the app origin (`script-src 'self'`, frames only from the content origin and the listed Shiny origins, `frame-ancestors 'none'`), and the viewer's `index.html` carries no policy in its place. What stands in at level 0 for those headers is the two host names, the `sandbox=""` frame around every HTML output, the cleaning of HTML outputs and SVG at conversion, and the two sanitisers of the three app-origin surfaces.
>
> **Hosting requirements.** There are two. (1) Two host names: one serves `site/` at its root and the other serves `content/` at its root. Two paths of one host separate nothing, and a build for one host name stops. (2) For PDFs, the content host answers cross-origin range requests from the site: a `GET` that carries the site's `Origin`, with or without a `Range` header, is answered with `Access-Control-Allow-Origin` for that origin (or `*`); a ranged one with status 206 and `Content-Range`; `Content-Range`, `Accept-Ranges` and `Content-Length` are exposed; and the preflight that a `Range` header causes is answered. On hosting that does not, a PDF deck or reading says that it could not be loaded and keeps its download link, and everything else works. Every address of the site is a file, an `index.html` at that address, so no rewrite rule and no fallback page is asked for.

## Risks

- **A static host enforces nothing.** It sends no `sandbox` policy, no `nosniff`, no `Content-Disposition` and no `frame-ancestors`, mints no token and knows no date. Level 0 rests on omission at build time, two origins, `sandbox=""` on the frame, and the sanitisers at conversion and in the browser. A file on the content host opened on its own runs as that host and reaches nothing of the site, which the A45 browser test shows; it is still not what level 1 gives. The build checks none of this on a deployed host, by decision.
- **The second host name has a cost.** A level 0 site needs two host names, each serving its tree at the root. Two project pages of one account on a shared host have one host name, and a site under a path is not a host of its own: the build stops. A site on one host name stays a later owner decision.
- **Hosts differ in what they add.** A host that forbids framing or cross-origin embedding (`X-Frame-Options`, `Cross-Origin-Resource-Policy: same-origin`) shows no HTML output or image, and one without range answers shows no PDF, each with a plain message. Addresses rely on the directory index that every static host has, `/` included, and on the name of a course folder being served as it is spelled.
- **The browser proof comes last.** A44 and A45 run in a browser only in session 4. Until then the switch is closed, so no site can be built; the cost is that a fault of the shell on real hosts shows late.
- **Sizes are estimates, and three sessions are full.** P5-14b, P5-14, P5-15, P5-16 and P5-16a are estimated at 520 to 553 lines, which leaves 47 to 80 under the limit; P5-05 stands at 569 with this plan at its present length, and its design document is written to what is left. A further split needs a further session, which raises the count of sessions to seven.
- **Names of units not yet built.** `readCourseForSite`, `convertRevision`, `publicationReport`, `siteRoutes`, the compile function of `build/web.ts` and the loader are known from two designs only. A different signature changes glue, not the design; a missing entry point (the validator or `reading.ts` not in the packed copy) is caught by the test of P5-14c.
- **One restatement.** `viewNotebook` restates server code that the tool cannot load. The parity test of P5-14a fails when either side changes alone.
- **No policy in `index.html`.** A level 0 site sends no content security policy unless its operator sets headers. A site page can then load a script or an image from another origin, which the header blocks at level 1, and for the three app-origin surfaces the two sanitisers are the whole defence. Open question 2 puts recommended headers to the owner.
- **The notebook download is not the class's file.** At level 1 a student downloads the stored `.ipynb` with its outputs. At level 0 the download has no outputs, no attachments and no metadata beyond the language name, and its Markdown cells hold rendered HTML; the page shows the stored outputs.
- **A second browser workflow.** The level 0 suite runs in `.github/workflows/open-site.yml`, beside the `e2e` job of `ci.yml`, which it does not lengthen. A pull request then waits for one more check, and the workflow needs an image that has the browser of Playwright 1.56.1.
- **Size of a course.** Objects are read into memory one at a time and conversions run one after another; a large course builds slowly. `dist/content` is written anew by every build, so the address of an object that a course no longer has stops answering.
