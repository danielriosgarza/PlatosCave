# Plan

## Goal

Make Parallax installable and pluggable as `docs/needed_specs.md` states it (N1 to N10). One command creates a site from a template. The site folder holds only its own files and its own JSX pages. A course folder becomes the same material the editor produces. A site runs at level 0 (plain files), level 1 (server, PostgreSQL 16, a way to sign in) or level 2 (runner). Parallax as built does not change.

The work is 25 units in **4 close-ended sessions**. Each session is started by the phrase "continue package development" and ends by reporting "x of y done". Opus implements every unit, complex design goes through `/collab-independent-plan` first, and Fable reviews every unit before it counts as done.

Two owner decisions of 2026-10-12 were made after this plan was judged and are written into it: package development is local, on the owner's machine, and no cloud session is launched; and the owner stops the hourly orchestrator for the whole of package development.

**3. The trigger and what a session does (K5, K6).** The owner types, in a local Claude Code session on the owner's machine, opened in the repository's working copy: "continue package development". A session that receives it does exactly this:

1. *Finds the procedure.* After step 2 has merged, `CLAUDE.md` (loaded into every session) names `.claude/skills/package-development/SKILL.md`, which holds this section. Before that, this plan is the only file under `docs/plans/` and the only file under `docs/` that contains the phrase (`grep -rl "continue package development" docs/`). The plan and `docs/needed_specs.md` are untracked today, so the first trigger is given in the working copy where the plan was landed, on the owner's machine; step 2 commits both, and from then on a fresh clone is enough.
2. *Computes progress* from `origin/main` only. **y** is the number of Phase 5 units: the count of `### P5-` headings in `docs/delivery/plan.md` (`grep -c '^### P5-'`), which is 25 once step 3 has merged and one more for every item added later; before step 3 has merged it is the 25 units of the Steps below. **x** is the number of those units whose `docs/delivery/done/<ID>.txt` is on `origin/main`. Each unit's own pull request adds that file, and a pull request reaches `main` only under the merge rule, so a unit counts only after Fable approved it. Work in flight is read from GitHub: the unit's issue and pull request, their labels and `Review verdict:` comments. There is no second dashboard and nothing is read from an earlier chat (README:18), so every fresh session gets the same two numbers, on the first run and after an interrupted one.
3. *Selects the session:* the lowest-numbered session that has a unit not done; a further session written with a letter (`2a`) comes directly after the session it is named for. Its list is the one fixed in the Sessions table (section 4; step 3 copies the table into `docs/delivery/plan.md`), together with the added items whose `Session:` line on `main` names it. Nothing is added to a list once its session has started. If every unit still open in that session is labelled `needs-human`, it reports that it waits for the owner, with "x of y done", and stops.
4. *Checks* that it runs as Opus, on the owner's machine and not as a cloud session, that OD-1 is closed and the Delivery status issue (#3) carries `paused` (for everything after step 1), that Fable can be launched, and, for a session with a command run (sessions 1, 2 and 3), that the command and its tools are installed. If one of these checks fails it says why, reports "x of y done" and stops. It also lists which local tools of row P-d are present. A missing one stops nothing: the suite that needs it runs in CI only, and the report names it.
5. *Works the list* in dependency order with at most three units in flight (README limit), each by the unit procedure below. A resumed unit continues from its state: approved and green, merge; changes requested, Opus fixes; no verdict on the head, a new Fable review; issue without pull request, start; no issue, create it; `needs-human`, skip.
6. *Stops* at the end condition: every unit of the session is done, or labelled `needs-human` with an escalate record. It reports, for example, `Session 2 of 4 closed. 13 of 25 done. Next: session 3 (P5-14 to P5-21).` and ends. It never starts a unit of the next session, even with time left. With all units done it reports "25 of 25 done" (y of y, if items were added) and does nothing else.

*Unit procedure (K7 to K10).*

- **Issue.** `[P5-nn] Title`. The session whose list holds the unit creates it when work on the unit starts; the issue of an added item is created by the session that found it. No Phase 5 issue is created before the orchestrator is stopped: the owner confirms it at OD-1 (row P-a), and issue #3 carries `paused` for the whole of package development. From step 2 on the orchestrate skill also skips `phase:5`, which holds if the orchestrator is ever started again. Labels `plan`, `phase:5`, `model:opus` (`model:fable` for the design units 03, 04 and 05, which README defines as a design item implemented by Opus at maximum effort), `security` where the step says so, one status label; the body is the plan entry with `Depends on:` and `Touches:`. One unit is one issue and one pull request of at most 600 changed lines (plan §0).
- **Simple unit.** Opus implements it directly, following `.claude/skills/implement-issue/SKILL.md` steps 1 to 4 (tests first, done file, pull request with `Closes #`).
- **Complex unit.** It is planned with `/collab-independent-plan` and then implemented by Opus. Five runs plan all 19 complex units (table below). The unit that owns a run executes the command first; the other units of that run start only after it has landed, and implement its plan. The session runs the command exactly as `~/.claude/commands/collab-independent-plan.md` defines it, in its default mode judged by Jev, with the TASK text of the unit's plan entry and no flags. `/collab-independent-plan` is never given `--judge classic` or any other flag that turns Jev off. If Jev's preflight fails, or Jev drops out later, the session tells the owner and asks before any classic fallback; without the owner's yes the unit is labelled `needs-human`. If one of the command's two authoring sides is unavailable, the session stops that unit and says so; it never substitutes a side. The landed plan (`docs/plans/<date>-<slug>.md`) is committed in the unit's pull request.
- **Implementer.** Always Opus: the session itself, or an Opus subagent that the session launches on the same machine, in its own worktree. No cloud session is launched. No other model writes Phase 5 work. A failed attempt is retried with Opus, the third time at maximum effort, then `needs-human`.
- **Review.** When CI is green on the head, the package session launches a fresh Fable reviewer, one per review round, as a local subagent in its own worktree. It starts from `main` and follows `.claude/skills/review-pr/SKILL.md`: it runs the checks, posts findings and a `Review verdict:` comment naming the head SHA, sets the review label, and never pushes. Fable runs at maximum effort, and with `/security-review` for `security` units, where README asks for it (`.claude/`, `.github/`, `CLAUDE.md`, `docs/adr/`, `docs/delivery/README.md`). Opus fixes the findings; Fable never does. No other model reviews: a third `CHANGES REQUESTED` becomes `needs-human` instead of going to an arbiter, and if Fable cannot be launched the unit waits, labelled `needs-human`. For a review that starts before P5-01 is on `main` (P5-01 itself, and P5-02 when it runs beside it), the skill on `main` still has the old text, so the launch prompt states that Fable is the only reviewer and that there is no arbiter round, as the owner's task sets.
- **Merge.** The package session squash-merges under README's merge rule as it stands (approved verdict on the head, up to date with `main`, CI green, issue not `needs-human`), once the owner has allowed it at OD-1 (row P-b). If the owner said no, each approved, green pull request waits for the owner's merge: the session goes on with the units that do not depend on it and, when none is left, reports that it waits for the owner's merge and stops.
- **Scope and added items.** Work found outside a unit becomes a new plan item (`P5-nna`, or `P5-AUDn` when the audit raised it) with its own issue. It is never added to the open pull request's work or to the running session. Before work on it starts, the item gets its own `### P5-` heading in `docs/delivery/plan.md` on `main`, which raises y by one, with its class (simple, or complex and its run), `Depends on:`, and two lines that assign it: `Session:` and `Boundary:`. `Session:` names the session that takes it: always one that has not started, after every unit the item depends on and no later than the first unit that needs it. Within those limits it is the earliest session of the table that keeps to the size rule of section 4 with the item added, and where there is none a further session, written with a letter after the session it follows (`2a`) or, after session 4, numbered 5, then 6. `Boundary:` names the dependency or size limit that puts the item there; the running session is closed to it because its list was fixed before it started. If no session meets these conditions, for example because a unit of the running session needs the item, the item takes the further session that follows the running one, and the unit that cannot be finished without it is labelled `needs-human`: only the owner changes a fixed list. The heading is committed, as plan lines only, in the pull request of the unit that found it (P5-25's pull request for an audit finding), and that pull request is not merged without it. The heading therefore reaches `main` together with that unit's done file, and no report says "y of y done" while such an item is open.

**4. Sessions (K2, K3, K4).**

*What a session is.* A session is one fixed list of units, started by the phrase. A trigger covers that list from the state that `main` and GitHub show up to the end condition: for each unit the run of the command if the unit owns one, the Opus implementation, the Fable review rounds, the fixes and the merge. The Opus subagents and Fable reviewers that a session launches work inside it: the phrase does not start them, and the count of sessions does not include them. A list is fixed before its session starts: it is the row of the table below and the added items whose `Session:` line on `main` names the session (section 3), and nothing joins it afterwards.

*Why four is the minimum.* Total: **4 sessions**.

- *Size rule.* A session holds at most 8 units, at most 4 units in one dependency chain, and at most 3 command runs. A dependent unit can start only when its predecessor is on `main`, which needs an Opus implementation, CI on the head and again after the update from `main` (README merge rule 2), and at least one Fable round; a chain therefore cannot be shortened by working in parallel. Four links and eight units are what one session can finish and have reviewed without dropping review findings from its context. This is a judgment (see Risks).
- *Boundary 1 | 2 is forced by closure.* The lists of sessions 2 to 4 consist of units whose scope, files and tests are written by the design units 03, 04 and 05, which rewrite their follow-on entries in `docs/delivery/plan.md` (the repository's rule for design items, `implement-issue` §Design items). A list that is fixed before its session starts cannot exist before session 1 has ended. Session 1 itself cannot shrink: OD-1 comes before everything, and the three designs depend on each other in order.
- *Boundaries 2 | 3 and 3 | 4 are forced by the critical path.* After session 1 the longest chain is 06 → 07 → 08 → 14 → 15 → 16 → 17 → 22 → 23 → 24 → 25: eleven units. At four per session that is three sessions. The 20 units after session 1 need three sessions by the unit limit as well.
- *The audit comes last by definition:* it reads `main` after every other unit has merged, so it closes session 4 and cannot move earlier.
- *Fewer units is not available:* merging units would push them past 600 changed lines, the size at which plan §0 tells an item to split.

*Sessions and triggers.* When nothing fails and nothing is added, the four sessions take four triggers, one each. Rework never adds a session: review rounds happen inside the unit's session. A session that stops before every unit on its list is done is resumed under the same number by the next trigger, which costs one more trigger and no session. That happens when the owner has not answered OD-1 in the first sitting, when a check of section 3 (item 4) fails, when a session is interrupted or stops with a unit at `needs-human`, and, if the owner answered no to row P-b, when it waits for the owner's merge. A further session exists only for added items that no session of the table can take (section 3): work found outside a unit or the surplus of a unit that outgrows 600 changed lines, an OD-1 answer that adds more work than session 4 may hold, or a blocking audit finding that P5-25 does not fix. Its list is the items whose `Session:` line names it, within the size rule and frozen from `main` at its start, like the others. Each further session adds one session and one trigger, and the report that announces it states the new total.

**6. Rules that bind every step.**

- *Nothing built changes (K11, K13).* No step edits an existing route, screen, viewer output, editor or review screen, the draft/release/adoption model, or where code runs. `/` keeps its redirect unless a site supplies a front page. Provider buttons appear only when a provider is configured. `open` defaults to false. Refactors (steps 7 and 10) keep every existing test file unmodified and green. A commitment beyond N1 to N10 and the OD-1 answers is escalated (`needs-human`), not decided by a session. School mode is one installation with several instructors; no step adds a shared installation for many projects, a settings-centred "material / event / engine" model, or JSX or MDX inside course content.
- *Migrations (K16).* The chain is extended to `… → P4-09 → P5-10 → P5-12 → P5-18`, each depending on the one before. P5-10 adds `0013_p5-10_open_class.sql`. P5-12 adds a migration only if run R4 needs a table for provider identities. P5-18 adds one only if run R2 needs stored source identity, or run R1 needs stored state for setup (P5-19 follows the chain and adds none itself). A chain item that needs none adds none, and each migration takes the next free number. No other item adds a migration or touches `apps/server/drizzle/` or `db/schema/index.ts`; a column another item needs goes into the next unmerged chain item. A schema need that appears after P5-18 has merged requires a new named chain item: it is appended to the chain in `docs/delivery/plan.md` §0 (`… → P5-18 → P5-nna`), as an added item under section 3, before any pull request adds the migration.
- *Untrusted content at level 0 (K17).* Decided in step 6 (ADR-0002 amendment), built in step 15; nothing can serve a level 0 site before step 16. The build writes notebook HTML outputs, images, SVG, uploads and PDFs only to `content/`, stops when the two origins share a host or an object would land under `site/`, and frames HTML outputs with `sandbox=""` as today. The three app-origin surfaces keep their two sanitisers. JavaScript outputs are never served: the notebook renderer never stores them, and a test asserts it for the build. The hosting must give two host names and, for PDFs, cross-origin range requests from the content host; step 6 writes these requirements into the ADR amendment and step 25 into the guide. The tool checks, at build time, only what a build can know: that the two configured origins have different hosts and that no untrusted object lands under `site/`. It checks no response header of a deployed host.
- *Hidden material (K18).* A level 0 build leaves out every test definition (questions, checks, files, rubrics), every exercise's answers, feedback, hints and solutions, and every resource that is not student-visible or whose release date is in the future (a static host cannot enforce a date). The data is written through schemas that have no field for answers, and A43 plants sentinel strings in hidden checks, solutions and answers and asserts that no emitted file contains them. In a tree declared public, `exercises/` and `tests/` definitions are read from the private overlay (git-ignored in the template), and `parallax check` and `parallax build` refuse an answer-bearing definition in the public tree. Practice exercises checked in the browser are built only if the owner says so at OD-1 (Q17). Automatic release (N10) changes who releases, not what the release policy shows.
- *Authorization (K19).* New `/api/*` routes are the provider start and callback and the list of sign-in methods (public scope, like the link routes) and the class setting. Each goes through `registerRoute` with a contract that declares `scope` and `examples`; the isolation matrix replays them; non-members get 404. `parallax sync` and `parallax apply` add no route: they run on the server's host and reach scoped tables only through `forCourse` and `forClass` with a scope from `resolveActorScope`, in modules under `apps/server/src/db/`. Their caller is the operator, who has shell access to that host; there is no network caller and no new credential.
- *Tests (K20).* A test that realises a scenario carries its ID in the title; every unit adds `docs/delivery/done/<ID>.txt`; integration tests use real PostgreSQL; no step skips, deletes or weakens an existing test.
- *Public repository (K21).* Templates, fixtures and examples use `example.org` addresses and fictional courses. Secrets are generated on the operator's machine into a git-ignored file. The provider tests use an in-process issuer, the Colab tests a fake `colab` program. Workflows read registry tokens from repository secrets only. Issues, `[P5-OD1]` and its answers included, pull requests and commit metadata are public as well: they hold no secret, credential or personal data, and row P-c records package and namespace names only.
- *Interface (K22).* The template's front page and the sign-in additions use the `--pc-*` tokens and state content, actions, audience and real state. No step lets a site change the look (Q10).
- *Database (K23).* PostgreSQL 16 only; the plug is where it lives. Level 0 has no database, and its build runs with `DATABASE_URL` unset.
- *File form (K24).* A YAML file is parsed and then checked by `exerciseV1` or `testV1`; the result is what the editor saves. The loader fills a code file's `content` from the file beside the definition and adds nothing else. No field, question kind or stored format is added.
- *Compute (K25).* Notebook code never runs on the server that serves the site. Colab over SSH is offered for paid Colab only, and the interface says so; open-in-Colab-and-upload stays the route for free Colab.
- *Environment (K26).* Sessions are local, on the owner's Windows machine (owner decision, 2026-10-12). No step needs a Docker daemon in a session or runs `playwright install`. Image builds, the one-host compose start and the runner run in CI behind the documented `*.docker.*` gate. A suite whose local tool is missing (row P-d) runs in CI only.

## Risks

- **Session size is a judgment.** Eight units or four in a chain may be more than one sitting holds, and session 1 is the longest (three command runs). A session that cannot finish is resumed under the same number by the next trigger, so the count stays four while the number of triggers may grow. The run of the command that produced this plan took about three hours on the owner's machine, and session 1 holds three runs.
- **The command's tools are local.** `~/.claude/commands/collab-independent-plan.md` and its helper scripts are installed for the owner's user, not in the repository. Package sessions run on that machine (owner decision, 2026-10-12), where the command was present on that date, so sessions 1 to 3 can run it; a session that cannot find it stops at the run's unit and never substitutes.
- **Fable must be available.** README says it is no longer used. OD-1 confirms how it is launched; if it cannot be launched, units wait rather than being reviewed by another model. A local session's subagent launcher listed Fable as a model on 2026-10-12.
- **The repository was built on Linux only.** CI runs on `ubuntu-24.04`, and on the owner's Windows machine `main` failed its own checks until `[P4-WIN1]` (row P-d). New code can break Windows again without CI noticing, since no CI job runs on Windows; a session sees it in its local `pnpm check`. The integration and e2e suites have not run on this machine yet, and `scripts/pg-local.sh` is written for Linux, so the database comes from Docker here. A change to that script, or a Windows CI job, is outside every unit and would be an added item.
- **A second host name at level 0.** A separate content origin is the safe equivalent, but it makes a level 0 site harder to host than a Docusaurus site: two project pages of one GitHub account share a host. PDFs also need cross-origin range requests from the content host, as `apps/server/src/http/content.ts:105-120` provides today. Step 6 must state the hosting requirements; a one-host variant would need its own ADR and owner decision.
- **A second host at level 2.** With the runner on its own host (Q27), PostgreSQL must accept the restricted runner role from that host. Run R1 designs that connection, and the owner may still answer Q27 differently at OD-1.
- **Compiling site pages into the web application.** The route tree is generated (`routeTree.gen.ts`), and adding pages without touching existing routes is the least proven part of area A. Run R1 and the unmodified e2e suite are the guard.
- **Packaging the renderers.** They run in worker threads from `*.worker.mjs` files, which is awkward inside a published package. The scaffold test of step 18 installs the packed packages to catch it.
- **Accounts keyed by a verified address.** A provider that asserts an address it has not verified would allow account takeover. Step 13 refuses unverified addresses and gets `/security-review`.
- **Colab over SSH is untested against Colab.** The tests use a fake program; Google's CLI lists Linux and macOS only; free runtimes forbid it. A real check needs the owner's paid plan and cannot be automated without credentials.
- **Docker-only checks give slow feedback.** The compose start, images and runner cannot run in a session; steps 23 and 24 keep the Docker-touching code thin and test the logic around it in `pnpm check`.
- **Identity across conversions.** A wrong scheme detaches notes and attempts on the second conversion. Step 5 designs it before any code, and A41 tests it on real PostgreSQL.
- **Estimates of unit size.** A design run may show that a unit exceeds 600 lines. The surplus becomes an added item (section 3), which raises y and can add a further session; step 4, 5 or 6 must then write its heading, with its `Session:` and `Boundary:` lines, in plan §Phase 5.
