# Plan

## Goal

A course folder becomes the material the editor produces (N4, N5; answers Q12 to Q16), through one reader and the functions that exist: the upload rules, the renderers in their worker threads, the draft services and the publication. This run (R2, owned by P5-04) fixes the layout, `course.yaml` and `topic.yaml`, identity across conversions, the YAML form of exercises and tests, the private overlay, `parallax check` and `parallax sync`. It gives P5-04, P5-08, P5-09 and P5-18 their scope, files, tests and sizes, and adds seven items for the work that does not fit 600 changed lines. No table, column, route, contract, screen or stored format is added, and P5-18 adds no migration.

## Approach

**1. Shape.** The author's machine runs `parallax check`, which reads the folder and reports. A level 0 build (run R3) reads the same folder through the reader's site entry and converts with the same conversion entry. At level 1 `parallax sync` reads the folder on the server's host and pipes one bundle to a script in the server image; the script writes drafts through the draft services, the existing job converts, and the existing publication validates and snapshots. Course folders and the overlay are untrusted content and may hold hidden material; the operator has shell access to the host. Facts about the repository below were read at `9f7bd9ec`.

**2. Layout (K6).** `courses/<course>/` holds `course.yaml` and one folder per topic; a topic folder holds `topic.yaml` and the tab folders `slides/`, `reading/`, `exercises/`, `notebooks/`, `tests/` (each may be absent: git keeps no empty folder). The reader takes the path of one course folder and returns no absolute path, mode or instructor, so `courses/` read at `courses/` and at `instructors/<name>/courses/` gives equal results (A38).

| Tab folder | File | Becomes | Beside it |
| --- | --- | --- | --- |
| `slides/` | `*.md`, `*.markdown` | `slides_web` | nothing |
| `slides/` | `*.pdf` | `slides_pdf` | nothing |
| `reading/` | `*.md`, `*.markdown`, `*.html` | `reading_native` | nothing |
| `reading/` | `*.pdf` | `reading_pdf` | nothing |
| `notebooks/` | `*.ipynb` | `notebook` | a folder named as the notebook without `.ipynb`: each file in it is a data file, at its path inside that folder |
| `notebooks/` | `*.shiny.yaml`, holding `url` and nothing else | `shiny` | nothing |
| `exercises/` | `*.yaml` | `exercise` | nothing |
| `tests/` | `*.yaml` | `test` | a folder named as the test without `.yaml`: code files at `<question id>/<path>` |

Extensions are compared in lower case, and the kinds of uploaded file are those of `uploadFormats`, as in the upload route (`apps/server/src/http/routes/authoring.routes.ts:153-159`); `.htm` and `.yml` are not accepted. Topics are ordered by the `position` each `topic.yaml` states (§3), so the name of a topic folder is a path and carries no order, title or identity; resources by their order in `topic.yaml`, across tabs, which is `resources.position`. A name that starts with `.` is skipped everywhere (a `.gitkeep`, for one); one that starts with `_` is skipped in a course, topic or tab folder. Every other entry must be recognised: a file of a kind its folder does not take, a file that no entry of `topic.yaml` lists, a file beside a notebook or test that nothing uses, and a folder without `topic.yaml` are each an error that names the path and what the folder accepts, and nothing is converted while one stands. *Paths.* The reader refuses, with the path named: an absolute path and a path that climbs out of its folder; a symbolic link or junction whose target lies outside the folder being read (the course folder for the tree, the course's folder under `private/` for the overlay), so a link in `reading/` cannot bring in a file of `private/`; and two names in one folder, or an entry's `file` and the name on disk, that differ only in case, so a folder reads the same on Windows and on a host that tells case apart. A Markdown reading gets no local images, because the editor has no way to attach one (`AddReading.tsx:27-40`).

These are all the fields a folder states. The limits are those of the draft contracts (`packages/contracts/src/routes/drafts.ts:15`, `:98-105`). References are by id, so they hold when a folder or file is renamed and when topics change places; `parallax check --write-ids` has written an id before another topic names it. `topicPayload` in contracts turns both kinds of id into the stored values in one step, with the row ids of §4: `prerequisites` as an array of topic row ids, `completionRule` as `{ requires: [...] }` with `submitted:<resource row id>`. A prerequisite that is no topic's id, and a requirement that is no id of a resource of the same file, are errors. An invalid file is reported one line per problem, with file, field and line, and stops the command with exit code 1 before anything is written: `courses/reef-ecology/sampling/topic.yaml: resources[1].visibility: expected "visible" or "hidden" (line 14)`.

**4. Identity (K8, Q14).** Each topic and each resource has an `id` in its topic's `topic.yaml`. `parallax check --write-ids` is the one command that writes it, on the author's machine, when a topic or an entry is new. It reads the folder's structure as the reader's site entry does (layout, paths, both metadata files, every file listed once) and, when nothing is wrong there but ids that are missing, gives each topic and each entry without an `id` a fresh UUID. It writes ids and nothing else: entries and titles are the author's to write, existing ids, comments and order stay byte for byte, each file is replaced atomically after a check that it did not change meanwhile, and every field it set is printed. While another error stands (an unlisted file, an entry whose file is gone) it writes nothing in the course and prints the errors, so a renamed file whose `file:` was not corrected cannot become a new resource. A second run changes no file. `check`, `sync` and `build` write nothing into a course folder. The id belongs to the entry, so a rename of a file or of a topic folder, a new order, or moving a file with its entry to another topic keeps it. A missing id is an error that names file and field and the command to run. An id used twice in one course is an error that names both places and is never repaired.

*A changed id.* `check` accepts any other well-formed UUID: a folder does not show an id's history. Sync does see it. It stops, with exit 1 and no row changed, when in one run a resource it made is no longer listed and a new id stands at the file path that resource last recorded (the `path` of its provenance, §10); the message names the file and both ids and says to put the earlier id back. That is the case of an id removed and written again by `--write-ids`, and of a hand-edited id. Only with `--accept-new-ids` does sync go on: it creates the new resource, archives the earlier one and reports the earlier id, and putting the id back and syncing again restores it. Every other new id is created without a stop. A resource's type never changes: a different kind of file under an old id is refused, and the entry needs a new id.

Database ids follow by derivation; nothing is stored to map them. A course is the pair of owning account and course folder name: `courses.id = uuid5(0b6a98fa-33c2-51ab-9808-310d3f212845, "<owner user id>/<folder name>")`, with that fixed namespace, created through `createCourse`, which takes an id (`apps/server/src/db/identity.ts:54`). `topics.id = uuid5(<course id>, "topic:<id>")` and `resources.id = uuid5(<course id>, "resource:<id>")`. The same folder therefore reaches the same rows on every sync, and an interrupted sync continues where it stopped. A copied course folder (another name, or under another owner) reaches rows of its own although it carries the same ids. A renamed course folder, or another address in `instructor.yaml`, is a second course, and the first stays as it is. `createTopic` and `createResource` (`drafts.ts:213`, `:268`) gain an optional `id` argument, as `createCourse`, `createClass` and `publishRelease` have; no route passes it. A row with a version 5 id was made from a folder; the editor's rows have random ids (version 4). That is how sync tells its own rows from the editor's without stored state.

**5. YAML exercises and tests (K24, N5).** The file is parsed as one YAML 1.2 document with the core schema. No date is created (a timestamp stays a string), a quoted number or boolean stays a string, and a tag outside the core schema is never interpreted: nothing is constructed or run for it, and its node is read as the plain value it wraps. Anchors and aliases are expanded, within the parser's alias limit, so the value is the one the definition gives when written out. The result must be a JSON value: maps with string keys, lists, strings, finite numbers, booleans and null. Refused, each with file and line: a key that stands twice in one map, an alias that points into its own node (a cycle), a key that is not a string, a number that is not finite, and a second document. That value, which is what `JSON.parse` gives for the same definition written as JSON, goes unchanged to `exerciseV1` (`packages/contracts/src/exercise.ts:202`) or `testV1` (`test.ts:188`), and the schema's result is what is stored. One step comes before the schema: in a test, an entry of a code question's `files` that has no `content` gets it from `tests/<test>/<question id>/<path>`, as UTF-8 text or, with `encoding: base64`, as base64 of the bytes, so two questions may each have a `main.py`. Nothing else is added. A file is therefore accepted exactly when the schema accepts the same definition (A42). A rejected file names the field in the form above (`tests/quiz.yaml: questions[2].files[0].path: no file tests/quiz/q3/main.py`); an entry with both `content` and a file, and a file no entry names, are errors.

**6. Private overlay and hidden material (K14, K18, Q16).** The overlay is `private/` at the site root, as `docs/design/site.md` §3 already writes it and the template ignores it in git. It mirrors the path from the site root: `private/courses/<course>/<topic>/…` and `private/instructors/<name>/courses/<course>/<topic>/…`. A tree is declared public by `public: true` in `course.yaml`; the field has no default, so an undeclared tree stops every command. Answer-bearing is every file under a topic's `exercises/` or `tests/` folder: every exercise definition (each step has feedback), every test definition and every code file. In a public tree those files are read from the overlay at the same relative path, and any file under a public `exercises/` or `tests/` folder is an error that names it; `topic.yaml` in the public tree still lists the entry with its title. In a tree declared `public: false` they are read from the tree. A definition present in both places is an error that names both. A definition that is listed and found in neither place: `sync` stops with exit 1 and names the path it expected, and `check` at level 1 and above does the same. At level 0 `check` reads as the level 0 build reads, opens no definition, prints the note that definitions are not read at level 0 and exits 0: a checkout of a public repository has no `private/`, and a level 0 build needs none.

**7. The reader (P5-08).** `packages/cli/src/folder/read.ts` has three entries:

`manifest` is null while an error stands, so no caller can convert a refused tree. `CourseManifest` (schema `courseManifest` in contracts) is the operator's manifest, a plain JSON value: title, `public`, the topics in `position` order with their fields and ids, each resource with id, type, title, visibility, alternative, path, `overlay` and its source, and `files`, the distinct files with `sha256`, `size` and format. The source is `{ file }` for a PDF, reading or notebook (a notebook also lists its data files with their paths), `{ markdown }` for web slides, `{ url }` for Shiny, `{ definition }` for an exercise or test. `SiteManifest` (schema `siteManifest`, strict) is an allow-list for a site build: the same topics and, of the resources, the visible ones. A hidden resource is not in it. An exercise or test entry carries its id, title, topic, position and visibility, and the schema has no field for a definition, a source, a code file, an answer, feedback, a hint, a solution or a rubric. A folder states no release date (§10), so there is no resource to leave out by date. `readCourseForSite` takes no overlay and opens no file under `exercises/`, `tests/` or `private/`; it lists the public folders to refuse what lies there, as `check` does, and its `open` gives only the files its manifest lists. `sync`, and `check` at level 1 and above, call `readCourseForSync`; the level 0 build of P5-14, and `check` at level 0, call `readCourseForSite`; the catalogue calls `readCourseHeader`. So nothing these units hand to a site build or a catalogue holds a test definition or an exercise's answers, feedback, hints or solutions. The reader, the YAML forms and `check` import no database driver; of the server's sources `check` loads only the validator of §8, through `paths.ts`.

**10. `parallax sync` (K9, K10, K12, K32; Q12, Q13).** `parallax sync [<course> …] [--overwrite-editor] [--accept-new-ids]`, run by the operator in the site folder at level 1 or 2; `<course>` is a reference as in `classes[].course`, and without one every course is synced. For each course the command reads the folder and the overlay with `readCourseForSync`, stops with exit 1 on any error, and pipes one bundle to `src/scripts/sync-course.ts` in the server image. The bundle is the header as one line of JSON (`syncHeader`: the address in `instructor.yaml` and that file's path, the course folder name, the manifest, the options), then the bytes of `manifest.files` in order, each exactly the `size` its entry states, and nothing after. It is a stream: the command pipes each file from disk, and the script checks each file against its `size` and `sha256` while it goes into storage, so a course is never held in memory; a short, long or altered file ends the run with exit 2 before a draft is written. The definitions read from the overlay travel inside the manifest, already parsed. Everything travels on standard input: nothing is mounted, the container needs no access to the site folder, and no address is on a command line. The script reads `DATABASE_URL` and the storage settings of the service; there is no route, network caller or credential. In order:

1. *Owner.* The active account (`kind` user, not deactivated) with the address; if there is none, stop before any write, name `instructor.yaml` and say that the person signs in once first. Sync creates no account.
2. *Course.* The derived id; `resolveActorScope(db, owner, { kind: 'course', role: 'owner' }, id)` (`auth/scope.ts:177`) gives the `CourseScope`. If the course does not exist it is created with `createCourse`, only when the address is in the server's `INSTRUCTOR_EMAILS` (the first half of `mayCreateCourse`, `db/catalog.ts:223`); an archived course is refused. The title of an existing course is not changed: no service renames a course.
3. *Objects.* Each file passes the upload rules (`folder-input.ts`) while it streams into `storeCourseObject` (`storage/objects.ts:10`) with the route's content type; a data file is stored as `application/octet-stream` and its id read with `courseObjectId`, as the workspace-file route does (`authoring.routes.ts:202-210`).
4. *Plan.* The drafts are read, and a pure function compares them with the manifest: topics and resources to create, change, move, restore or archive, and refusals. The ids in `prerequisites` and `completionRule` become row ids here (`topicPayload`). No draft has changed yet.
5. *Refusals.* If the plan holds one (an editor's head, a new id at a recorded path, another kind of file under an old id), stop with exit 1 and name each file. Only content-addressed objects, and on a first sync the empty course, exist by then.
6. *Drafts.* `createTopic`, `updateTopic`, `createResource` and `updateResource` (`db/content/drafts.ts:213-406`) with the derived ids and the row's `expectedRevision`; a conflict (someone saved meanwhile, or another sync made the row) stops with exit 3. When its writes are done sync takes the fingerprint of all drafts: a hash over what a release snapshots, which is each live topic's and resource's id and fields and each head revision's id.
7. *Conversion.* For each head revision of a processed type (`isProcessed`, `reading-ingest.job.ts:72`) without a status, `enqueueIfUnprocessed` (`reading-ingest.job.ts:405`), the call the draft routes make (`drafts.routes.ts:34-44`); a failed head is queued again with `enqueueReadingIngest`, as the retry route does. `sendScopedJob` puts the owner as `actorId` and the course as scope into the payload (`jobs/scoped.ts:87-106`), and the worker resolves the scope again. Sync polls `listResourceJobStatus` (`db/jobs/derived.ts:230`) until every head is ready or failed.
8. *Publication.* `publishFolderRelease` (`db/content/sync.ts`) opens one transaction, takes the lock on the course row that publication takes (`releases.ts:272-277`), reads the drafts with their rows locked and compares their fingerprint with the one of step 6. A difference means that someone saved while sync waited: the run ends as a conflict, with no release and exit 3, and the next run plans against the changed drafts, where an editor's head on a listed resource is a refusal. A fingerprint equal to that of the newest release means there is nothing to publish. Otherwise it calls `publishRelease` (`releases.ts:267`) with the transaction in the handle's place, where its own transaction is a savepoint, as `setup.ts` does (`docs/design/site.md` §8), and with the server's `SHINY_ORIGINS` and `RUNNER_RUNTIMES`, as the route calls it (`releases.routes.ts:28-32`). Before the commit the fingerprint of the snapshot is compared once more, so a row that someone added after the read rolls the release back as the same conflict. The release, written in that transaction, is the record of what was published: its snapshot gives the fingerprint, so a second sync that runs at the same time finds its drafts equal to the newest release and publishes nothing more. Sync writes no audit event of its own; `course.create` and `release.publish`, which the functions it calls write, name the owning account as actor.

`revisionPayload` in contracts builds these values and is the one function sync and a level 0 build use; `topicPayload` does the same for a topic's fields. Title, visibility, order and alternative go through the same two services.

*Which side wins.* The folder declares, for a topic, its title, objective, estimated time, prerequisites, completion rule and position; for a resource, its topic, order, title, visibility, alternative and content. An absent optional field declares the value the editor's empty form gives. It declares no release date, class, assignment or grant, and sync never reads or writes one: a release date set through the API stays as it is. A topic or resource with a random id was made in the editor and is left as it is; the report counts them. A version 5 row that the folder no longer lists is archived with `updateTopic` or `updateResource`, never deleted: the next release leaves it out, and it can be restored. A revision made from a folder records `provenance = { source: 'folder', course, topic, resource, path, overlay, digest }`, where `digest` is `revisionHash` (`drafts.ts:105`) of its type, content, object keys and alternative with provenance null. A head revision came from the folder exactly when its provenance has that source and `digest` equals the digest of what the revision itself stores. `updateResource` carries provenance forward when the editor saves (`drafts.ts:372`; the web editor never sends the field), so after an editor's edit the stored content no longer matches `digest` and the head counts as the editor's, also on a resource that sync created; a later save that puts the folder's content back matches `digest` again and counts as the folder's. Sync refuses, unless `--overwrite-editor` is given, to replace such a head with different content, to archive a resource whose head is the editor's, and to archive a topic that holds an editor-made resource. With the flag the folder's content becomes the new head and the editor's revision stays in the history. If the editor's head already equals the folder's content, sync records a revision with the same content and the folder's provenance. When the content is unchanged sync sends no revision field, so a file that is only renamed or moved gets no revision: its title, topic and position are updated on the draft row, and the head's provenance keeps the earlier path. A sync of an unchanged folder changes no row and makes no release.

*Waiting, reports and what a stop leaves.* The wait ends when every head is ready or failed, when nothing has changed for 60 s while no head is running (no worker took the jobs), or after 30 minutes. In the last two cases sync does not publish: it prints the report of `validateDrafts`, which names each head still being processed, and exits 3; the queued jobs stay queued, and a worker that starts later finishes them. A failed conversion is not handled specially: publication is called and blocks with the existing `unprocessed_reading` or `unconverted_deck` message. Sync prints, per course, the counts (created, new revisions, moved, archived, unchanged, editor only), then `release <n> published` with its warnings, or `not published` with every error and warning of the `ValidationReport`: its code, its message and the folder path of its `resourceId`. Exit codes: 0 published or nothing to publish; 1 refused or blocked (folder errors, no account, editor heads, a new id at a recorded path, validation errors); 2 usage, level 0 or a malformed bundle; 3 not finished (time-out, no worker, queue or storage unavailable, a concurrent save, a draft that changed during the wait), safe to run again. A stop after step 6 leaves drafts written as an editor's save leaves them, queued jobs that a worker will finish, and no release; classes read releases only, so no student sees a change, and the next run publishes. Sync deletes no topic, resource, revision, release or object, changes no release and no column of a revision (`derived` is the job's), creates no class and moves no class to a release: adoption stays with the routes and `parallax apply`.

> ## Amendment: Conversion from a folder (P5-04, 2026-10-13)
>
> **Context.** N4 and N5 (spec §13) ask that a folder of files becomes the material the editor produces, and that converting it again keeps notes, highlights and attempts attached. The owner's answers Q12 to Q16 (plan §8) say where conversion runs, where metadata and ids live and which side wins. This amendment adds a second way to write drafts. It reverses nothing in the Decision: drafts stay mutable, revisions and releases stay immutable, publication validates and snapshots, and adoption compares releases by `resource_id`.
>
> **Folder.** A course folder holds `course.yaml` (the title, and whether the tree is public) and one folder per topic with `topic.yaml` and the five tab folders. `topic.yaml` holds what the editor records beside a file: the topic's position, title, objective, estimated time, prerequisites and completion rule, and each resource's file, title, visibility and accessible alternative. Content files carry no front matter, so the bytes stored are the file's bytes. An exercise or a test is a YAML file that is parsed to a JSON value and checked by `exerciseV1` or `testV1`; the schema's result is stored; a code file's content is read from the file beside the definition. No field, question kind or stored format is added.
>
> **Identity.** Each topic and each resource has an `id` in `topic.yaml`, a UUID that `parallax check --write-ids` writes once on the author's machine; no other command writes into a course folder. The id belongs to the entry, so a rename, a move to another topic or a new order keeps it, and prerequisites and completion requirements name ids. A course is identified by the account that owns its instructor folder and the name of the course folder. Database ids follow by derivation, and nothing is stored to map them: `courses.id` is the version 5 UUID of `<owner account id>/<folder name>` in the namespace `0b6a98fa-33c2-51ab-9808-310d3f212845`, and `topics.id` and `resources.id` are the version 5 UUIDs of `topic:<id>` and `resource:<id>` in the namespace of the course's id. The same folder reaches the same rows on every conversion, a copied course folder reaches rows of its own, and a row with a version 5 id is one a folder made (the editor's ids are random). A missing id stops conversion, and an id used twice in a course stops it and names both places. A new id at the path that a resource the folder no longer lists last recorded stops it too, with the file and both ids named, unless the operator passes `--accept-new-ids`; then, as for every other new id, a new resource is made and the earlier one is archived. A resource never changes its type.
>
> **Provenance.** A revision made from a folder records `provenance = { source: "folder", course, topic, resource, path, overlay, digest }`: the course folder's name, the two ids, the file's path from the course folder, whether it was read from the private overlay, and `digest`, the revision hash of its type, content, object keys and accessible alternative with provenance null. It holds no absolute path, host name or address. A head revision came from the folder exactly when its provenance has that source and its `digest` equals the digest of what the revision itself stores. A save in the editor carries the earlier provenance forward while it changes the content, so the two no longer match and the head counts as the editor's, also on a resource that conversion created; a save that puts the folder's content back matches again. A file that is only renamed or moved gets no revision, and its head keeps the earlier path.
>
> **Which side wins.** The folder wins for what it declares: for a topic its title, objective, estimated time, prerequisites, completion rule and position; for a resource its topic, order, title, visibility, accessible alternative and content. An absent optional field declares the value the editor's empty form gives. The folder declares no release date, class, assignment or grant, and conversion does not rename an existing course. Topics and resources made in the editor are left as they are. A topic or resource that a folder made and no longer lists is archived, never deleted. Conversion stops before it writes a draft when it would replace or archive a head revision that came from the editor, and names each file; `--overwrite-editor` lets it go on, and the editor's revision stays in the history. The editor does not change.
>
> **Conversion and publication.** `parallax sync` runs on the server's host, started by the operator, with no route, network caller or credential. It writes through the draft services under the owning account's `CourseScope` from `resolveActorScope`, queues the `reading.ingest` job, whose payload carries actor and scope, waits for it, and calls the publication above. Before it publishes it takes the course's lock and compares the drafts with what it wrote; a draft that changed meanwhile ends the run without a release. A validation error leaves the drafts written and no release, and the command prints the report with its codes and messages. Nothing is published when the drafts equal the newest release. Sync creates no account and no class, moves no class to a release and writes no audit event of its own.
>
> **Hidden material.** In a tree that `course.yaml` declares public, every file under a topic's `exercises/` or `tests/` folder is read from the private overlay `private/`, a directory outside the tree with the same layout. A file under such a folder of the public tree, a definition in both places and, at level 1 and above, a missing definition stop the check, the build and the conversion, which name the file. What a level 0 build receives holds no definition and no hidden resource.
>
> **Consequences.** No table or column is added, and P5-18 adds no migration. `createTopic` and `createResource` take an optional id that no route passes. `validate` moves unchanged to a module without database imports, so that the check and a level 0 build report with publication's codes and messages. A renamed course folder, or another address in `instructor.yaml`, is a different course. Each conversion that changes content adds revisions, as an editor's save does.
>
> **Alternatives considered.** *A table from folder ids to rows:* stored state that can disagree with the folder, and a migration, for what a derivation gives. *Ids from file paths:* a rename would detach every note. *Front matter:* the stored bytes would differ from an upload, and PDFs and notebooks cannot carry it. *Telling the editor's head by the provenance source alone:* the editor's save carries provenance forward. *Letting sync write ids:* the folder on the server would differ from the author's copy.

## Risks

- **P5-04 cannot split.** This plan, the design document and eleven entries are one pull request of about 572 changed lines; P5-03 came to more than its estimate. §12 says what the design document leaves to the landed plan if the count passes 600. Four more units, P5-08a, P5-09, P5-08 and P5-18, are estimated between 552 and 580 lines, and §12 names the part of each that splits off first.
- **Two rules exist twice.** The upload route's checks and the editor's `declareFiles` cannot be edited, so `courseFiles.ts` restates them. Tests hold each pair equal (P5-08a, P5-18), and a later change to one side fails a test and not a course. The test that compares with `declareFiles` sits in the contracts package and loads the editor's module, with everything that module imports, when it runs (§8); `pnpm check` of P5-08a on Windows shows that it loads there.
- **The validator is packed through a seam.** P5-17a's entry on `main` names the conversion entry only, and this run does not rewrite it. `packed-check.test.ts` of P5-08c fails if the validator is not in the packed copy, and P5-08c then adds the entry file itself.
- **The move of `validate` touches four core files.** It is a move with re-exports, and the nine integration files and four unit files named in step 4 guard it; if a body would have to change, the unit stops and is labelled `needs-human`.
- **Identity rests on three stateless rules:** derived ids, the UUID version as the mark of a folder-made row, and the digest in provenance. Each is small and tested by case in `folder-plan.test.ts` and A41, but a mistake in one detaches notes. A course is tied to the owner's account and the folder's name, so renaming the course folder or changing the address makes a second course; the first stays, and nothing is lost. The stop for a changed id compares the path the head's provenance holds, which after a rename without a change of content is the earlier path: a changed id at the new path is then created without a stop, and the report names the earlier id.
- **`validate` without a database is not the whole of publication.** Test rules that need the server's runtimes, conversions `check` did not run, the course's other drafts and a server whose settings differ from the configuration show only at sync or in a build; `check` says in its last line which checks it left out. Publication snapshots the whole course, so an editor's unpublished changes that were there before a sync are published with it, as publishing does today; only a save during the wait stops the run.
- **Waiting for the worker.** A busy worker can look like none, and sync then stops with exit 3 although nothing is wrong; running it again finishes the work. The bounds are constants in one module.
- **The bundle is a stream on standard input.** If `runInServer` of P5-23a takes text only, P5-18c passes the stream through the same injected runner with the arguments `compose.ts` exports; a large course is never held in memory.
- **Session 1a grows to six units**, two of which edit `drafts.ts`; the dependency P5-18b → P5-09a keeps them apart. In session 4 the entry of P5-24 (documentation, a simple unit this run does not rewrite) does not name P5-18c; the session should finish P5-18c first, which the short chain 23a → 18c allows.
- **Aliases in YAML** are expanded before the schema sees the value, so a definition can be larger than its file; the parser's alias limit bounds it. A merge key is not part of YAML 1.2: `<<` is read as an ordinary key, which the schemas treat as any unknown key.
