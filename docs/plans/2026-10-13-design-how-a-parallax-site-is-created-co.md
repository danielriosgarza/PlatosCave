# Plan

## Goal

Fix, for planning run R1 (owned by P5-03), how a Parallax site is created, configured, built, installed on one host and upgraded: the published pieces, the site folder, `parallax.config.ts`, the `parallax` command, the mechanism that compiles a site's `src/pages` with `apps/web`, both modes, setup from configuration, the one-host installation, the upgrade, the level 2 runner profile, and the release. The plan gives the ADR-0001 amendment text and, for P5-03, P5-06, P5-07, P5-17, P5-19, P5-22 and P5-23 and four added items, scope, files, scenario tests and a size of at most 600 changed lines. It builds on N1 to N3, N9 and the recorded answers Q1 to Q11 and Q27 (`docs/delivery/plan.md` §8) and decides nothing beyond them. Parallax as built does not change.

## Approach

**1. Shape.** A site is a folder with one dependency, `parallax-site`. The package carries the web application's sources; `parallax build` copies them into a git-ignored work tree in the site, adds one generated entry that hands the site's pages to a new mount function of `apps/web`, and runs the same Vite build that `pnpm build` runs today. At level 1 the published server image serves that build through the existing `STATIC_DIR` setting. Setup runs as a script inside the server image on the server's host. Existing files this run edits, and no others: `apps/web/src/main.tsx`, `apps/web/package.json`, `packages/contracts/src/index.ts` (one export line), `apps/server/src/db/migrate.ts`, `apps/server/src/version.ts` (one line), `infra/docker/server.Dockerfile` and `infra/docker/runner.Dockerfile` (both in P5-22 only), `.gitignore`, `vitest.config.ts`, the root `package.json`, `.github/workflows/image.yml`, `pnpm-lock.yaml`, `docs/adr/0002-authorization-and-class-isolation.md` (one sentence and its status line, in P5-19), and the documents of P5-03. No route file, screen, viewer, editor, review screen, contract, schema file or migration is among them, and the Playwright configuration is not changed.

**2. Published pieces and names (Q1).** One version number covers all of them. The names are fixed; the directory names below replace the working names.

| Piece | Published as | Directory | Holds |
| --- | --- | --- | --- |
| Command-line tool | npm `parallax-site`; the command inside a site is `parallax` | `packages/cli` | the tool, and, copied in at pack time, the sources of the web application (`apps/web`, `packages/ui`, `packages/contracts`) and of the conversion entry of P5-09 with its `*.worker.mjs` files |
| Scaffolder | npm `create-parallax-site`, run as `npm create parallax-site` | `packages/create-parallax-site` | the create command and the templates `instructor` and `school` |
| Server image | `ghcr.io/<owner>/parallax-server` on GHCR | `infra/docker/server.Dockerfile` | `apps/server`: API, relay, worker, migrations, operator scripts |
| Runner image | `ghcr.io/<owner>/parallax-runner` on GHCR | `infra/docker/runner.Dockerfile` | `apps/runner`, the runner service |

`<owner>` is the repository's GitHub owner. The manifest of `parallax-site` carries `ghcr.io/<owner>` in a field `parallax.registry`, which the release workflow stamps beside the version, and a site's tool reads the image names from there; the npm account is an owner input (plan §7). The sandbox runtime images that the runner starts are not published by this run: they stay with `scripts/runner-image.sh` and the digest allow-lists of `docs/design/runner.md`, and their references and digests are level 2 inputs of the operator (section 11). The `@parallax/*` workspace packages stay private. The published tool runs its TypeScript sources with `tsx`, as the server image does (ADR-0001, "Server execution"), so the renderers' worker threads, which already register `tsx` themselves (`apps/server/src/content/reading.worker.mjs`), run unchanged from the package. *Packing:* `packages/cli/scripts/vendor.ts` (run by `prepack`) copies the sources into `packages/cli/vendor/{web,ui,contracts,server,deploy}` without test files, rewrites every `@parallax/…` import specifier in the copies to a relative path, so the tree needs no workspace link, no alias and no loader hook, and follows the relative imports of `apps/server/src/content/convert.ts` to copy exactly the conversion closure. `vendor/deploy` holds `scripts/backup.sh` and `scripts/restore.sh`. Every third-party package the copies import is a dependency of `parallax-site` at the version the source manifest pins; `pg` and `drizzle-orm` are not among them. In the repository, where `vendor/` does not exist, `packages/cli/src/paths.ts` resolves the same roots from the workspace. `packages/cli/scripts/pack.ts <package> <version> <folder>` stages a package in a temporary folder, stamps the version there, and runs `prepack` and `npm pack`, so a test and the release workflow get stamped tarballs with no change to a tracked manifest.

**3. Site folder (N1).** It holds only the site's own files; Parallax arrives as the dependency.

```text
my-site/
  package.json           "parallax-site": "1.4.0" (exact): the one place that names the Parallax version
  .npmrc                 package-lock=false: the site keeps no lock file
  parallax.config.ts     mode, name, logo, level, sign-in, origins, instructors, classes
  tsconfig.json
  src/pages/index.tsx    the site's own pages, JSX only (section 6); styles in *.module.css beside them
  instructor.yaml        instructor mode: name and email of the one instructor
  courses/<course>/…     instructor mode; the layout inside a course folder is run R2's
  instructors/<name>/    school mode: instructor.yaml and courses/<course>/…, the same layout
  compose.yml  Caddyfile  compose.level2.yml  compose.runner.yml      the installation (sections 9, 11)
  .gitignore             node_modules/  dist/  .parallax/  .env  backups/  private/
```

Generated and git-ignored: `.env` (secrets), `.parallax/` (the work tree `app/`, the Vite cache, `site.env`, the backup overlay of section 10, and at level 2 `pg_hba.conf` and `runner/runner.env`), `dist/` (the compiled site) and `backups/`. `private/` is the private overlay of run R2 (the name `docs/design/course-folder.md` gives it wins). The site keeps no lock file: the template's `.npmrc` sets `package-lock=false`, so `npm install` writes none. No file of the site other than `package.json` names the version: the compose files take the image references from `.parallax/site.env`, which `parallax env` derives from the installed package. An upgrade therefore changes `package.json` and no other tracked file of the site (A37): the install and the rebuild replace only git-ignored files. The templates hold `.gitignore` and `.npmrc` as `_gitignore` and `_npmrc`, and the create command writes them under their real names, because npm does not deliver files of those two names in a published package.

**4. `parallax.config.ts` (K5).** The default export of the file, written with `defineConfig` from `parallax-site`, which only gives the editor the type.

```ts
import { defineConfig } from 'parallax-site';

export default defineConfig({
  mode: 'instructor',
  name: 'Statistics for Biologists',
  logo: { file: 'src/logo.png', alt: 'Statistics for Biologists' },
  level: 1,
  origins: { app: 'https://stats.example.org', content: 'https://content.stats.example.org' },
  signIn: { email: { from: 'Statistics <login@example.org>' } },
  classes: [
    { course: 'statistics', name: 'Spring 2027' },
    { course: 'statistics', name: 'Open course', open: true },
  ],
});
```

| Field | Rule | Used for |
| --- | --- | --- |
| `mode` | `'instructor'` or `'school'`, required | where instructor folders are looked for (section 7) |
| `name` | 1 to 80 characters, no control characters | given to the site's own pages only |
| `logo` | optional; `{ file, alt }`: a PNG, JPEG or WebP file inside the site folder, outside the course folders and the private overlay, and its alternative text (1 to 120 characters) | given to the site's own pages only |
| `level` | `0`, `1` or `2`, required | what each command does; moving between levels is a change of this value |
| `origins.app`, `origins.content` | two origins, `https` (or `http` on a loopback host); their host names must differ, the rule of `apps/server/src/config.ts:298` | level 1: `APP_ORIGIN`, `APP_HOST`, `CONTENT_ORIGIN`, `CONTENT_HOST`; level 0: the two outputs of run R3 |
| `origins.shiny` | optional list of origins, none the app or content origin | `SHINY_ORIGINS` (existing setting); run R3 at level 0 |
| `signIn` | `{ email?: { from } }`; at least one method at level 1 and above; unused at level 0. Run R4 adds `providers` in this object | `MAIL_TRANSPORT`, `MAIL_FROM`; the relay address with its password is `SMTP_URL` in `.env` |
| `instructors` | references to instructor folders, never addresses: in school mode the names of the folders under `instructors/`, required and unique; in instructor mode the one reference `'.'` (the site root), which is the default. The addresses are only in each folder's `instructor.yaml` | who has instructor access: `INSTRUCTOR_EMAILS`, taken from the listed folders' `instructor.yaml`; the accounts `apply` looks up |
| `classes[]` | `{ course, name, open, instructors }`: `course` is `<course>` in instructor mode and `<name>/<course>` in school mode; `name` 1 to 80 characters, unique within its course; `open` defaults to `false` (joined with an enrolment code), `true` means joined by the open join link; `instructors` is optional, references from the top-level list, default the folder that holds the course | `apply` (section 8) |
| `runner` | `{ host, databaseHost, runtimes }`: two addresses, and the sandbox runtimes with their images and digests in the form of the existing `RUNNER_RUNTIMES` setting; required at level 2, unused below | section 11 |

*Validation.* The schema `siteConfig` is a strict zod object in `packages/contracts/src/site.ts`, with `instructorMeta` (`{ name, email }`, strict) and `siteCatalogue` beside it. Every command first loads the file with `tsImport` from `tsx/esm/api`, parses the default export and, on failure, prints one line per issue (`parallax.config.ts: classes[1].course: no folder courses/genetics`) and exits 1 before it writes anything. The loader (`packages/cli/src/site/load.ts`) adds the checks that need the folder: the logo exists inside the site and outside the course folders and the private overlay; the mode's folders exist; every listed instructor folder exists and has a valid `instructor.yaml`, every instructor folder on disk is listed, and no two carry one address; every `classes[].course` is a folder; every class instructor is in the list. An unknown key is an error that names the key. Loading and building import no database driver and run with `DATABASE_URL` unset.

**5. Commands (K6).** `parallax <command>` runs in a site folder. `packages/cli/src/main.ts` discovers one module per command in `src/commands/<name>.ts`, as the server discovers route modules, so a later unit adds a file and edits no shared list.

| Command | Does | Unit |
| --- | --- | --- |
| `npm create parallax-site <folder> [-- --template instructor\|school]` | creates the folder from a template (default `instructor`), writes `package.json` with the scaffolder's own version as the exact version of `parallax-site`, asks nothing, uses no network, runs no install, refuses a folder that is not empty | P5-17 |
| `parallax dev` | validates; Vite development server for the compiled site, pages reload on save; `/api` is proxied to `http://127.0.0.1:3000` with the browser's `Host`, as `apps/web/vite.config.ts` does. At level 0 it stops, as `build` does, until run R3's units provide the open site | P5-07 |
| `parallax build` | validates; level 1 and 2: compiles `src/pages` and the web application into `dist/`; level 0: calls the build of P5-14, and until that unit merges stops with a message, so nothing can serve a level 0 site before P5-15 | P5-07 |
| `parallax env` | level 1 and 2: creates or completes `.env`, never changing a value that is there; rewrites `.parallax/site.env` from the configuration and the installed version | P5-23a |
| `parallax start` | `env`, `build`, then `docker compose pull` and `up -d --wait`; `migrate` runs before the services. Safe to run again: no generated secret changes and the running services stay up | P5-23a |
| `parallax upgrade` | after the version in `package.json` was changed and installed: `env`, `build` and `docker compose pull` while the old version still serves; then it stops `server` and `worker`, takes a backup (section 10) and ends there if the backup fails; then `up -d --wait`, in which `migrate` runs before the services | P5-23 |
| `parallax apply` | setup from the configuration (section 8) | P5-23a (command), P5-19 (server side) |

A command that needs a server (`env`, `start`, `upgrade`, `apply`) stops at level 0 and says that level 0 has no server. *A first installation, in order:* `npm create parallax-site`, `npm install`, the configuration, `parallax start`, each listed instructor signs in once in the browser, `parallax sync` (P5-18), `parallax apply`. *Where other runs attach:* `check` (P5-08) and `sync` (P5-18) are files `src/commands/check.ts` and `src/commands/sync.ts`; `sync` runs its server script with `runInServer` of `src/host/compose.ts`, as `apply` does. The level 0 build (P5-14) is `src/open/`, called from the level switch in `src/commands/build.ts`. Run R4 adds provider variables in `src/host/siteEnv.ts`.

**6. Site pages (N3; Q8 to Q11).**

*a. `apps/web` as a dependency (P5-06).* New `apps/web/src/app.tsx` exports `createApp(site?)` and `mount(root, site?)`; `main.tsx` shrinks to a call of `mount` with no argument, and the two style imports and the router's `Register` declaration move to `app.tsx` unchanged. `site` is `{ pages: { path, load }[], props }`. With no pages `createApp` passes the generated `routeTree` to `createRouter` untouched, so the application is exactly today's and `/` keeps its redirect to `/courses` or `/signin`. With pages it adds one code-based route per page beside the generated children: `createRoute({ getParentRoute: () => routeTree, path, component: lazyRouteComponent(load) })`, then `routeTree.addChildren([...kept, ...added])`. `kept` is `routeTree.children` as generated, read once when `app.tsx` loads, so a second `createApp` (a hot reload, a test) does not pile pages up; the generated index route (compared by identity with the `Route` exported by `routes/index.tsx`) is left out of it only when a page has the path `/`. No route file and not `routeTree.gen.ts` is edited. New `apps/web/src/sitePages.tsx` holds what both shells share: the page types, `siteRoutes(parent, site)`, which run R3's level 0 shell can call with its own root, a `Link` for pages, and the pure address rules `pageAddress(file)`, `normalise(address)` and `screenAt(address, patterns)`. `normalise` decodes percent-escapes, lower-cases and drops a trailing slash, so `/courses/` and `/%63ourses` are both `/courses`. `createApp` throws when a page other than `/` is, after `normalise`, at a screen's address, so a caller that skips the build check still cannot replace a screen. `apps/web/package.json` gains `exports` for `./app` and `./pages`; nothing imports the package today.

*b. From files to addresses.* `src/pages/index.tsx` is `/`, `about.tsx` is `/about`, `team/index.tsx` is `/team`. A page is a `.tsx` or `.jsx` file whose default export is a component; a segment is lower-case letters, digits and hyphens, and a file with any other segment stops the build; names starting with `_` are helpers, not pages. Two files with one address (`about.tsx` and `about/index.tsx`) stop the build, which names both. A `.md` or `.mdx` file under `src/pages` stops the build: pages are JSX only (Q11).

*c. Added pages only (Q8, A39).* `packages/cli/src/site/pages.ts` reads the application's addresses from the keys of `FileRoutesByTo` in `routeTree.gen.ts`, the generated list of every address a route answers, and fails loudly if that block is missing. The build stops before Vite starts when a page's address, after `normalise`, matches one of them (`$name` matches any segment), or lies under `/api`, `/assets` or `/content`, which the server answers itself (`apps/server/src/http/static.ts`, `http/content.ts`). So `courses.tsx` and `courses/index.tsx` are both refused. The message names both: `src/pages/classes/demo/review.tsx would be at /classes/demo/review, the address of the Parallax screen /classes/$classId/review. A site adds pages and cannot replace a Parallax screen: move or rename the page.` `/` is the one exception, because it has no page today.

*d. One compiled site.* `packages/cli/src/build/web.ts` (i) copies the `web`, `ui` and `contracts` sources into `.parallax/app/`, skipped when the copy's version marker matches; (ii) writes there `web/src/site-pages.gen.ts` (one `{ path, load: () => import('<relative path to the page>') }` per page, and the page props) and `web/src/site-entry.gen.tsx` (`mount(root, { pages, props })`), and a copy of `index.html` whose only change is the script address; (iii) runs Vite with `configFile: false`, root `.parallax/app/web`, `publicDir: false`, `cacheDir` `.parallax/vite`, `outDir` the site's `dist/`, and the plugins of `apps/web/vite.config.ts` in the same order: `tanstackRouter({ target: 'react', autoCodeSplitting: true })`, then `react()`. The router plugin regenerates an identical `routeTree.gen.ts` inside the copy and splits the routes as today; this is why the build runs on a copy outside `node_modules`: the code splitter only knows route files the generator has listed (`router-code-splitter-plugin.js` reads `routesByFile`), and the generator writes files. Nothing is written under `node_modules` or into the repository's `apps/web`. One small Vite plugin resolves bare imports: from a file of the work tree as if it sat at its original location, and `react`, `react/jsx-runtime` and `parallax-site/pages` from a site page to the package's own copies, with `resolve.dedupe` for `react`, `react-dom`, `@tanstack/react-router` and `@tanstack/react-query`. The same plugin stops the build when the logo or a file that `src/` imports resolves into a course folder (`courses/`, `instructors/<name>/courses/`) or the private overlay, and names the importing file and the path. The build therefore does not depend on how a package manager lays out `node_modules`.

*e. Serving at level 1.* `dist/` has the form the server already serves: `index.html` and `assets/`. `compose.yml` mounts it read-only at `/site` and sets `STATIC_DIR=/site` (`apps/server/src/config.ts:69`), which replaces the image's default. No server code changes and no route is added. Pages run under the app origin's existing headers (`script-src 'self'`).

*f. Page data (Q9).* A page receives props fixed at build time and nothing else: `{ site: { name, logo, entry }, catalogue }`. `logo` is absent or `{ src, alt }`, the address of the compiled file and its alternative text. `entry` is the address of the Parallax interface for the level (`/courses` at level 1 and above; the level 0 shell gives its own), so a page links to it without knowing the level. `catalogue` is `{ instructors: [{ slug, name, courses: [{ slug, title }] }] }`: display names and course titles from the folder, each with its folder's name. Its strict schema has no field for an address, a topic, a resource or a definition, and `packages/cli/src/site/folders.ts` (P5-07) reads directory names and `instructor.yaml` only; it opens no file inside a course folder. The title is the course folder's name until run R2 names a metadata source. No runtime API for pages is offered or supported, and no `/api/*` route is added.

*g. Look (Q10).* `mount` takes no theme, style or component. Site pages render inside the unchanged root layout (`routes/__root.tsx`), below Parallax's global bar; the site's name and logo exist only in the props of the site's pages, and no Parallax screen reads them. The document title stays `Parallax`; a page module may export `title`, which the page's route sets while the page is shown and restores when it is left. The build stops when a stylesheet imported from `src/` is not a `*.module.css`, declares a `--pc-*` property, uses `:global`, or has a selector without a class, so a site stylesheet cannot reach a Parallax screen or a token.

**7. Both modes, ownership, catalogue (N2; Q4 to Q6).** The mode is the value `mode`. An instructor folder is a folder with `instructor.yaml` and `courses/`: the site root in instructor mode, each `instructors/<name>/` in school mode. `courses/` has the same layout in both, so it moves between the modes unchanged. `instructor.yaml` holds `name` and `email`; the address decides ownership: the account with that verified address owns the courses under that folder, in both modes. Accounts stay keyed by a verified address, and setup never creates one (section 8). The configuration names the instructor folders that have instructor access (`instructors`); a folder that is not listed, or a listed folder that is missing, stops every command with a message that names the folder. There is no role, no instance administrator and no new permission: ownership is the existing course owner grant, instructor access is the existing `INSTRUCTOR_EMAILS` list and the existing memberships. School mode is one installation with several instructors. A school site's catalogue page is the template's front page: it lists the instructors, then each one's courses, from the build-time catalogue; `/courses` and its screen do not change.

**8. Setup from configuration (Q7; A51).** `parallax apply` runs on the server's host. The command builds one JSON document from the configuration and the instructor folders (schema `siteSetup` in `packages/contracts/src/site.ts`; each instructor carries the path of its `instructor.yaml`, for messages) and pipes it to `docker compose run --rm -T server node_modules/.bin/tsx src/scripts/apply-site.ts`, as the managed connector's script is run today. The script reads `DATABASE_URL` from the service's environment on the internal network: no HTTP call, no route, no network caller and no new credential. Its caller is the operator, who has shell access to that host. The script composes functions of `apps/server/src/db/` only:

| Step | How | Second run |
| --- | --- | --- |
| Instructor access | for each listed instructor folder, the active account (kind `user`, not deactivated) with the folder's address, found by the new `findInstructorAccount` in `apps/server/src/db/setup.ts`. An account row exists only after a verified sign-in (`userForVerifiedEmail`, `db/auth/accounts.ts`), and `apply` never creates one. If an account is missing, setup stops before any write, names each `instructor.yaml` whose address has no account and says that the person signs in once first. `parallax env` writes the same addresses as `INSTRUCTOR_EMAILS` | account exists |
| Course | the course a folder syncs to, through the lookup P5-18 provides; a folder not yet synced is reported as pending | — |
| Class | `CourseScope` from `resolveActorScope(db, ownerId, { kind: 'course', role: 'owner' }, courseId)`; `findClassByName` (new, `forCourse`) returns the course's classes of that name: one is the class; with none the existing `createClass` makes it; with two or more, made through the existing routes, the item is refused and their ids are named | class exists |
| Class instructors | `ClassManagerScope` from `resolveActorScope` with the grant `manage_members`; new `ensureInstructor(db, scope, userId)` gives the class instructor membership and course draft editing, as `acceptInstructorInvite` does (`db/invites.ts:228`) | membership exists |
| Access | `open` is set through the data-access function of P5-10 when it differs; if `listMembers` shows no open enrolment invitation, the existing `issueInvite` issues one. The code, or for an open class the join link of P5-11, is printed once and written nowhere | invitation exists; not shown again |
| Adopted release | for a class with no release: the course's newest release (new `latestRelease`, `forCourse`), adopted with the existing `adoptRelease` under the `ClassScope` of the class's first instructor | class has a release |
| Audit | one event of setup's own for each class it changes (`recordSetup`, below) | nothing changed, no event |

Every scoped table is reached through `forCourse` or `forClass` with a scope from `resolveActorScope`; `users` and `courses` are not scoped tables. The account check stops the whole run; after it each class is one transaction; a refused item is reported with its cause and the exit code is 1; the others still run. Setup needs no stored state: a class is found by course and name, access by the open invitation, instructors by membership, adoption by `classes.release_id`. Run R1 therefore asks P5-18 for no schema, and P5-19 adds no migration. The existing setup routes stay. A class renamed in the configuration is a new class: the earlier one stays as it is, and `apply` never renames, archives or deletes. *Enrolment codes.* When `apply` has ended, the plain code exists only in what the operator's terminal showed; the database holds its hash, and no template, fixture or file of the site holds a code. If it is lost, an instructor of the class issues a new code in the web application, through the existing invitation route.

*Recent sign-in and the audit trail.* The routes that issue an invitation or change a grant call `scope.requireRecentAuth()` (ADR-0002, spec §3). `apply` has no session: the operator, on the server's host, makes these changes for the owning account through the data-access functions, under scopes from `resolveActorScope`, whose `requireRecentAuth()` still always throws; no route loses its call. P5-19 records this exception in ADR-0002, beside the sentence on sensitive membership changes, names it in that ADR's status line, and adds this sentence:

> `parallax apply` (P5-19) is the one caller that makes these changes without a session: run by the operator on the server's host, it issues enrolment invitations and gives instructors their class membership and course editing for the owning account, through the data-access functions under scopes from `resolveActorScope`, and it appends one `setup.apply` audit event for each class it changes. The routes keep `requireRecentAuth()`, which always throws on such a scope.

The events the existing functions write name the owning account as actor, as they would from that person's own session. So that the trail shows that setup made a change, `recordSetup` appends, in the class's transaction, one event with the action `setup.apply`, no actor (a system action), the class as scope and target, and in `after` the account it acted for and the names of the changes. No route writes that action, and it needs no migration: `action` is free text and `after` is JSON.

**9. One-host installation (Q2; K20 to K22).** `compose.yml` in the template, started by `parallax start`.

| Service | Runs | Networks | Notes |
| --- | --- | --- | --- |
| `postgres` | `postgres:16.15`, profile `bundled` | `backend` (internal) | volume; no published port. `parallax env` leaves the profile off when the operator put a `DATABASE_URL` of an existing PostgreSQL 16 in `.env` |
| `migrate` | server image, `tsx src/db/migrate.ts`, once | `backend` | waits for `postgres` when it is bundled (`required: false`); the others wait for `service_completed_successfully` |
| `server` | server image, `tsx src/main.ts relay`: exactly one process, which serves every path (`docs/operations.md` Routing) | `backend`, `egress`, `edge` | `./dist` read-only at `/site`; volume `storage`; `STORAGE_DRIVER=fs`; the readiness probe of `compose.prod.yml` |
| `worker` | server image, `tsx src/main.ts worker` | `backend`, `egress` | the same `storage` volume |
| `caddy` | a pinned `caddy` image | `edge` | ports 80 and 443; `Caddyfile`; volume for certificates |

There is no runner service, no Docker socket and no object store. `Caddyfile` has two site blocks, `{$APP_HOST}` and `{$CONTENT_HOST}`, each `reverse_proxy server:3000`: Caddy obtains a certificate for each name, upgrades WebSockets and forwards `Host` unchanged, which is how the one server tells the two origins apart (ADR-0002). The `edge` network has a fixed subnet and Caddy a fixed address there, and `TRUST_PROXY` is that address. *Secrets:* `parallax env` generates `POSTGRES_PASSWORD`, `SESSION_SECRET`, `CONTENT_TOKEN_SECRET` and `READY_PROBE_TOKEN` (and `RUNNER_DB_PASSWORD` at level 2) with `crypto.randomBytes` on the operator's machine into `.env` (mode 0600), which the template's `.gitignore` lists. The compose files name each secret as `${VAR:?}` and hold no literal value. Everything that is not a secret (`APP_HOST`, `CONTENT_HOST`, the two origins, `MAIL_FROM`, `INSTRUCTOR_EMAILS`, `SHINY_ORIGINS`, the image references, the compose profile) is derived into `.parallax/site.env`, which the services read as `env_file`, so a later version can add a setting without a change to the site's compose file. The operator types the two host names once, as `origins` in `parallax.config.ts`, and the sign-in settings: `signIn` in the same file and `SMTP_URL` in `.env`; `start` stops early when `signIn.email` is set and `SMTP_URL` is empty. `infra/compose.prod.yml` and its test stay as they are.

**10. Upgrade (Q3; A52).** Changing the version is the upgrade: the operator edits the version of `parallax-site` in `package.json`, runs `npm install`, then `parallax upgrade`. The command first runs `env`, `build` and `docker compose pull` while the old version still serves, so a failure there interrupts nothing. It then stops the services that write (`docker compose stop server worker`), takes a backup into `backups/<UTC time>`, and only then runs `up -d --wait`, in which `migrate` runs before the new services. A failed backup starts no migration: the command ends, names the stage and gives the command that starts the old services again (`docker compose start server worker`). A failed migration leaves `server` and `worker` stopped, and the message names the backup. *Where the backup runs:* the existing `scripts/backup.sh`, carried in the package, runs in a one-shot container of `postgres:16.15`, the bundled database's image, which has `pg_dump` 16, bash and the GNU tools the script needs. `packages/cli/src/host/backup.ts` writes `.parallax/compose.backup.yml` with the one service `backup` and runs `docker compose -f compose.yml -f .parallax/compose.backup.yml run --rm --no-deps backup`, so the site's `compose.yml` keeps its five services. The container joins `backend`, where bundled PostgreSQL answers although it publishes no port, and `egress` for an existing PostgreSQL; it gets the same `DATABASE_URL` as `server`, the `storage` volume read-only as `STORAGE_DIR`, `PG_BIN` set to the image's PostgreSQL 16 directory, the script read-only, and `backups/` as its target. `apps/server/src/db/migrate.ts` gains `assertNotNewer`: it compares the newest `created_at` in `drizzle.__drizzle_migrations` with the newest `when` of the package's `drizzle/meta/_journal.json` and, when the database is newer, exits non-zero with a message that names both dates and says what to do. Without it drizzle's migrator applies nothing and an older server starts on a newer schema. Migrations only move forward; rollback is installing the earlier version and restoring the backup taken before the upgrade with the shipped `restore.sh` (`docs/backup-restore.md`). At level 0 an upgrade is the version change, `npm install` and `parallax build`.

**11. Level 2 runner profile (N9; Q27).** Level 1 needs no runner. Level 2 adds a runner on a separate host that the operator controls; the template has no profile that puts a runner on the site's host, and ADR-0004 and the sandbox policy of `apps/runner` are not changed. Level 2 adds three inputs, all typed in the `runner` field of `parallax.config.ts`: `host` (the runner host's address), `databaseHost` (the site host's address on the private network) and `runtimes`; a runtime without a digest is refused. `compose.runner.yml` is copied to the runner host with `.parallax/runner/runner.env`. It has one service, `runner`, with the hardening of `compose.prod.yml` (`cap_drop`, `no-new-privileges`, the socket's group, `RUNNER_PULL=never`, `RUNNER_DOCKER_RUNTIME` default `runsc`, the 80 s stop grace) and exactly the variables the runner reads. `runner.env` holds `RUNNER_DATABASE_URL` for the role `parallax_runner`, `RUNNER_IMAGES` derived from `runner.runtimes`, and no application secret; `parallax env` prints the pull commands for the runner host, where nothing is pulled at run time. *How the runner host reaches PostgreSQL:* directly on port 5432, over a private network between the two hosts (a provider's private network or a WireGuard link the operator sets up). Parallax does not encrypt this connection; it relies on that network. On the site host, `parallax start` at level 2 adds `compose.level2.yml`, which publishes PostgreSQL only on `runner.databaseHost` and starts it with `hba_file` set to the generated `.parallax/pg_hba.conf`. That file admits the application role only from the `backend` subnet and `parallax_runner` only from `runner.host/32`, only to the application database, with `scram-sha-256`; nothing else matches. `start` then sets the role's login, its password (the generated `RUNNER_DB_PASSWORD`) and its connection limit with one `ALTER ROLE` sent to `psql` on standard input, and `site.env` carries `RUNNER_RUNTIMES` from `runner.runtimes`. With an existing PostgreSQL the operator's database administrator applies the same rule and sets the password, and `RUNNER_DATABASE_URL` is typed into `runner.env`. The existing role keeps its grants: schema `pgboss_exec` only (`scripts/runner-role.sql`).

**12. Release (Q1; K3).** `.github/workflows/package-release.yml` follows `connector-release.yml`. Triggers: a tag `parallax-v<version>`; a pull request that changes the workflow, the two manifests, `packages/cli/scripts/**` or `infra/docker/**`; `workflow_dispatch` with `dry_run` true by default. Workflow permissions are `contents: read`. Job `build` holds no secret. It takes the version and the `publish` flag from `packages/cli/scripts/release.ts`, which states the connector workflow's rule as a tested function (the tag's version, or `0.0.0-dryrun.<sha>` and `publish=false`; a manual run stays a dry run unless `dry_run` is off and the ref is a tag). It stamps the version and the image namespace, runs the pack check, packs both packages with `pack.ts`, runs the installed-package check (step 8), builds the two images without pushing, and uploads the two tarballs as the run's artifact. Job `publish` runs only when `publish` is true, which a pull request never is. It alone has `packages: write` and alone reads `secrets.NPM_TOKEN`, in the one step that publishes; GHCR is reached with `secrets.GITHUB_TOKEN`. It pushes the two images, built from the tagged revision, then downloads the artifact and publishes those tarballs unchanged, `parallax-site` and then `create-parallax-site`, as `connector-release.yml` publishes the files its build job checked. It uploads a release manifest (the tarballs' checksums, the images' digests, the source revision) as an artifact of the run. No session pushes a tag; the first release tag is the owner's.

> ## Amendment: Distribution (P5-03, 2026-10-13)
>
> **Context.** Until Phase 5 Parallax could only be run from a copy of this repository: every workspace package is private and `infra/compose.prod.yml` builds its images from the source tree. N1 and N3 (spec §13) ask for a site folder that holds only its own files and compiles its own JSX pages against Parallax, and N9 for a runner on the operator's side. The owner's answer Q1 (plan §8) fixes the form of delivery.
>
> **Published pieces.** A release is two npm packages and two container images on the GitHub Container Registry (GHCR), under one version number. `parallax-site` (`packages/cli`, command `parallax`) is the command-line tool; it carries the sources of the web application (`apps/web`, `packages/ui`, `packages/contracts`) and of the conversion entry (`apps/server/src/content`), copied in at pack time with their `@parallax/…` imports rewritten to relative paths. `create-parallax-site` (`packages/create-parallax-site`, run as `npm create parallax-site`) is the scaffolder with the templates `instructor` and `school`. `ghcr.io/<owner>/parallax-server` is `apps/server`, and `ghcr.io/<owner>/parallax-runner` is `apps/runner`, the runner service. The sandbox runtime images that the runner starts are not part of a release: they stay with `scripts/runner-image.sh` and the digest allow-lists. The `@parallax/*` workspace packages are not published.
>
> **Execution.** The published tool runs its TypeScript sources with `tsx`, as the server image does; there is no bundling step. A site's build compiles the web application with Vite from the sources the package carries, in a work tree inside the site, with the plugins of `apps/web/vite.config.ts`. The server image serves the result through `STATIC_DIR`.
>
> **Versioning.** One semantic version for all pieces, set by the release tag; manifests in the repository carry `0.0.0`. A site names the version once, as the exact version of `parallax-site` in its `package.json`, and keeps no lock file; the tool starts the images tagged with that same version. Migrations only move forward: `migrate` runs before the services and stops when the database holds a migration newer than the package's newest. The upgrade command first stops the services that write and takes a backup; rollback is restoring that backup and installing the earlier version. The connector keeps its own version and workflow.
>
> **Release.** `.github/workflows/package-release.yml`, modelled on `connector-release.yml`. A tag `parallax-v<version>` on `main` publishes. A pull request that changes the workflow or what it packs, and `workflow_dispatch` with `dry_run` (the default), build, pack and check everything and publish nothing. Building and publishing are separate jobs; only the publishing job may write packages and read the npm token, from repository secrets, and it publishes the tarballs that the build job packed and checked, unchanged. Images are pushed first, then `parallax-site`, then `create-parallax-site`. No session pushes a tag; the first release tag is the owner's.
>
> **Consequences.** `infra/compose.prod.yml` stays the from-source deployment. `tsx` and Vite become run-time dependencies of `parallax-site`. Its third-party versions are the pins of this ADR, and a pack check fails when they differ from the source manifests. The site's build, not Parallax's, compiles the web application, so a pull request that changes `apps/web/vite.config.ts` must keep the tool's build configuration in step; a test compares the two.
>
> **Alternatives considered.** *Images only:* N3 needs an npm dependency to compile pages. *Publishing each `@parallax/*` package:* more names and versions to keep in step, for no consumer. *A prebuilt web library:* Vite's library mode inlines assets, which the app origin's `script-src 'self'` forbids for the PDF worker, and a second bundling pass breaks the first pass's chunk and style references. *Bundling the tool to JavaScript:* a build step the server does not have, while the renderers already load TypeScript through `tsx` in worker threads.

## Risks

- **The site build is the least proven part.** It compiles sources copied out of an installed package, with imports resolved by a plugin. Nothing here was run. The guards are the A37 test, which builds in a folder outside the repository where no workspace resolution can help, the A37 end-to-end test of P5-17, which installs the packed tool and builds with it, the installed-package check of P5-22, and the unmodified e2e suite for the application without a site. If the router plugin misbehaves on the copy, the fallback is `enableRouteGeneration: false`, which loses route splitting and nothing else.
- **Sizes.** P5-07, P5-17 and P5-19 carry the largest estimates of the table in section 14, 560 to 570 lines. A unit that passes 600 is split by the rule; the first candidates are `site/folders.ts` with its test (P5-07), the end-to-end test (P5-17) and the level 2 files of `siteEnv.ts` (P5-23a). Sessions `1a` and `2a` add one trigger each.
- **Setup waits for a first sign-in.** `apply` stops until every listed instructor has signed in once, so a first installation has a step the operator cannot do alone. A mistyped address in `instructor.yaml` gives no one the courses: setup names the file and stops.
- **No lock file.** The site does not record the versions of transitive dependencies; `parallax-site` pins its direct dependencies exactly, which fixes those only.
- **The A37 end-to-end test needs the npm registry.** It is the only test that does, and it adds an install to the `e2e` job.
- **The runner link is not encrypted by Parallax.** It relies on a private network and on `pg_hba` by address; the role reaches `pgboss_exec` only. A site without a private network needs a WireGuard link, which the operator sets up.
- **Sandbox runtime images are not published.** Until the owner answers the question below, a level 2 operator builds them with `scripts/runner-image.sh` from a copy of the repository.
- **Seams with later runs.** `apply` needs P5-18 to give the course of a folder; the catalogue's titles are folder names until run R2 names a source; the overlay's directory name is R2's. Each is written into `docs/design/site.md` for those runs to read. If R2 offers no course lookup, P5-19 cannot finish and is labelled `needs-human`.
- **Site pages sit under Parallax's global bar,** and with a front page the bar's "Parallax" link opens the front page instead of redirecting. This follows from `/` being free (Q8).
- **The stylesheet rule is a guard, not a boundary.** Site JSX is the owner's trusted code (N3) and could inject styles by hand; that is outside what a site is offered.
- **Fixed subnets** for `edge` and `backend` can collide with networks already on a host; both are one line in `compose.yml`. Caddy's certificates need public DNS for both names and ports 80 and 443.
- **Docker-only feedback is slow.** The compose start runs in CI only; the logic around it (environment files, compose structure, the order of the backup, the migrate guard) is tested in `pnpm check` and `pnpm test:integration`.
- **A later version may add a screen at an address a site already uses.** That site's build then stops with the A39 message and the owner renames the page; it is the Q8 rule at work, and the one case where a new version asks for an edit in the site.
