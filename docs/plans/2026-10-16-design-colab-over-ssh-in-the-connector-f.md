## Approach

The design follows Q26 exactly and plugs Colab into the existing SSH code as a different first hop. It adds no second SSH stack and no new protocol surface beyond one target shape.

- **D1 One fixed command, built in.** The `colab` target is reached by running `colab ssh --proxy-mode`. The program is `colab`, resolved with `exec.LookPath` on the `PATH` of the connector's own process each time it starts; a match through a relative `PATH` entry counts as missing. It takes exactly the two arguments `ssh` and `--proxy-mode` and starts with `exec.Cmd`, never a shell. The argument list is a constant in `connector/internal/sshtarget/colab.go`. No link message, configuration file or flag can add to it or name another program. No value from a message reaches the program, whether in argv, in its environment or on its stdin before the SSH bytes. Its environment is an allow-list (`colabEnv`) copied from the connector's own environment and never includes `SSH_AUTH_SOCK` or `PARALLAX_*`. Its working directory is the home directory. It runs in its own session and process group with no controlling terminal, and on Linux with `Pdeathsig`. Its stderr is drained into a bounded 4 KiB buffer, passed through `redact.Redact` and `safetext.Sanitize`, and discarded: no byte of it is logged, shown or sent to Parallax. There is no general `ProxyCommand`. The other two Q26 ideas are not adopted: a tunnel the person opens to a loopback target, and a connector inside the runtime.
- **D2 Transport = a different first hop.** Today `dialHop` (`connector/internal/sshtarget/dial.go`) dials the first hop through `netscope.Dialer` and reads the banner, then `hop()` (`stages.go`) runs `ssh.NewClientConn` over that `net.Conn`. For a `colab` target, `route()` returns one hop (`target`) flagged as reached through the program. `dialHop` then starts the program and returns its stdout and stdin wrapped as one `net.Conn` (`proxyConn`). Everything after that is unchanged code:
  - `readBanner`, key exchange, `hostCheck`/`Decide` (`hostkey.go`) and `hopAuth` (`auth.go`);
  - the workspace check, the forwarding check (`direct-tcpip` to `127.0.0.1`), `Remote.Test`/`Open`/`park`/`take` (`remote.go`), `Reconnect`/`watch`/`lost` (`reconnect.go`) and `Stop`/`SweepOrphan` (`stop.go`);
  - the tunnel `tunnelDial` to the session's fixed `127.0.0.1:<P>` (`tunnel.go`).

  One run of the program carries one SSH connection: closing the connection ends the program.
- **D3 The target shape.** `{ kind: 'colab', user, auth, workspace, hostKeys? }`. It has no host, port, jump host or `expectedEnd`, and, like every target, no field for a program, a path to one, an argument or a command. The schemas are strict (`additionalProperties: false`), so a field the server adds is refused by the JSON Schema, by the connector's decoder (`protocol.Decode` → `InvalidError`; the link closes with 4400, `link.go` `onText`) and by the zod mirror. `runtime.python` keeps its `ssh` meaning: the interpreter that the start template of design §6 runs inside the runtime, validated by rule 5 and quoted. It never reaches the `colab` program.
- **D4 Trust name.** The runtime has no `host:port`, so its host key is kept under the fixed name `colab.invalid` and port 22, which never resolves (`.invalid`) and is never dialled:
  - in the connector's `known_hosts` (`KnownHosts.Add/Replace/Lookup`, unchanged), as the line `colab.invalid <type> <key>`;
  - in `notebook_connections.trusted_host_keys` as `{ host: 'colab.invalid', port: 22 }`;
  - in `confirmations`.

  The §5.2 table applies unchanged. A new runtime's key is row 3 or 5, `host_key_changed`: a hard stop (A30), never silently accepted, and replaced through the existing flow (confirmation with `replacing`, recent sign-in, old line kept as a comment).
- **D5 Reused parts of `sshtarget`.** For a `colab` target:
  - authentication follows the order of §5.3: agent, then key file (+ certificate), then keyboard-interactive in the connector's own terminal if the runtime asks;
  - workspace, forwarding, runtime start and attach, token on stdin, tunnel, keepalive, leases from `sessions.json` (idle, grace, 12 h maximum) and the orphan sweep all apply unchanged.

  The program only ever carries encrypted SSH packets, so it never sees a key, a passphrase, the Jupyter token or a cell.
- **D6 Errors and losses.**
  - Two new `reachability` codes: `colab_missing` and `colab_proxy_failed`, with two new recoveries, `install_colab` and `check_colab`.
  - Reused codes: `unsupported_target` (a connector that does not offer the target, or the server's refusal before sending), `invalid_target`, `connection_timeout` (no SSH banner within 20 s) and every code from `host_identity` onwards.
  - The connector has no address to probe for this route: `reachable()` cannot parse the `proxyConn` address, so `DialsFail` holds. Rules 1, 3, 4 and 5 of §5.5 apply as usual. Otherwise a program exit, a connection that stops answering, or a runtime that Google ends all give `host_unreachable`.
  - `allocation_expired`, `ssh_timeout` and `process_exited` do not occur.
- **D7 Network scope and jump host.** The connector dials no address for this target, so §8's classification and `--allow-net` do not apply, and the server's `checkTargetPolicy` already returns ok for non-`ssh` targets (`apps/server/src/relay/netpolicy.ts`). There is no jump host. The program's own connections are outside the connector's scope, as with an OpenSSH `ProxyCommand`. Rule 5 of §8 (fixed forwarding destination) still holds.
- **D8 Paid-plan condition.** The condition is a paid Colab plan with a positive compute-unit balance (needed_specs N8, Colab FAQ). Parallax states it in the Connect panel option and the user documentation. Nobody in Parallax checks it: neither the connector nor the server can see the plan, and neither claims to. Free Colab keeps open-in-Colab-and-upload, unchanged.
- **D9 Platforms.** `hello.targets` lists `colab` on Linux and macOS, which includes the Linux connector inside WSL. The native Windows connector does not list it, and its session manager already answers a request for an unregistered kind with `error unsupported_target` (`session/manager.go`, `Request`/`open`). The Connect panel says so for a connector whose `os` is `windows`.
- **D10 Protocol version.** This records a reasoned deviation from §4.6, a compatible v1 extension instead of v2, in the ADR and in §4.6. A connector lists `colab` only from the version that implements it. The server sends a `colab` target only to a connector whose live `hello.targets` lists it (P5-21, `relay/targets.ts`). So connector-v0.1.0, released on 2026-10-08, never receives a kind it would close the link over. No existing message, field, rule or code changes meaning.
- **D11 Secrets.** Google credentials stay with the `colab` program. No message, `sessions.json` record, log line or `detail` holds a token, key, passphrase, OAuth code or URL with a secret. The program's stderr is read continuously into a buffer that keeps the last 4 KiB; the retained bytes pass through `redact.Redact` and `safetext.Sanitize` and are then discarded. What the connector logs or sends about a run is fixed catalogue text and the program's exit status, which holds no secret; its stdout and input are never logged. A signed-out program is not inferred from stderr: it is one cause of `colab_proxy_failed`. Ordinary redaction would miss an OAuth code it does not recognise, so no stderr text is forwarded at all.
- **D12 Units.** P5-20 owns the run. It carries the documents, the protocol (schemas, fixtures, the Go decoder and rules, and the TypeScript mirror, because the TypeScript tests read the protocol files), the transport core, the A48 Go test and the no-command test. Everything a session-3 unit does not need goes to P5-20a in the further session 3a: the connector offering the target (`cli/run.go`), the process group/`Pdeathsig`, the stderr drain, the two codes, the Colab description of a session and the guard tests. Session 3 has started and holds 8 units, and session 4 holds 8. P5-21 needs only the protocol and target kind from P5-20; its tests use the server's fake connector. Sizes are about 515 for P5-20, 500 for P5-20a and 510 for P5-21. The split candidates are named in steps 9, 13 and 17.
- **D13 Where a Colab session is named.** Four places name a session's location, and for a `colab` session each names the Colab runtime and the target's account: the connector's session log line and its `--confirm-sessions` question (`describe` in `connector/internal/session/manager.go`, P5-20a: `the Colab runtime as <user> in <workspace>`), the Files panel (`hostLabel` in `apps/server/src/relay/targets.ts` sends `host` "the Colab runtime" instead of null, which `where` in `apps/web/src/notebooks/files/files.ts` shows as "this computer", P5-21) and the Connect summary (`apps/web/src/notebooks/connect/ConnectSummary.tsx`, P5-21: destination "the Colab runtime", account `target.user`). None of them shows "this computer", the connector's device name or "the account running the connector" for a Colab session, and each has a test that says so.

## Risks

- **The real `colab` program is unverified.** The N8 findings establish only that `colab ssh --proxy-mode` serves as a `ProxyCommand` and that the README lists Linux and macOS. Several things are unknown:
  - whether it needs anything else to reach a runtime;
  - how long it takes to produce a banner (the reachability budget is 20 s);
  - whether it exits on end of input;
  - which account and key the runtime's SSH server accepts;
  - whether it allows `direct-tcpip` to loopback;
  - whether Jupyter Server 2 is present.

  Mitigation: every failure surfaces as a named stage code (`colab_proxy_failed`, `connection_timeout`, `auth_rejected`, `forwarding_denied`, `jupyter_missing` …), never as Ready. The owner's paid-plan check (plan §7) settles it without gating any unit.
- **Between P5-20 and P5-20a the transport exists but is not offered.** During that time its failure codes are `connection_refused` and its stderr is discarded. No person can reach it: `run` does not list `colab`, and the server only sends `colab` to a connector that lists it. The design text describes the final state, and P5-20's entry names the gap.
- **Hello compatibility in the other direction.** A connector that lists `colab`, linked to a server built before P5-20, is refused with 4400 and retries. No server release exists yet (P5-22 is the first). Releasing the first connector that lists `colab` only once such servers run is the owner's call (open question 6).
- **Every new runtime is a `host_key_changed` hard stop.** This is deliberate (A30), but it adds friction: a replacement with a recent sign-in each time. The Colab copy in `StageList` says when to replace.
- **Secrets on the program's stderr.** `redact()` matches only registered secrets and `*token=` values, so an OAuth code or short device code the program prints would survive it. The stderr is therefore drained, passed through `redact()` and the sanitiser, and discarded: no byte of it reaches a log, a message or a `detail`. The cost is diagnosis: `colab_proxy_failed` gives only the exit status, and the person checks the program in their own terminal (the recovery `check_colab`).
- **Process cleanup.** On macOS a crash of the connector relies on the program noticing that its pipes closed. Linux has `Pdeathsig`, and process-group kills cover children. The pid is not in `sessions.json`, so no sweep finds a surviving program.
- **`PATH` trust.** The connector runs whatever `colab` resolves to, as OpenSSH runs a configured `ProxyCommand`. A malicious program on the person's `PATH` is outside the threat model, alongside a malicious connector binary (§14).
- **Sizes.** P5-20 (≈ 516), P5-20a (≈ 501) and P5-21 (≈ 510) have about 15–16% margin, against the 10–35% overruns of past units. Each has a named candidate.
- **Windows sessions skip the in-process SSH tests.** The A48 Go test runs only in CI on ubuntu, as A28 to A30 do. The done-check's "fails without the change" is shown in CI.
- **Shared connector-wide trust record.** All `colab` connections on one connector share the `known_hosts` line for `colab.invalid`. Switching between two runtimes therefore replaces the key each time.

## Open questions

1. Does `colab ssh --proxy-mode` reach the intended runtime with no further argument? The N8 findings name none. If the real program needs one, for example to choose a runtime, adding it changes the fixed command and is the owner's decision. It would still be a constant in the connector, never a value from the server.
2. Which account and key does a Colab runtime's SSH server accept, and does it permit `direct-tcpip` forwarding to loopback and running Jupyter Server 2? The owner's paid-plan check (plan §7) answers this. The outcome is recorded there without account data and gates no unit.
3. Does the real program need an environment variable outside `colabEnv`, for example for its own credentials? Adding one is a later, tested change.
4. Is 20 s of `reachability` enough for the program to produce an SSH banner? The design keeps the deadlines of §5.1.
5. These are not built, and each is a later owner decision:
   - free Colab over SSH;
   - the two other Q26 routes (a tunnel to a loopback target, a connector inside the runtime);
   - a general `ProxyCommand`;
   - `colab` targets in class templates or for managed connectors;
   - Colab over SSH on the native Windows connector.
6. Release order: should the first connector release that lists `colab` be tagged only once every running server accepts it (any server built after P5-20)? Release tags are the owner's.
7. Should the panel ask the person to acknowledge the paid plan, for example with a checkbox? It is not added: it would be no check, and keeping it would need stored state, which needs a migration that this work may not add.
8. Should trust be per runtime instead of per connector? A runtime label in the target would avoid replacing the key for each new runtime, at the cost of a new field. This design keeps one trust name.
