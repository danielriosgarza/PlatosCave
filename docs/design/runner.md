# Runner detailed design (P3-12)

**Status:** accepted with the merge of P3-12, 2026-10-01; corrected by P3-12b (the twelve items left open by the review of PR #108) and P3-12c (the twelve follow-ups left open by the round-3 review of PR #127) before P3-13, P3-14 and P3-16 implement it. Refines [ADR-0004](../adr/0004-code-execution-isolation.md) for §11 of the [product specification](../product-spec.md). The normative machine-readable parts are the JSON Schemas in [`runner/protocol/v1/`](../../runner/protocol/v1/); this document explains them and fixes everything the schemas cannot: the harness behaviour, the container policy, limits and bounds, the per-student cap, replay and regrade, production placement and network policy. Items P3-13, P3-14, P3-16 and P4-11 in [the plan](../delivery/plan.md) implement it and name their tests from §12 below.

Terms: a **run** is one execution request for one code question and one code snapshot. A **job** is the document the server enqueues for it. A **check** is one test case inside a job. The **harness** is the program inside the sandbox that runs the checks and reports a **result**. The **runner** is the trusted service (`apps/runner`) that turns jobs into containers and results into an **outcome**.

## 1. Components and trust boundaries

```
 browser ──HTTPS──▶ apps/server (api) ──INSERT execution_jobs; bossExec.send('execution.run', job)──▶ Postgres ┐
                    apps/server (worker) ◀──bossExec.work('execution.result'), work('execution.failed')──────┤ schema pgboss_exec
                                                                                                             │
 runner host:       apps/runner (role parallax_runner, schema pgboss_exec only) ◀──fetch / send result / complete─┘
                        │ dockerode: create ▸ attach ▸ start ▸ stdin: nonce line + job JSON + EOF ▸ wait ▸ inspect ▸ remove
                        ▼
                    sandbox container (NetworkMode none, read-only root, tmpfs /work /tmp, uid 10001)
                        python3 /opt/parallax/harness/run.py  ──▶ one nonce-framed result document on stdout
                            └─ per check: materialise the check's files into /work/c<N> ▸ subprocess (python3 | Rscript) ▸ compare ▸ remove
```

| Component | Trusts | Is trusted for |
| --- | --- | --- |
| `apps/server` | its own tables; `RunnerOutcome` only after zod validation | authorisation (ADR-0002), the per-student cap, limit clamping, which checks and files a student may see |
| Postgres schema `pgboss_exec` | — | the only channel between server and runner, in both directions: queues `execution.run`, `execution.result` and the dead-letter queue `execution.failed` |
| `apps/runner` | job payloads from the queue after zod validation; the Docker daemon | enforcing the container policy, re-clamping limits, allowlisting images, classifying outcomes |
| sandbox container, harness | nothing from outside except what arrives on stdin | nothing: its stdout is parsed, validated and bounded before any field is used |
| student code | — | nothing; it can only influence its own result's `passed`/`failed`/`error` fields |

The job payload carries **no user, class, attempt or course identifiers**, only `jobId` (ADR-0004 §Components). The runner's database role has privileges in `pgboss_exec` only: a compromised role can read the jobs waiting there (student code and checks, without names) and the outcomes, and can enqueue runs and results, and nothing else. It has no privilege on the application tables or on the application's own `pgboss` schema, so it cannot read the scoped jobs of P1-07, whose payloads name an actor, nor enqueue one; `a13-runner-role.itest.ts` asserts both (§10.3). Injected or forged results are bounded by what the server does with an outcome: it writes a result row for the named job and never changes an attempt's state or grade from it directly (P4-01 reads results through its own rules).

## 2. Life of a run

1. **Request.** A student clicks Run sample tests. The client autosaves the editable files and `POST`s them to `/api/classes/:classId/attempts/:attemptId/questions/:questionId/runs`. The route runs under class scope (role student, own attempt).
2. **Snapshot and reuse.** The server computes `codeHash` (§8.2). If this attempt already has a terminal result for (`attemptId`, `questionId`, `codeHash`, `set: 'public'`, `graderVersion`) whose status is not `infrastructure_error`, it answers `200` with that run and `reused: true`: identical code gives identical output, a slot is saved, and the record still binds this student, this attempt and the hash (spec §11, A12). Runs of other attempts or students are never reused, so every run a student sees is one of their own.
3. **Cap.** Inside one transaction with `pg_advisory_xact_lock(hashtext('execution:' || userId))`, the server loads this user's `execution_jobs` across all classes (`forOwnRows(scope.user, executionJobs)`, §8.4) with `reason = 'sample'` in `queued` or `running`, looks their pg-boss jobs up in **one** statement (`SELECT id, state FROM pgboss_exec.job WHERE name = 'execution.run' AND id = ANY($1)` over the rows' `boss_job_id`s, §8.5) and counts those the staleness rule of §8.5 calls **live** (pg-boss job `created`, `retry` or `active`, or no job yet inside the send window). The cost under the lock is therefore two statements before the insert, however many rows the student has: in normal operation the worker's result handler settles a row seconds after its job completes, so the set holds at most the two live rows plus the rows whose settlement is in flight; during a worker outage it grows by one row per finished run and shrinks again when the worker returns and drains `execution.result`, and the single lookup keeps that growth off the lock's critical path. A live row counts however long it has waited, because under load a sample run legitimately sits in `created` for many minutes (§5, `queuePosition`); a row that is not live is simply not counted, so a lost message, a dead worker or a crash mid-enqueue can never lock a student out. The cap only counts: it writes nothing to the rows it finds in other classes, and a row that is not live is settled later by the read path under its own class scope (§8.5). Two or more live rows: `429 { error: 'too_many_runs', active: 2, message: 'Two runs are already queued or running. Wait for one to finish.' }`. A queued sample run for the same question is cancelled first (`supersededBy`), so a student iterating quickly never queues behind their own stale code.
4. **Enqueue.** The server chooses the pg-boss job id itself (`randomUUID()`), inserts the `execution_jobs` row (`state queued`, `boss_job_id` set) in that transaction and commits; only then does it build the job with `buildRunnerJob` (§8.2) and call `bossExec.send('execution.run', job, { id: boss_job_id, priority, expireInSeconds: wallSeconds + 60, retryLimit: 3, retryDelay: 5, retryBackoff: true })` on the execution pg-boss instance (§8.4; pg-boss 12.35.0's `JobOptions.id` makes the id the caller's choice). pg-boss runs on its own pool connection, so sending inside the transaction would let a fast result arrive before the row is visible. Because the id is on the row before the job exists, there is no window in which a result, a dead letter or a read finds a row without its id: the handlers of §8.5 always match on `boss_job_id`, and `recordOutcome` always has the id for `started_at` and `infrastructure_attempts`. After the send returns the server marks the row with a **conditional write**, `UPDATE execution_jobs SET job_sent_at = now() WHERE id = … AND state = 'queued' RETURNING state`, and never with a plain read: every other writer of a `queued` row (the cancel route, a supersede, the read path's `enqueue_failed` move, `recordOutcome`) is itself a single `UPDATE … WHERE state = 'queued'`, so the row lock orders them and exactly one wins, where a `SELECT` could read `queued` an instant before a concurrent `enqueue_failed` committed and leave a job running for a row shown as unavailable. When the update touches no row the row was settled while the send was in flight, and the server calls `bossExec.cancel` on the job it just created, unconditionally: `cancel` acts only on a job that is not yet complete, so it stops the job of a cancelled or `enqueue_failed` row and is a no-op for a row the worker already settled with a result (a slot fetched, ran and the handler recorded it before this update, which NOTIFY-driven fetching makes possible). A run the student has been told is cancelled or unavailable therefore never runs, and no result can flip a settled row back. The read path's `enqueue_failed` move is the mirror image: after its own commit it calls `bossExec.cancel('execution.run', boss_job_id)` by the id it knows from the row, a no-op while no job exists yet, so in every interleaving one of the two cancels finds the job (settlement committed before the post-send update: the server's cancel; after it: the read path's cancel runs after the job was inserted). A send that throws, including one that fails on the way back after the insert landed, marks the row `infrastructure_error`, kind `enqueue_failed`, and cancels by id too. The route answers `202 { runId, state, queuePosition }` with the state the update returned, or the row's state read afterwards when it touched none: `queued` in every ordinary case and the row's actual state in the races above, as step 2 answers with an existing run.
5. **Fetch.** One of the runner's slots fetches the job. The runner validates it with `RunnerJob` and the semantic rules of §3.1, re-clamps limits, resolves the image (§6.4), creates the container with `buildContainerConfig(job, image)` (§7.3), attaches to stdin, stdout and stderr, starts it, writes the 32-hex nonce, a newline and the job JSON to stdin, closes stdin, and arms the kill timer at `wallSeconds + 5 s`. Nothing is uploaded to or mounted into the container.
6. **Harness.** Inside the container the harness reads the nonce and the job from stdin and keeps the job in memory only, makes itself non-dumpable, parses the student's files (compile phase), and for each check materialises the files that check may see into a fresh directory, runs it in a subprocess with the remaining wall budget, compares, and removes the directory. It then prints one framed result document (§4.4) and exits 0.
7. **Collect.** The runner waits for exit, inspects `State.OOMKilled`, extracts the framed result from stdout, validates it with `RunnerResult`, classifies (§7.4) and removes the container. It sends the outcome as an `execution.result` message and then completes its `execution.run` job with the same outcome as output. Infrastructure problems fail the pg-boss job instead; after the retries, or at once for terminal kinds, pg-boss moves it to the dead-letter queue `execution.failed` (§7.5).
8. **Record.** The server worker consumes `execution.result`: it inserts the `execution_results` row, moves `execution_jobs.state` to the outcome's status, and copies `startedOn` and `retryCount` from the pg-boss job. Dead letters on `execution.failed`, which carry the failed job's document with the failure in `sourceOutput` (§8.5), become `infrastructure_error`. The API's `GET …/runs/:runId` returns the student view (§8.6): status, public checks with expected/actual/message, the code hash, and never a hidden check; while the row is not terminal it reports `queued` or `running` from the pg-boss job's state.
9. **Stale.** The editor compares the result's `codeHash` with the hash of the current editor content and labels the output out of date when they differ (A12).

A grading run (step 4 with `set: 'full'`, `reason: 'grading'`) is enqueued by the submission flow, not by the student, and is read only by instructors and the grading item.

## 3. Protocol v1

Files: [`job.schema.json`](../../runner/protocol/v1/job.schema.json), [`result.schema.json`](../../runner/protocol/v1/result.schema.json), [`examples/`](../../runner/protocol/v1/examples/). P3-13 mirrors them as zod schemas in `packages/contracts/src/runner.ts` (`RunnerJob`, `RunnerResult`, `RunnerOutcome`, `RUNNER_BOUNDS`, `clampLimits`, `validateJob`) with a test that parses every example in `examples/`, rejects every file under `examples/invalid/` (fails the JSON Schema) and rejects every file under `examples/rejected/` (passes the JSON Schema but breaks a semantic rule below). Each invalid or rejected fixture breaks exactly one rule, so a mirror that misses a rule fails on a named file. The Python harness tests (P3-14) read the same fixtures. JSON Schema's `format: uuid` is an annotation in draft 2020-12; the zod mirror asserts it. A change to either schema is a protocol change: bump `v`, keep the old file, and have the runner accept both until no server sends the old one.

### 3.1 Job

| Field | Meaning |
| --- | --- |
| `v` | `1` |
| `jobId` | `execution_jobs.id`; echoed in the outcome so the server can match it |
| `runtime.id` | approved runtime, `python-3.12` or `r-4.6`; the runner maps it to an image |
| `runtime.language` | `python` or `r`; selects the harness branch |
| `runtime.image` | only for replays: the exact image the original run used, as a repository digest (`repo@sha256:…`) or a Docker image id (`sha256:…`) (§9) |
| `set` | `public` (student-triggered; only public checks and non-hidden files are present) or `full` (every check and file) |
| `limits` | `wallSeconds`, `memoryMiB`, `outputBytes`, clamped by the server to §5 and clamped again by the runner |
| `files[]` | `path`, `content`, `encoding` (`utf8` default or `base64`), `hidden` (default false); the question's starter files overlaid by the student's editable files; at most 64 files and 2 MiB decoded |
| `checks[]` | 1 to 50 checks, names unique, order significant; `files[]` on a check lists additional hidden files it needs |

Paths are relative, at most 200 characters, every segment starting with a letter, digit or underscore (so `.`, `..`, dotfiles and absolute paths are unrepresentable).

**Semantic rules** the schema cannot express, enforced by `validateJob` in the server (before sending), in the runner (terminal `job_invalid`) and in the harness (exit 64), each with a fixture under `examples/rejected/`:

1. check names are unique (results are matched to checks by name);
2. a job with `set: 'public'` contains no hidden check and no hidden file;
3. every path a check names (`file`, `files[]`) is in `files`, and a public check names no hidden file;
4. paths are unique after normalisation, no path is a directory prefix of another (`data` beside `data/sample.csv` cannot be materialised; fixture `job-path-is-directory.json`), and the decoded size of all files is at most 2 MiB (the serialised job at most 4 MiB; the stream the harness reads is that plus the 33-byte nonce line, §4.2).

**Check kinds**

| Kind | Runs | Passes when |
| --- | --- | --- |
| `stdio` | `file` as a program (`python3 -s -P -B /opt/parallax/harness/launch.py file args…`, which puts the check directory first on `sys.path`, or `Rscript --vanilla file args…`) with `stdin` | exit code equals `expected.exitCode` (default 0) and stdout compares equal to `expected.stdout` under `compare` |
| `call` | the language driver loads `file`, calls `function` with JSON `args` and `kwargs` | `expected.value` compares equal to the returned value under `compare`, or the call raises an exception matching `expected.raises` |
| `script` | an author-written test program `file` with `args` and `stdin` | exit code 0; anything else is `failed` with the last line of stderr as the message |

`call` and `stdio` checks are the strong kind: their expectations exist only in the harness (§4.5), so the code under test can pass them only by producing the expected value or output. A `script` check is the weakest kind: its verdict is an exit code decided inside the student's process, and the student's module runs at import time, so `os._exit(0)` in a solution, conditioned on the presence of the hidden test file, passes every hidden `script` check without an assertion running. In-process tests cannot be made cheat-proof; `script` checks exist for convenience (several assertions without a test framework), and publication validation warns when a question's hidden checks are `script`-only (§8.1, §11).

**Comparison modes** (`compare.mode`; `abs` defaults to 1e-6 and `rel` to 1e-9; a number `a` matches `b` when `|a − b| ≤ abs + rel·|b|`)

| Mode | For | Rule |
| --- | --- | --- |
| `exact` | stdio, call | stdio: the decoded texts are identical. call: the JSON serialisations are structurally equal (`1` equals `1.0`; tuples are lists) |
| `trimmed` | stdio | trailing whitespace removed from every line, trailing blank lines removed, then identical |
| `tokens` | stdio | whitespace-separated token sequences identical |
| `numeric` | stdio, call | stdio: token sequences of equal length where numeric tokens match within tolerance and other tokens are identical. call: recursive structural equality where numbers match within tolerance |
| `repr` | call | the language's `repr` (Python) or `deparse` (R) of the value equals the string `expected.value` |

`expected.raises.type` is matched against the raised exception's class and its bases in Python (`ValueError`), and against the condition classes in R (`error` matches any error). `message`, when given, is a regular expression searched in the message. A `call` check that expects a value and gets an exception is `error`/`exception`, not `failed`; a check that expects an exception and gets a value is `failed` with `actual: 'returned <repr>'`, which is the wireframe's `Expected: ValueError` case.

`job-sample-python.json` and `job-full-python-replay.json` are the `public` and `full` jobs of the same question: the public one carries the editable `solution.py` and the public `data/sample.csv`, the full one adds the hidden `tests/hidden_test.py` and the two hidden checks.

### 3.2 Result

One entry per job check, in job order. Statuses:

| Status | Meaning | Job status it implies (§7.4) |
| --- | --- | --- |
| `passed` | ran and compared equal | — |
| `failed` | ran and compared different, or a script exited non-zero | `failed` |
| `error` | did not reach a comparison; `errorKind` says why: `exception` (uncaught, call checks), `exit` (unexpected exit code), `signal`, `memory` (killed while the cgroup counted an out-of-memory kill), `spawn` (could not start, for example the pids limit), `harness` | `failed`, except `memory` → `resource_exhausted` |
| `timeout` | killed at its time cap | `time_limited` |
| `skipped` | not run: compile error, or the wall budget was already spent | `failed` |

`expected`, `actual` (≤ 2048 characters, cut with `…`; the harness cuts by the size of the field's JSON encoding, at most 2048 bytes, which satisfies the character limit and bounds the frame, §7.4) and `message` (≤ 512, likewise) are what the UI shows per public check, in the wireframe's form `FAIL [2, 4, 6, 8] · Expected: 1.290994 · Received: None`. `stdout`/`stderr` are the check's captured streams, each bounded by what remains of the job's `outputBytes` (§4.3), `truncated` when cut. `compileError` (`file`, `line`, `message`) is present when a file did not parse; every check is then `skipped`, so a syntax error is shown as a compile error distinctly from a runtime error (`error`/`exit` with the traceback in `stderr`), as spec §11 requires. `runtime.version` is the interpreter's own version string; `harnessVersion` is the integer version of `runner/harness`.

### 3.3 Outcome (runner → server, zod only)

```ts
RunnerOutcome = {
  v: 1, jobId,
  status: 'passed' | 'failed' | 'time_limited' | 'resource_exhausted',
  image: { ref: string; id: string; digest: string | null },      // docker Id, RepoDigests[0]
  container: { exitCode: number | null; oomKilled: boolean; killedByTimer: boolean; durationMs: number },
  result: RunnerResult | null,   // null only with oomKilled or killedByTimer
  harnessLog: string,            // container stderr tail, ≤ 8 KiB; never student output (the harness is pid 1, §4.4)
}
```

The outcome travels twice: as the `execution.result` message the runner sends, and as the output of the completed `execution.run` job (for operators). Infrastructure problems are not outcomes. The runner fails the pg-boss job with `{ kind, message }`, `kind` ∈ `daemon_unreachable`, `image_unavailable`, `image_not_allowed`, `job_invalid`, `harness_failed` (non-zero exit without OOM or timer), `result_missing`, `result_invalid`. `image_not_allowed` and `job_invalid` (which includes a harness exit 64) are terminal (`deadletter` in pg-boss's per-job results); the others are retried up to three times with backoff, then terminal. pg-boss dead-letters a terminal failure onto `execution.failed` as a new job whose `data` is the failed job's document (the `RunnerJob`), whose `sourceOutput` is the failed job's output (the runner's `{ kind, message }`, or pg-boss's own `{ "value": { "message": "job timed out" } }` when the last attempt expired) and whose `sourceId` is the original job's id (pg-boss 12.35.0 `insertDeadLetterJob`); the server consumes it (§8.5, which maps pg-boss's timeout output to kind `expired` and any other output without a known kind to `unknown`) and shows **Run unavailable · Retry**.

## 4. Harness

### 4.1 One harness, two languages

`runner/harness/run.py` is stdlib-only Python 3 and is the harness for both images: the R image installs `python3` from its Ubuntu base for this purpose. Language-specific work is confined to two small drivers, `driver.py` and `driver.R`, and a command table:

| | python | r |
| --- | --- | --- |
| compile phase | `python3 -s -P -B -c 'import ast,sys; ast.parse(open(sys.argv[1]).read(), sys.argv[1])' FILE` for every non-hidden `*.py` | `Rscript --vanilla -e 'invisible(parse(commandArgs(TRUE)[1]))' FILE` for every non-hidden `*.R`/`*.r` |
| stdio | `python3 -s -P -B /opt/parallax/harness/launch.py FILE ARGS` | `Rscript --vanilla FILE ARGS` |
| call | `python3 -s -P -B /opt/parallax/harness/driver.py` | `Rscript --vanilla /opt/parallax/harness/driver.R` |
| script | `python3 -s -P -B /opt/parallax/harness/launch.py FILE ARGS` | `Rscript --vanilla FILE ARGS` |
| interpreter version | `python3 --version` | `Rscript -e 'cat(R.version$major, R.version$minor, sep=".")'` |

One implementation means one test suite, one version number and no base-R JSON parsing. `jsonlite` is used only inside `driver.R`.

The Python flags are `-s -P -B`, which is `-I` without the `-E` it implies: `-s` keeps the user site directory off `sys.path`, `-P` (Python 3.11 and later) keeps the program's own directory off it, `-B` writes no bytecode. `-E` is deliberately absent because it makes the interpreter ignore every `PYTHON*` variable, so under `-I` the `PYTHONHASHSEED=0`, `PYTHONDONTWRITEBYTECODE` and `PYTHONIOENCODING` of §4.3 would do nothing and a program printing a set of strings would give a different order on every run (reproduced on 3.11: `PYTHONHASHSEED=0 python3 -I -c 'print(hash("a"))'` differs per run, `-s -P -B` is stable). The environment is scrubbed by the harness (§4.3), so the only `PYTHON*` variables a child sees are the harness's own. With `-P` neither the check directory nor the program's own directory is on `sys.path`, so `from solution import …` in a test program or a sibling import in a multi-file program would fail; `launch.py` is a stdlib launcher of a few lines that inserts its cwd (the check directory) at the front of `sys.path`, drops itself from `sys.argv`, and runs `FILE` with `runpy.run_path(…, run_name='__main__')`. `driver.py` performs the same insertion for `call` checks (§4.5). `Rscript` resolves `source()` paths against the cwd and needs no launcher.

### 4.2 Start-up

1. `main(argv)` takes the swept roots as optional arguments, `--work`, `--tmp` and a repeatable `--ipc`, with the production defaults `/work`, `/tmp`, `/dev/shm` and `/dev/mqueue` (§7.3's `Cmd` passes none); an explicit `--ipc` **replaces** the default list rather than extending it (argparse's `append` with a list default would do the opposite, and a test passing one temporary IPC root would then sweep the host's `/dev/shm`); every later step names the defaults for brevity. The harness tests of §12 exercise it only this way, spawning `python3 run.py --work … --tmp … --ipc …` with temporary directories, the nonce and a job on its stdin, and reading the frame from its stdout, so `prctl`, the signal handler, the wait loop and the end-of-check kill act on the harness process and never on the test process; `run(job, work_dir, tmp_dir, clock, ipc_dirs)` is the function `main()` calls after the steps below, and only pure helpers (comparison, encoded-size cuts, the environment table) are unit-tested in-process. Read stdin to EOF with a 10 s `select` timeout and a cap of 4 MiB plus the nonce line (33 bytes: 32 hex characters and a newline), so a job of exactly the 4 MiB that §3.1 allows is accepted: the first line is the nonce (`^[0-9a-f]{32}$`), the rest is the job JSON. A missing or malformed nonce, a timeout, an oversize stream, or a job that fails the structural check (`v`, `runtime.language`, `files`, `checks`, `limits`) or a semantic rule of §3.1 → exit 64 without output. Then close fd 0 and reopen `/dev/null` on it so children never inherit the container's stdin.
2. `prctl(PR_SET_DUMPABLE, 0)` and `prctl(PR_SET_CHILD_SUBREAPER, 1)` via `ctypes`, and the no-op `SIGINT` handler of §4.4. The subreaper flag makes orphans re-parent to the harness whether or not it is pid 1 (as pid 1 it is a no-op), so the wait loop of §4.3 reaps them inside the image and in the `check` job alike, where the tests run the harness as an ordinary process (§12). Non-dumpable means that from now on no same-uid process can open `/proc/<harness pid>/fd/*`, `environ` or `mem`, so student code cannot write to the harness's stdout pipe or read the job, which exists only in the harness's memory and is never written to disk. The harness is pid 1 of the container (`Init: false`, §7.3), so this is the only process holding the container's stdout and stderr: there is no dumpable `docker-init` whose `/proc/1/fd/1` and `/proc/1/fd/2` a student process could write through (§4.4). (Children are fresh `exec`s and are dumpable again, which is irrelevant.)
3. Compile phase: the non-hidden files are materialised into `/work/compile/`, each is parsed in a subprocess with a 5 s cap inside the budget, and the phase ends with the same kill-and-reap and sweep as every check (the sweep of §4.3, over every root it names). The first failure fills `compileError` and marks every check `skipped` with `message: 'Not run: <file> does not compile'`. Hidden files are the author's and are validated at publication, not here.

### 4.3 Running a check

For each check in order, while `remaining = wallSeconds − elapsed > 0`:

- **Materialise.** `<work root>/c<N>/` and `<tmp root>/c<N>/` (`/work/c<N>/` and `/tmp/c<N>/` in the image; the roots are the arguments of `main()`, §4.2) are created with `mkdir` (never `exist_ok`): the sweep below has already run, so nothing can exist there and an `EEXIST` is an internal fault (exit 70), not a condition a job can produce. `/work/c<N>/` receives the files this check may see: every file with `hidden: false`, plus, for a hidden check only, the hidden files it names in `file` and `files[]`. The check runs with that directory as cwd and with the private `/tmp/c<N>/` as `HOME` and `TMPDIR`. Public checks therefore never have a hidden file on disk, and a hidden check sees only the hidden files it declared. Throughout the check the harness reaps orphans as they die, from its own wait: processes whose parent exited are re-parented to the harness (as pid 1 inside the image, and through `PR_SET_CHILD_SUBREAPER` in both contexts, §4.2 step 2, which is why the loop below holds in the `check` job too), and a zombie holds its pid against `PidsLimit: 64` until reaped, so the main thread waits with `os.waitpid(-1, 0)` in a loop, reaping on the spot every pid that is not the check's direct child and ending when the direct child's status returns. The child's exit status comes from that call and never from `Popen.wait()` or `poll()` (which would read `ECHILD` as exit 0); the direct child's pid is known from `Popen` before the loop starts, so a child that exits at once is a zombie the loop collects, not an orphan it mistakes; there is no second reaper to race or starve, and nothing peeks or spins. The harness sets `proc.returncode` from the status that call returned (`-signum` for a signal, else the exit code), so no `Popen` is ever finalised with `returncode is None`: such a `Popen` is appended to `subprocess._active`, and every later `Popen()` would `waitpid(pid, WNOHANG)` on that pid, which after a pid wrap (a fork bomb in a later check can wrap the namespace's `pid_max`) could reap a later check's direct child behind the loop's back. A check ends in a fixed order: the direct child's status returns from the loop (after the timer killed its group, if it did), the timer is cancelled, the harness kills every process left behind (`os.kill(-1, SIGKILL)`, which spares only the caller, the harness being pid 1), reaps them (`waitpid(-1, …)` until `ECHILD`), **then** joins the reader threads, and only then sweeps. The readers end at EOF, which needs every holder of the pipes' write ends to be dead: a program that leaves a daemon holding its pipes and exits would block a join placed before the kill until the runner's kill timer destroys the container (`killedByTimer`, no result). Outside pid 1, where the tests run the harness (§12), `kill(-1)` would reach every process of the user, so there the harness instead kills the direct child's process group and every process whose parent chain in `/proc/<pid>/stat` reaches it (its descendants, which `PR_SET_CHILD_SUBREAPER` keeps under it, §4.2), repeating until none is left, and then reaps to `ECHILD`. The sweep covers **both tmpfs roots**: everything under `/work` and under `/tmp` is removed, not only the two directories it created, because both roots are world-writable tmpfs and a stash at `/tmp/stash` or a pre-created `/work/c<N+1>` would otherwise survive; the entries of `/dev/shm` and `/dev/mqueue` (Docker's private IPC tmpfs under `IpcMode: 'private'`) are removed the same way. The sweep fixes permissions as it goes (same uid, no capabilities needed); a sweep that cannot complete is an internal fault (exit 70). So nothing a check wrote under `/work`, `/tmp`, `/dev/shm` or `/dev/mqueue`, and no process it started, outlives it, and `/work` and `/tmp` hold one check at a time. System V shared memory, semaphores and message queues are not swept and could carry bytes from one check to the next; that residual is covered by the release layer (`full` outcomes are hidden until release) and can be closed later by `IPC_RMID` over `/proc/sysvipc/*` if ever needed. In a `set: 'public'` job nothing hidden exists anywhere in the container, so its output is free of hidden material. In a `full` job the student's code also runs inside hidden checks, with hidden files on disk, so every field of a `full` outcome, public checks included, is still treated as potentially carrying hidden material (§8.6, §11): the sweep is defence in depth, the release layer is the control.
- **Process.** The harness creates the two pipes with `os.pipe()`, starts the reader threads on their read ends and starts the timer thread **before** spawning, so after the spawn it creates no thread: its own threads count against `PidsLimit: 64`, and a fork bomb must not be able to make a `Thread.start()` fail and turn a `failed` run into `harness_failed`. The timer's deadline is fixed when it starts, but it kills nothing until the main thread hands it the pid and process group id after `Popen` returns (it waits on an event set right after the spawn); if its deadline has already passed by then it kills at once, so a cap of a few milliseconds (the last check, with `remaining` nearly spent) cannot expire before a pid exists and leave a looping program uncapped until the runner's kill timer. Then `subprocess.Popen` with the command from §4.1, `start_new_session=True` (its own process group), `stdin` = the check's `stdin` (empty by default), `stdout`/`stderr` = the pipes' write ends (closed in the parent after the spawn), and **no `preexec_fn`**: with threads alive at fork time CPython documents `preexec_fn` as not safe (the child can deadlock between `fork` and `exec`, and Python 3.12 warns on the fork), and neither of its former jobs needs it. The resource limits are the `Ulimits` of §7.3 (core 0, nofile 256, fsize 32 MiB), applied by Docker to pid 1 and inherited by every child; and `SIGINT` needs no per-spawn reset because the harness's own disposition is a handler, which `exec` resets (§4.4): every child, `Rscript` included, starts with `SIG_DFL`, and a Python child then installs its usual `KeyboardInterrupt` handler, which it does only when it inherits `SIG_DFL`. The student's program therefore sees the signals a normal interpreter sees.
- **Environment.** Exactly: `PATH=/usr/local/bin:/usr/bin:/bin`, `HOME=/tmp/c<N>`, `TMPDIR=/tmp/c<N>`, `LANG=C.UTF-8`, `LC_ALL=C.UTF-8`, `PARALLAX_JOB=1`, `PYTHONHASHSEED=0`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONIOENCODING=utf-8`, `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, and for R `R_LIBS_USER=/tmp/none`. Nothing is inherited. The `PYTHON*` keys take effect because the interpreter runs without `-E` (§4.1); with `PYTHONHASHSEED=0` two runs of the same program give the same output, which the reuse of a result for identical code (§2 step 2) relies on.
- **Capture.** Two reader threads drain the pipes incrementally. Each stream keeps at most `outputBytes − bytes kept so far in this job`, counted as the size of the text's JSON encoding (UTF-8 with `ensure_ascii=False`, so the escapes for quotes, backslashes and control characters count), and sets `truncated` beyond that; reading continues (bytes are discarded) so the child never blocks on a full pipe and a 10 MiB print finishes normally, cut at 1 MiB with the default limit. Text is decoded as UTF-8 with replacement characters.
- **Time.** The cap is `min(check.timeoutSeconds ?? remaining, remaining)`. On expiry the harness sends `SIGKILL` to the process group, records `timeout` and **continues with the next check** while `remaining > 0`: `timeoutSeconds` is a cap for that check only, and `skipped` means the wall budget was spent (§3.2). Only the loop guard skips: once `remaining` reaches zero, whether through a check that ran out its cap of `remaining` or through accumulated time, every later check is `skipped` with `message: 'Not run: time budget spent'`. The harness waits for the process group to end before continuing; a daemonised process that escapes its group is killed by the kill-and-reap at the end of the check.
- **Memory.** Before and after the check the harness reads the `oom_kill` counter from `/sys/fs/cgroup/memory.events` (cgroup v2) or `/sys/fs/cgroup/memory/memory.oom_control` (v1); unreadable counters count as zero. A child that died by `SIGKILL` while the counter rose is `error`/`memory` with `message: 'Killed: memory limit of <n> MiB exceeded'`. If the harness itself is the victim, the container exits with `OOMKilled: true` and the runner classifies the job (§7.4) without a result.
- **Spawn failure** (`EAGAIN` from a saturated pids limit, `ENOENT`, `ENOSPC` while materialising) is `error`/`spawn`. Because the pipes, the readers and the timer exist before the spawn, a `Popen` that raises is followed by the teardown the check would otherwise reach through its child: the harness cancels the timer (cancelling sets a cancel flag and the pid event together, so a timer still blocked waiting for the pid wakes, sees the flag and exits instead of outliving the check), closes both write ends in the parent, joins the readers (which see EOF at once), then records the check and runs the end-of-check kill-and-reap and sweep as usual. Without that the readers would block on pipes whose write ends the harness still holds, the harness would hang until the container's kill timer, and the pre-created threads of each failing check would accumulate against `PidsLimit` until `Thread.start()` itself failed (exit 70, `harness_failed`), the outcome the pre-creation exists to prevent.
- **Comparison** per §3.1, performed by the harness, never by the driver (§4.5). `expected` and `actual` are rendered as JSON for values, as the raw text for stdio, and as `Type: message` for exceptions, each cut with `…` so that its JSON encoding (`ensure_ascii=False`) is at most 2048 bytes, which is at most 2048 characters as the schema requires and bounds every check entry to about 5 KiB besides its captured streams (§7.4). `message` is cut the same way at 512 bytes and is one line: `Expected 1.290994, received None`, `Line 2 differs`, `Exited with code 1`, `Expected ValueError, but the call returned None`.

### 4.4 Result framing

After the last check the harness repeats the kill-and-reap and sweep of §4.3 and only then writes the result, serialised with `ensure_ascii=False`, so no leftover process can interleave bytes with it and the frame is at most `outputBytes` plus the fixed overhead of §7.4. It writes nothing to stdout except a newline and the result, framed by the nonce:

```

--parallax-result <nonce>
{ …one-line JSON… }
--parallax-end <nonce>
```

The leading newline guarantees that the start marker begins a line whatever preceded it on the stream. Its own diagnostics go to stderr (kept by the runner as `harnessLog`, ≤ 8 KiB). The runner accepts a result only when the container exited 0 and exactly one well-formed frame with the job's nonce is present; bytes before, between and after frames are noise, ignored (and logged), never a reason to reject. Student processes cannot reach the container's stdout or stderr at all: the harness is pid 1 (`Init: false`, §7.3) and non-dumpable (§4.2 step 2), so it is the only process holding those descriptors and `/proc/1/fd/1` and `/proc/1/fd/2` are not openable by a same-uid process; children get `/dev/null` and harness-owned pipes. With `Init: true` (ADR-0004's table) `docker-init` would hold the same descriptors as a dumpable same-uid pid 1, and a student program writing through `/proc/1/fd/1` could not forge a result (it does not know the nonce) but could exceed the runner's read cap or glue bytes to the marker line and turn every attempt of a run into `result_invalid`/`result_missing`, and could put its text into `harnessLog`; making the harness pid 1 closes that (§13 item 1). Student code does not know the nonce (it is consumed from stdin before any student code runs and lives only in the non-dumpable harness's memory), so a forged or corrupted result cannot be accepted; killing the harness only produces `harness_failed`. As pid 1 of the namespace the harness is unreachable by signal from inside it: the kernel discards a signal sent to a namespace's init from within unless init has a handler installed, so `os.kill(1, SIGKILL)` or `SIGTERM` from student code returns 0 and does nothing. Python installs a `SIGINT` handler by default, which would let `os.kill(1, SIGINT)` raise `KeyboardInterrupt` in the harness, so at start-up (§4.2 step 2), before any child runs, the harness replaces it with a **no-op Python handler** and leaves every other signal at its default. The signal is then delivered and does nothing (an interrupted `waitpid` or `read` is retried, PEP 475), which holds whether or not the harness is pid 1, so the harness test that sends it `SIGINT` is meaningful in the `check` job too (§12); `SIG_DFL` would be discarded as well, since the kernel drops a signal to a namespace's init for `SIG_DFL` exactly as for `SIG_IGN`, but would kill the harness where it is not pid 1. Handlers reset to `SIG_DFL` on `exec`, so every child starts with the default disposition and no `preexec_fn` is needed (§4.3). The runner's kill timer and `remove(force)` send `SIGKILL` from the parent namespace, which does land. Exit codes: 0 result written; 64 bad input (nonce or job); 70 internal fault. With `ReadonlyRootfs` and tmpfs mounts no file survives the container's exit, and Docker refuses to copy files into a read-only container at all, which is why both the job and the result travel over the attached standard streams rather than through `/work` as ADR-0004 sketched (§13).

### 4.5 Call driver protocol

The harness starts the driver with the call specification as the first line of its stdin (`{ file, function, args, kwargs, outcomePath }`), followed by the check's `stdin` for the student function to read. The driver never receives `expected` or `compare`: the comparison happens in the harness, so neither the driver's memory nor its stdin is an oracle for the code under test. The driver adds the working directory to the module path (`sys.path.insert(0, cwd)`; `source(file, local = env)`), resolves `function` (dotted names allowed for Python attributes), calls it, and writes one JSON document to `outcomePath` (a harness-chosen file under the check's private `/tmp/c<N>/`): `{ ok: true, value }` or `{ ok: false, exception: { type, bases: [...], message } }`. Values are serialised as JSON when possible (tuples as lists, `NaN`/`Infinity` as the strings `"NaN"`, `"Infinity"`, `"-Infinity"`; R atomic vectors of length 1 unboxed, longer ones as arrays, named lists as objects) and otherwise as `{ "repr": "<repr>" }`, which `exact` compares as a string and `repr` mode compares directly. The student's own stdout and stderr are the process's streams and are captured as for any check. A student process can overwrite its own outcome file; that is equivalent to returning the expected value and is not a privilege the sandbox tries to remove: it passes only a check whose expected value the student already knows. Hidden `call` and `stdio` checks, whose expectations never leave the harness, and instructor review are the controls against cheating; `script` checks are not one of them, because their verdict is decided inside the student's process (§3.1). The sandbox is the control against escape (§11).

### 4.6 Versioning

`harnessVersion` is bumped whenever a result can differ for the same job (comparison semantics, environment, capture caps, driver serialisation). It is baked into the image label `org.parallax.harness` and reported in every result; the server includes it in `graderVersion` (§8.2), so a harness change never silently regrades.

## 5. Limits and bounds

Server-enforced bounds (`RUNNER_BOUNDS` in `packages/contracts/src/runner.ts`, used by `clampLimits` on both sides):

| Limit | Default | Minimum | Maximum | Course override |
| --- | --- | --- | --- | --- |
| `wallSeconds` (whole harness budget) | 10 | 1 | 60 | per question, within bounds |
| `memoryMiB` (container `Memory`, no swap) | 512 | 64 | 2048 | per question, within bounds |
| `outputBytes` (captured stdout+stderr, all checks together; one check may use all of it) | 1 MiB | 4 KiB | 4 MiB | per question, within bounds |

Fixed, not overridable: 1 CPU (`NanoCpus: 1e9`), 64 pids, `/work` and `/tmp` tmpfs 64 MiB each (`noexec,nosuid,nodev`; each holds one check's directory at a time and is swept after every check), `RLIMIT_FSIZE` 32 MiB per process, files ≤ 2 MiB decoded and ≤ 64, serialised job ≤ 4 MiB (the harness's stdin cap is that plus the 33-byte nonce line), ≤ 50 checks, `stdin` and `expected.stdout` ≤ 256 KiB, `expected`/`actual` ≤ 2048 characters and ≤ 2048 bytes encoded, `message` ≤ 512, runner stdout read cap `outputBytes + 50 × 5 KiB + 64 KiB` (§7.4), container kill timer `wallSeconds + 5 s`, pg-boss `expireInSeconds = wallSeconds + 60`, three infrastructure retries.

Per-student cap: **2** sample runs `queued` or `running` per user across all classes, counting only the rows the staleness rule of §8.5 calls live (§2 step 3); a row with a live job is never dropped from the count for its age, because the queue wait under load (below) is unbounded by design. Grading, replay, regrade and preview runs do not count against it and are not capped per user. Priorities: sample runs 10, preview runs 10, grading runs 5, replay and regrade 0, so an interactive student never waits behind a bulk regrade and a class of 200 submitting together drains in priority order with a visible queue position. pg-boss fetches `priority DESC, created_on ASC`, so `queuePosition` = jobs on `execution.run` in `created`/`retry` with a higher priority, whatever their creation time, plus those with the same priority created earlier.

The runner clamps once more and refuses (terminal `job_invalid`) a job that exceeds a bound after clamping, so a bug in the server cannot ask for more than the policy allows.

### 6.2 Pinning and tags

`scripts/runner-image.sh hash <lang>` prints the SHA-256 of the sorted contents of `runner/images/<lang>/` and `runner/harness/`; `scripts/runner-image.sh build <lang>` builds `parallax-runner-<lang>:<hash>` and tags it `:dev`. CI builds the image on every PR in the `runner` job and uses it by tag; nothing is pushed from CI. Production images are pushed to the organisation's registry by the deploy pipeline (§10) and referenced by **digest** everywhere: in `RUNNER_RUNTIMES` on the server, in `RUNNER_IMAGES` on the runner, in `execution_results.image_digest`. In development and CI, where no registry exists, `digest` is null and the Docker image id (`sha256:…`) stands in for it; both are stored and shown, and a replay pins whichever the original run recorded (§9).

### 6.3 Approved runtimes (server)

`RUNNER_RUNTIMES` (JSON array) lists what questions may select:

```json
[{ "id": "python-3.12", "language": "python", "image": "parallax-runner-python:dev", "digest": null,
   "harnessVersion": "1", "packages": ["numpy", "pandas", "scipy"] }]
```

Production configuration requires `digest`. Test authoring offers only these ids; publication validation rejects a question whose runtime is not listed.

### 6.4 Image allowlist (runner)

`RUNNER_IMAGES` maps a runtime id to the image references the runner may run, newest first: `{ "python-3.12": ["ghcr.io/…/parallax-runner-python@sha256:aaa…", "ghcr.io/…@sha256:999…"] }` in production, `{ "python-3.12": ["parallax-runner-python:dev"] }` in development and CI. At start-up, and again whenever a job names an image it does not know, the runner inspects every allowlisted reference and records its `Id` and `RepoDigests`. A job without `runtime.image` runs on the first entry. A job with it runs only when the value equals an allowlisted reference, or the `Id`, or one of the `RepoDigests` of an allowlisted reference; otherwise `image_not_allowed`. Older digests stay listed as long as replays against them should still work; in development a rebuilt `:dev` image changes its id, so a replay of a run made with the previous build ends `image_not_allowed` (terminal) and the instructor regrades instead (§9); `image_unavailable` is reserved for an allowlisted reference that cannot be inspected or pulled. `RUNNER_PULL=never` (production default) means a missing image is `image_unavailable`, never a pull at job time; `RUNNER_PULL=missing` lets development and CI pull or use a locally built tag.

## 7. Runner service (`apps/runner`)

### 7.1 Configuration

| Variable | Meaning |
| --- | --- |
| `RUNNER_DATABASE_URL` | connection as role `parallax_runner`, which has privileges in schema `pgboss_exec` only (§10.3); required |
| `RUNNER_SLOTS` | concurrent containers, default 4 (1–32); one pg-boss `work()` registration per slot with `batchSize: 1`, `pollingIntervalSeconds: 1`, `perJobResults: true` |
| `RUNNER_IMAGES` | §6.4; required |
| `RUNNER_PULL` | `never` (default) or `missing` |
| `RUNNER_DOCKER_RUNTIME` | optional OCI runtime name, `runsc` in production |
| `DOCKER_HOST` | optional; dockerode's default socket otherwise |
| `LOG_LEVEL` | pino level |

`config.test.ts` asserts the schema has exactly these keys: the runner has no `SESSION_SECRET`, no storage, mail or content configuration, and no application `DATABASE_URL`.

### 7.2 Start-up and shutdown

pg-boss is created with `schema: 'pgboss_exec'`, `migrate: false`, `supervise: false`, `schedule: false` on a pool of at most `RUNNER_SLOTS + 2` connections. `start()` then only reads `pgboss_exec.version`; if the schema or the queues do not exist yet (the server creates them, §8.4), the runner logs and retries every 10 s. Before working it removes containers labelled `parallax.runner=1` left by a crash, pings the daemon and resolves the image allowlist (§6.4). On `SIGTERM` it stops fetching, waits for running containers up to the longest wall limit + 10 s, and exits; pg-boss expiry covers anything that did not finish.

### 7.3 Container policy

`buildContainerConfig(job, image, dockerRuntime?)` and `buildHostConfig(limits, dockerRuntime?)` are pure (the OCI runtime name comes in as a parameter, read from `RUNNER_DOCKER_RUNTIME` by the caller) and unit-tested field by field, including both bounds of every limit:

```ts
{
  Image: image.ref, Hostname: 'sandbox', User: '10001:10001', WorkingDir: '/work',
  Cmd: ['python3', '/opt/parallax/harness/run.py'], Env: ['PARALLAX_JOB=1'],
  Labels: { 'parallax.runner': '1', 'parallax.job': job.jobId },
  AttachStdin: true, OpenStdin: true, StdinOnce: true, AttachStdout: true, AttachStderr: true, Tty: false,
  HostConfig: {
    NetworkMode: 'none', ReadonlyRootfs: true,
    Tmpfs: { '/work': 'rw,noexec,nosuid,nodev,size=64m', '/tmp': 'rw,noexec,nosuid,nodev,size=64m' },
    Memory: memoryMiB * 1024 * 1024, MemorySwap: memoryMiB * 1024 * 1024,   // never a shift: 2048 << 20 overflows int32
    PidsLimit: 64, NanoCpus: 1e9,
    CapDrop: ['ALL'], SecurityOpt: ['no-new-privileges'], Init: false, IpcMode: 'private',   // the harness is pid 1 (§4.4)
    Ulimits: [{ Name: 'core', Soft: 0, Hard: 0 }, { Name: 'nofile', Soft: 256, Hard: 256 },
              { Name: 'fsize', Soft: 33554432, Hard: 33554432 }],   // applied to pid 1, inherited by every child; the harness sets no rlimit (§4.3)
    LogConfig: { Type: 'none' }, AutoRemove: false, Binds: undefined, Mounts: undefined,
    Runtime: dockerRuntime,   // 'runsc' in production
  },
}
```

Seccomp is Docker's default profile. `Init: false` departs from ADR-0004's table (its pointer line names it): the harness itself is pid 1, reaps orphans continuously and kills and reaps after every check (§4.3), is unreachable by signal from inside the namespace, `SIGINT` going to its no-op handler (§4.4), and is the only process holding the container's stdout and stderr, which `docker-init` as a dumpable same-uid pid 1 would expose to student code through `/proc/1/fd/*` (§4.4, §13 item 1); `policy.test.ts` asserts the field. The job reaches the container only through the attached stdin: after `start()` the runner writes `<nonce>\n` followed by the job JSON (the same document it validated, at most 4 MiB) and ends the stream, which `StdinOnce` closes. Nothing is copied into the container (Docker refuses `putArchive` into a read-only root filesystem) and nothing is mounted from the host; the image's filesystem is the only one the sandbox has, read-only, plus the two tmpfs mounts.

### 7.4 Classification

`classify(container, frame)` is pure:

| Observation | Job status |
| --- | --- |
| exit code 0 with exactly one well-formed frame that passes `RunnerResult` | from the result, rows below; `State.OOMKilled` is then only informational, because Docker sets it whenever any process in the container was killed and the harness has already recorded that check as `error`/`memory` |
| no valid frame and `State.OOMKilled` | `resource_exhausted` |
| no valid frame and the kill timer fired | `time_limited` |
| exit code 64 | terminal `job_invalid` |
| any other exit code ≠ 0, no frame, or a frame that fails `RunnerResult` | infrastructure failure `harness_failed` / `result_missing` / `result_invalid` (§3.3) |
| result with any check `error`/`memory` | `resource_exhausted` |
| result with any check `timeout` | `time_limited` |
| result with `compileError` or any check `failed`/`error`/`skipped` | `failed` |
| every check `passed` | `passed` |

Precedence is top to bottom. The stdout stream is read with a cap of `outputBytes + 50 × 5 KiB + 64 KiB`: the captured streams of all checks together are at most `outputBytes` of encoded text (§4.3); `expected`, `actual` and `message` are not counted against `outputBytes` but are cut by encoded size to 2048, 2048 and 512 bytes, which with the name (≤ 64 characters) and the fixed keys bounds every check entry to under 5 KiB for at most 50 checks; and `compileError`, `runtime`, the top-level fields and the marker lines fit in the 64 KiB. A legitimate result therefore always fits, at the minimum `outputBytes` of 4 KiB with 50 maximal checks included (`classify.test.ts` and `frame.test.ts` cover that frame), and exceeding the cap is `result_invalid`. Only the harness can write to the stream (§4.4), so the cap is a bound on the harness, not a lever for student code.

### 7.5 Reporting, retries and dead letters

A slot that obtains an outcome first sends it as an `execution.result` message (`id: jobId` and `singletonKey: jobId` on a `policy: 'short'` queue, so a duplicate from a retried attempt is dropped while the first is still queued, the server's unique `job_id` being the guard that always holds; the fixed id lets the server find a row's message with `getJobById('execution.result', row.id)` once the run job itself is gone, §8.5; with a fixed id pg-boss 12.35.0's `send` returns `null` whenever the insert was skipped by `ON CONFLICT DO NOTHING`, that is while the first message still exists (an unworked message for its `retentionSeconds`, a worked one for its `deleteAfterSeconds`); the slot treats `null` as the dropped duplicate it is, never as an error to retry, and once the first message is gone a retried attempt inserts a fresh one, which the row's terminal state drops as the guard that always holds), then completes the `execution.run` job with the outcome as output. A transient infrastructure error throws; pg-boss retries (3 attempts, 5 s backoff) and a `GET` of the run shows it `queued` again with `infrastructureAttempts` incremented. A terminal one returns `deadletter`. Both end as a dead-letter job on `execution.failed` (configured as `execution.run`'s `deadLetter`) whose `data` is the failed job's document, `sourceOutput` the `{ kind, message }` and `sourceId` the original id (§3.3), which the server consumes with `includeMetadata: true` (§8.5). Because completed and dead-lettered pg-boss jobs keep the job document (student code and, for `full` runs, hidden checks), every `pgboss_exec` queue uses `deleteAfterSeconds: 3600`; the durable record is `execution_results`. Student outcomes are never retried: a `failed` program is a completed job. A runner that dies mid-container leaves an `active` pg-boss job that the server's supervision of `pgboss_exec` expires at `wallSeconds + 60 s`, which counts as one infrastructure attempt; pg-boss writes `{ "value": { "message": "job timed out" } }` as that attempt's output, not a runner `{ kind, message }`, and after the last attempt that is what the dead letter's `sourceOutput` carries, which the server maps to kind `expired`; any other output without a `kind` (pg-boss's `job heartbeat timeout`, a runner exception thrown without one, pg-boss's own handler-contract errors) is kind `unknown` (§8.5).

### 7.6 Logging

Structured logs carry `jobId`, `runtimeId`, `imageId`, `status`, `durationMs`, `retryCount` and infrastructure error kinds. They never carry file contents, check definitions, captured output, `expected`/`actual` or the nonce; `log.test.ts` serialises a job and an outcome through the logger's redaction and asserts none of those strings appear.

## 8. Server side (`apps/server`)

### 8.1 Code question definition

Part of the test resource revision content (P3-15 defines the test; P3-18 edits it). The fields the runner path depends on, `codeTask.v1`:

```ts
{ kind: 'code', id: string, runtime: RuntimeId, prompt: …,
  files: [{ path, content, encoding?, editable: boolean, hidden: boolean }],   // editable files are the student's; hidden ones never leave a full run
  allowedPackages: string[],            // shown; validated against RUNNER_RUNTIMES[runtime].packages at publication
  limits?: { wallSeconds?, memoryMiB?, outputBytes? },      // clamped to RUNNER_BOUNDS at publication and at enqueue
  checks: [Check & { points: number }] }                     // Check as in job.schema.json; points are for grading, never sent
```

Publication validation (P3-18) rejects: an unknown runtime, a package outside the runtime, limits outside bounds, duplicate check names, no public check, a check naming a file that is not in `files`, a public check naming a hidden file, a file path that is a directory prefix of another (`data` beside `data/sample.csv`, §3.1 rule 4), a file that is both editable and hidden, and a hidden check whose files do not parse. It warns, without rejecting, when every hidden check of a question is a `script` check, because a `script` check's verdict is decided inside the student's process and the question then has no cheat-resistant hidden check (§3.1, §11); the warning names the `call` and `stdio` kinds as the remedy. It also runs the author's hidden checks in the instructor preview context so a broken hidden test is found before students meet it.

### 8.2 `buildRunnerJob` and hashes

`buildRunnerJob(question, snapshot, set, jobId, replayImage?)` is pure and tested: it overlays `snapshot.files` (only paths marked `editable` are accepted; others are rejected with 400) on the question's files, keeps the checks whose `visibility` the `set` allows (`public` → public only; `full` → all) and strips `points`, drops hidden files from a `public` job, copies `hidden` onto the files of a `full` job, clamps limits, and validates the result with `RunnerJob` and `validateJob` (§3.1). A `public` job therefore contains no hidden check and no hidden file, which `job-builder.test.ts` and `a12-execution-contracts.itest.ts` assert.

- `codeHash = sha256(canonical(snapshot.files))` where canonical is the JSON of `[{ path, content, encoding }]` sorted by path. It names the student's work only; the UI compares it with the editor's content for the stale label (A12).
- `graderVersion = sha256(canonical({ protocol: 1, runtimeId, image, harnessVersion, checks: question.checks, files: non-editable files, limits })).slice(0, 16)` where `image` is the runtime's `digest` from `RUNNER_RUNTIMES`, or its configured image reference where no digest exists (development, CI). It is computed before the run, so it can serve the reuse key, the job row and the attempt's pinned grader version; in production a digest pins the image exactly, while in development a rebuilt `:dev` image keeps the same grader version and reuse is correspondingly weaker. The image id the runner actually used is recorded on the result (§8.3) and is what a replay pins (§9).

### 8.4 Two pg-boss instances; enqueueing

The application keeps its scoped jobs (P1-07) in schema `pgboss`. Everything the runner touches lives in a second schema, `pgboss_exec`, served by a second `PgBoss` instance on the same pool (`createBoss(pool, { schema: 'pgboss_exec', role })`): queue `execution.run` (`policy: 'standard'`, `retryLimit: 3`, `retryDelay: 5`, `retryBackoff: true`, `expireInSeconds: 120`, `deleteAfterSeconds: 3600`, `deadLetter: 'execution.failed'`), `execution.result` (`policy: 'short'`, `retryLimit: 5`, `retryDelay: 2`, `retryBackoff: true`, `deleteAfterSeconds: 3600`) and `execution.failed` (`policy: 'standard'`, `deleteAfterSeconds: 3600`). Both API and worker create the three queues at start-up (idempotent); the runner never creates queues because that needs DDL. The per-user count behind the cap crosses classes, so `db/scoped.ts` gains `forOwnRows(user, table)` (`WHERE user_id = user.id`, taking the resolved `ClassScope`'s user, never a raw id, and returning only rows that user owns) and its introspection test lists the tables that allow it, `execution_jobs` being the first and, until another item needs one, the only. This is a deliberate, recorded exception to ADR-0002's rule that a class-scoped table is read only through a `ClassScope`: the cap is a property of the student, not of a class, and a per-class count would let a student hold two runs in every class at once. The exception is narrow by construction (a user's own rows, selected by the user of a scope that was resolved for the request; the helper cannot name another user and cannot be used from a route without a resolved scope) and it is **read-only**: the cap counts the rows and writes nothing through the helper; settling a row (§8.5) happens only on a read of that row under its own class scope or in the worker's handlers. ADR-0002 records the exception in its pointer to this section, so a reviewer of P3-16 finds the rule and the exception in the same place. The runner role's privileges stop at `pgboss_exec` (§10.3), so a compromised runner can neither read the actor-bearing scoped jobs in `pgboss` nor enqueue one.

Only `apps/server` sends `execution.run`, and only from code that holds a resolved `ClassScope` for the attempt's class. The payload is a `RunnerJob`, not a scoped-job payload: the runner cannot re-resolve membership, so authorisation is complete before `bossExec.send` and is repeated on every read (§8.6). The result and failed handlers are likewise plain `bossExec.work(...)` registrations in worker mode, not `defineScopedJob`s: their messages come from the runner and name no actor. `jobs/scoped.test.ts` asserts that no `*.job.ts` module defines `execution.*` jobs, keeping the exception explicit.

Cancellation: `POST …/runs/:runId/cancel` by the run's owner, for `reason = 'sample'` runs only (any other run of the attempt is 404, as for the student `GET` routes, so a student who learns a grading run's id cannot cancel it), cancels a `queued` job (`bossExec.cancel`) and marks it `cancelled`; a `running` job answers `409 { error: 'running' }` and runs to its bounded end. Submission and expiry of an attempt cancel its queued sample runs.

### 8.5 Result and failure handlers (worker mode)

| Message | Handler |
| --- | --- |
| `execution.result` `RunnerOutcome` | validate; load the `execution_jobs` row by `outcome.jobId` (unknown id → throw, so pg-boss retries the message a few seconds later in case the row's transaction has not committed; after the message's retries it is failed and logged); then `recordOutcome(row, outcome, bossJob)`: insert `execution_results` (`job_id` unique: a duplicate is completed without effect); set `state = outcome.status`, `finished_at`, and `started_at`/`infrastructure_attempts` from `bossExec.getJobById('execution.run', boss_job_id)` (`startedOn`, `retryCount`; both left null when that job is already gone, see the `no job` row below). `recordOutcome` moves only a row that is still `queued`/`running`: a row already terminal (settled from the job at read time, cancelled, or `enqueue_failed`) is left as it is and the message is completed without effect |
| `execution.failed`, worked with `includeMetadata: true`: `data` is the failed `RunnerJob`, `sourceOutput` the failed job's `output`, `sourceId` the original `execution.run` id | load the row by `data.jobId` and check `boss_job_id = sourceId` (always set, §2 step 4; a mismatch is a stale or forged dead letter, logged and completed without effect); then `recordFailure(row, output)`: set `state = 'infrastructure_error'` and `failure = { kind, message }` mapped from the output (below), `finished_at`, and for a `reason: 'grading'` run move the attempt to NeedsReview (§8.7). `recordFailure` is idempotent and owns the NeedsReview move, whichever caller reaches the row first: a row already `infrastructure_error` is left as it is, NeedsReview included, with one refinement: a dead letter for a row whose `failure.kind` is `lost` replaces `failure` with the real kind and message, state and attempt untouched, so a read that recorded `lost` while the dead letter waited does not hide the runner's kind from operators for good |

**Failure output mapping** (`recordFailure`, into `failure`): a job the runner failed carries the runner's thrown error serialised by pg-boss (`serialize-error` keeps own properties), so `output.kind` is one of §3.3's kinds and `output.message` its message, and both are kept. A job pg-boss itself expired (a runner that died mid-container, §7.5) carries exactly `{ "value": { "message": "job timed out" } }`, the string pg-boss 12.35.0 writes in `expireJobsDistributed`; that output, and only that one, maps to kind `expired`. Every other output without a known `kind` maps to kind `unknown` with `output.value?.message ?? output.message ?? JSON.stringify(output)` cut to 512 bytes as the message: pg-boss's `{ "value": { "message": "job heartbeat timeout" } }`, a runner exception thrown without a `kind` (serialised as `{ name, message, stack }`) and pg-boss's own handler-contract errors (`perJobResults handler must resolve with an array of job results`, `no disposition returned by handler`) are runner or contract bugs, and an operator who reads `unknown` with the serialised message looks for the bug instead of a dead runner. So a row never lacks a kind, and `expired` never names anything but a timeout. Both `recordOutcome` and `recordFailure` live in `execution/results.ts` and are the only writers of a row's terminal state besides cancellation.

Read-time state for a non-terminal row: `GET …/runs/:runId` calls `bossExec.getJobById('execution.run', boss_job_id)` and reports `queued` for `created`/`retry` (with `queuePosition`, §5, from one count query on `pgboss_exec.job`) and `running` for `active`. **Staleness rule** (`execution/status.ts`), the one statement of it in this document (§2 step 3 and §5 point here), by the state of the pg-boss job, which `getJobById` returns together with `output`, `startedOn` and `completedOn`. The read path looks one job up with `getJobById`; the cap evaluates the first column for all of a student's rows with one statement, `SELECT id, state FROM pgboss_exec.job WHERE name = 'execution.run' AND id = ANY($1)` over their `boss_job_id`s (§2 step 3), the second and last statement the server runs directly against `pgboss_exec` (§13 item 4); the dead-letter queue is never queried by `sourceId`, which is why the `lost` row below ends with a later replacement of `failure` rather than a lookup. The first column decides whether a row is **live** (counted by the cap, reported `queued`/`running`); the second says how a read of the row under its own class scope **settles** a row that is not live. The cap never settles (§2 step 3, §8.4):

| Job | Live? | Settlement on read |
| --- | --- | --- |
| `created`, `retry`, `active` | yes, whatever the row's age | none; `queued` or `running` |
| `completed` | no | the job's `output` is the `RunnerOutcome` the runner completed it with (§7.5): `recordOutcome` (above), so a result whose `execution.result` message is still in flight, or whose worker is down, is recorded from the job itself and the message is then the duplicate; an `output` that fails `RunnerOutcome` validation (the runner never completes with one, so this is corruption) → `recordFailure` with kind `result_invalid` |
| `failed` (terminal; a retriable failure is `retry`) | no | `recordFailure` with the failure output mapping above, NeedsReview move included for a grading run, so an instructor's `GET …/results` that lands before the dead letter is worked produces the same row and attempt state the handler would |
| `cancelled` | no | row state `cancelled`: a cancel route, a supersede or an attempt's expiry ran `bossExec.cancel` and died before its row update; the student cancelled this run and is not told it was unavailable |
| no job for the row's `boss_job_id`, `job_sent_at` null (the send has not returned, or the process died between the send returning and the `job_sent_at` update) | within 60 s of `queued_at`: yes (the send follows the commit at once, §2 step 4, and may still be in flight; reported `queued` without a `queuePosition`); after it: no | first `getJobById('execution.result', row.id)` exactly as in the row below, because the job may have run after all (the send returned and the process died before marking the row; the job then ran, completed and was deleted an hour later with the worker down) and a message in any state settles the row from its `data`. Without a message, `recordFailure` with kind `enqueue_failed` through `UPDATE … WHERE id = … AND state = 'queued' AND job_sent_at IS NULL`: the process died between commit and send. When that update touches no row the send landed meanwhile and the row is reported `queued`; when it moved the row, the read path commits and then calls `bossExec.cancel('execution.run', boss_job_id)`, a no-op while the job does not exist yet (§2 step 4). This is the only place a wall clock enters the rule, and it measures a local send, never the queue wait. A send that outlasts the window finds its own conditional update of `job_sent_at` touching no row and cancels the job it created; exactly one of the two updates wins, and whichever side loses still cancels by id, so a settled row is never flipped and a job never runs for one |
| no job for the row's `boss_job_id`, `job_sent_at` set (the job existed and was deleted `deleteAfterSeconds`, 3600 s, after it completed or failed) | no | first `getJobById('execution.result', row.id)`: the runner sends the row's result message with `id: jobId` (§7.5), and an unworked message waits for its `retentionSeconds` (14 days), so a row whose handler never ran (a worker outage longer than an hour, nobody reading the row) still has its message, and a message in any state settles the row from its `data` through `recordOutcome` (with `started_at` and `infrastructure_attempts` left null): a finished run is never shown as **Run unavailable**. Without a message, `recordFailure` with kind `lost`. The one case this cannot name is a run job that failed terminally and was deleted before its dead letter was worked (the server worker down for over an hour): the row is `lost` with the same student-visible outcome (`infrastructure_error`, NeedsReview for a grading run), and the dead letter, which waits on `execution.failed` for its own `retentionSeconds`, replaces `failure` with the real kind when it is finally worked (§8.5 handler table) |

The rule never presumes: a finished job is settled from what it carries, so a worker outage delays results without ever showing **Run unavailable** for a run that succeeded, and `recordOutcome` and `recordFailure` move only non-terminal rows, so nothing settled is flipped later. A job in `created` is live however long it has waited, so a student whose run sits behind a class-wide queue is neither told **Run unavailable** nor locked out of the cap. No server process polls or joins pg-boss tables; the server's only SQL against `pgboss_exec` is that count and the cap's lookup of job states by id (§2 step 3).

### 8.6 Contracts

All under `/api/classes/:classId/attempts/:attemptId/…` with class scope; students only for attempts they own, instructors for the class. Responses include a `queuePosition` while queued.

| Route | Scope | Behaviour |
| --- | --- | --- |
| `POST …/questions/:questionId/runs` `{ files }` | student (own attempt, attempt `in_progress`) | §2 steps 2–4: `200` reused run of this attempt, `202` with the row's actual `state` (`queued` in every ordinary case; the terminal state when a cancel, a read or a result settled the row during the send, §2 step 4, so the response schema admits every `state`), `429` cap, `400` non-editable path or oversize |
| `GET …/runs/:runId` | student owner (`reason = 'sample'` runs only, else 404), instructor | student view below; instructors get the full outcome |
| `GET …/questions/:questionId/runs?latest=1` | same | the latest run for the question; for a student the latest `reason = 'sample'` run, so a grading run never reaches `toStudentView` (restores the panel after reload) |
| `POST …/runs/:runId/cancel` | student owner (`reason = 'sample'` runs only, else 404) | §8.4 |
| `POST …/questions/:questionId/replays` `{ reason: 'replay' \| 'regrade', note }` | instructor | §9; `202` with the new run id |
| `GET …/results` | instructor | every result of the attempt, hidden checks included |

**Student view.** `toStudentView(job, outcome)` accepts only `check_set = 'public'` jobs (anything else is a programming error that throws) and returns `{ runId, state, codeHash, queuePosition?, queuedAt, startedAt?, finishedAt?, result?: { status, runtime, compileError?, checks: PublicCheck[], truncated, durationMs } }` where `PublicCheck` is the check result **without** any `visibility` field. Because a `public` job carries no hidden check and no hidden file, nothing in its outcome can contain hidden material. A `full` outcome is different: its public checks ran in the same container as hidden ones (§4.3), so every field of it, the public checks' `stdout`, `stderr`, `actual` and `message` included, may be shown to a student only when the release policy permits hidden details. Grading results therefore reach students only through released grades (P4-01, P4-04), never through these routes. The zod response schema is `.strict()`, and `a12-execution-contracts.itest.ts` asserts structurally that no key in the student response schema (recursively) matches `/hidden|visibility|points/i`, that a job built with `set: 'public'` contains no hidden check and no hidden file, that the student `GET` and cancel routes return 404 for a `full` run of the student's own attempt and `?latest=1` never selects one, and that a stored `full` outcome rendered for an instructor still shows hidden checks.

### 8.7 Grading runs

On submission (P3-15's `submitAttempt`), P3-16 enqueues one `full` run per code question with `reason: 'grading'`, priority 5, against the attempt's pinned question revision. Its result is the automated component the grading item (P4-01) reads: points of passed checks over points of all checks, per question. An `infrastructure_error` on a grading run after retries moves the attempt to NeedsReview with the failure visible to the instructor, who can trigger a replay; the move belongs to `recordFailure` (§8.5), so it happens whichever caller settles the row first, the dead-letter handler or a read of the row; the student's attempt is not consumed and their view shows nothing about it (A18).

## 9. Replay and regrade

| | Replay | Regrade |
| --- | --- | --- |
| Purpose | run the identical grading again (lost result, infrastructure failure, audit) | grade with a changed runner image or harness |
| Image | pinned: `runtime.image` = the original result's `image_digest`, or its `image_id` where no digest exists (dev, CI); the runner must still allowlist it (§6.4), otherwise `image_not_allowed` and the instructor is told to regrade instead | current image for the runtime |
| Checks, limits, code | the attempt's pinned question revision and the job's stored `snapshot`, unchanged | same |

Grade overrides (P4-01) reference a result row and keep it, so a regrade never hides the result a grade was based on. `a18-run-unavailable.itest.ts` exercises a replay in CI against the `:dev` image by its id.

### 10.3 Database role

`scripts/runner-role.sql` (P3-13), adopted by P3-16's migration with `:app_role` substituted by the role that runs pg-boss (the migration reads it from `DATABASE_URL`; the script takes it as a `psql` variable):

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'parallax_runner') THEN
    CREATE ROLE parallax_runner NOLOGIN;
  END IF;
END $$;
CREATE SCHEMA IF NOT EXISTS pgboss_exec;
GRANT USAGE ON SCHEMA pgboss_exec TO parallax_runner;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA pgboss_exec TO parallax_runner;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA pgboss_exec TO parallax_runner;
ALTER DEFAULT PRIVILEGES FOR ROLE :app_role IN SCHEMA pgboss_exec
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO parallax_runner;
ALTER DEFAULT PRIVILEGES FOR ROLE :app_role IN SCHEMA pgboss_exec GRANT USAGE ON SEQUENCES TO parallax_runner;
ALTER ROLE parallax_runner SET statement_timeout = '30s';
```

No statement touches `public` or `pgboss`: the role never receives a grant there, and the application's tables carry no `PUBLIC` grants, so `USAGE` on `public` through `PUBLIC` reaches nothing (asserted by the test below rather than by a `REVOKE` that would not take effect). The default-privilege statements name the application role explicitly because the queue partitions are created later by pg-boss running as that role, which may differ from the role that runs migrations. `CREATE ROLE` needs `CREATEROLE` and the default-privilege statements must run as `:app_role` or a member of it. In development and CI the connection is a superuser and the migration does everything. In production operators run `scripts/runner-role.sql` before `pnpm db:migrate` under a role that may create roles; the migration's `IF NOT EXISTS` then skips creation, and the migration itself runs as the application role (or a member of it), which the default-privilege statements require. Operators give the role a password and `LOGIN` out of band (`ALTER ROLE parallax_runner LOGIN PASSWORD …`, `CONNECTION LIMIT` = slots × processes + 4). pg-boss's worker path needs exactly these rights: `fetch` and `complete` update `pgboss_exec.job`, `send` inserts into it, `fail` deletes and re-inserts the row, `start()` with `migrate: false` reads `pgboss_exec.version` and `pgboss_exec.queue`.

`a13-runner-role.itest.ts` (P3-13) applies the script in its own `beforeAll` against its cloned test database with `:app_role` = the connection's role, grants itself membership (`GRANT parallax_runner TO current_user`, allowed because the creating role holds `ADMIN OPTION`), `SET ROLE parallax_runner`, and asserts: `SELECT` on `users` and `resource_revisions` is denied; `SELECT` and `INSERT` on `pgboss.job` are denied; `SELECT` on `pgboss_exec.version` succeeds. P3-16 extends it with `execution_results` once that table exists.

### 10.4 Deploy and operate

Deploy builds the images, pushes them by digest, updates `RUNNER_RUNTIMES` and `RUNNER_IMAGES` together (keeping the previous digest in `RUNNER_IMAGES` for replays), pulls on the runner host, and restarts the runner. A smoke job runs `job-sample-python.json` through the real path after each deploy. Metrics worth exporting: queue depth and oldest `created` job age on `execution.run`, outcomes per status, `execution.failed` kinds, container duration percentiles.

## 11. Threat model and controls

| Threat | Control | Asserted by |
| --- | --- | --- |
| student code reaches platform credentials or data | no network, no secrets in the container, runner role limited to `pgboss_exec`, payload without identities | `A13 environment holds no secrets`, `A13 network connect and DNS fail without a route`, `A13 runner role cannot read application tables or the application job queue` |
| escape via kernel or daemon | `CapDrop ALL`, `no-new-privileges`, read-only root, no mounts, non-root uid, default seccomp, gVisor in production | policy unit tests; `A13 host files are unreadable and the root filesystem is read-only` |
| resource exhaustion | memory and swap limit, pids limit, 1 CPU, tmpfs sizes, `RLIMIT_FSIZE`, wall budget and kill timer, output caps | `A13 infinite loop ends time_limited within the budget`, `A13 one gibibyte allocation ends resource_exhausted`, `A13 fork bomb hits the pids limit and ends failed`, `A13 ten mebibyte print is truncated at one mebibyte` |
| forged or corrupted result | nonce from stdin, non-dumpable harness, exit-code check, single frame, zod validation, size cap, leftover processes killed before the frame | `A13 result forged on container stdout is ignored`, `frame.test.ts`, `A13 killed harness ends run unavailable, not passed` |
| run sabotaged through the container's stdout or stderr descriptor (over-cap bytes or bytes glued to the marker line → `result_invalid`/`result_missing` on every attempt; student text in `harnessLog`) | the harness is pid 1 and non-dumpable, so no other process holds those descriptors and `/proc/1/fd/1`, `/proc/1/fd/2` are not openable by student code; children get `/dev/null` and harness-owned pipes; the harness writes a newline before the marker and the runner treats bytes outside the frame as noise | `policy.test.ts` (`Init: false`), `A13 writing to the container's stdout through pid 1 is refused and the result is still read` |
| hidden checks or hidden files reach the student | `set: 'public'` jobs contain no hidden check and no hidden file; the job lives only in the harness's memory; public checks never see a hidden file on disk; student routes (`GET`, `?latest=1`, cancel) serve only `reason = 'sample'` runs; a `full` outcome is released only under the release policy; strict response schemas | `a12-execution-contracts.itest.ts` structural tests; `job-builder.test.ts`; harness test `public check sees no hidden file` |
| hidden material carried from a hidden check to a public check of the same `full` job (a file stashed anywhere under `/tmp`, `/work` or `/dev/shm`, a pre-created check directory, a lingering process; System V IPC objects remain a residual) | private `TMPDIR`/`HOME` per check, kill-and-reap and a sweep of everything under `/work`, `/tmp`, `/dev/shm` and `/dev/mqueue` after every check and after the compile phase; and every field of a `full` outcome is treated as hidden until release | harness test `nothing under a swept root survives a check` (a hidden check's program copies its hidden file to `/tmp/stash` and `/dev/shm` and pre-creates the next check directory; the following public check finds none of it) |
| hidden `call`/`stdio` expectations used as an oracle by the code under test | `expected` and `compare` never leave the harness process; the driver receives only the call | harness test `driver stdin carries no expected value` |
| a `script` check's verdict decided by the code under test (the student's module runs at import time, so `os._exit(0)` conditioned on the hidden test's presence passes the check without an assertion running; the test file is readable by the process that runs it) | inherent to in-process tests, which cannot be made cheat-proof: `script` is the weakest kind; hidden `call`/`stdio` checks, whose expectations exist only in the harness, are the strong kind; publication validation warns when a question's hidden checks are `script`-only (§8.1); the script is materialised for its own check only and its stdout is hidden from students; instructor review | documented here; P3-18 test `publication warns on script-only hidden checks` |
| a compromised runner role acts as a user | the role has no privilege in `pgboss` (where scoped jobs carry `actorId`) or on application tables; results only create result rows | `A13 runner role cannot read application tables or the application job queue` |
| denial of service by one student | per-student cap, supersede rule, priorities, bounded wall time | `a13-run-cap.itest.ts` |
| student cheats a `call` check by faking its outcome file | out of scope for the sandbox: equivalent to returning the right value, which passes only a check whose expected value the student already knows; hidden `call`/`stdio` checks with expectations held only by the harness, and instructor review, are the controls (`script` checks are not, row above) | documented in §4.5 |
| harness sabotaged (killed or interrupted) by student code | the harness is pid 1: signals sent to it from inside the namespace are discarded unless it has a handler, and it replaces Python's `SIGINT` handler with a no-op one before any child runs (§4.4); a harness that does die (only from the host) ends `harness_failed` → Run unavailable after retries, never `passed`; bounded by three attempts | harness test `student code sending SIGINT to the harness does not interrupt it`; `A13 signals from student code to pid 1 are discarded`; `A13 killed harness ends run unavailable, not passed` (killed from the host with `docker kill -s KILL`, the only way it can be killed by signal; student code can end it only indirectly, through the OOM killer choosing pid 1, which §7.4 classifies) |

## 13. Decisions and deviations from ADR-0004

1. **Job over stdin, result over stdout.** ADR-0004 uploaded the bundle with `putArchive` and read `/work/result.json` with `getArchive`. Neither works under its own policy: Docker refuses to copy files into a container whose root filesystem is read-only, a tmpfs is not mounted until start, and nothing on a tmpfs survives exit. The job (files inline, ≤ 4 MiB) therefore follows the nonce on the attached stdin and is held only in the harness's memory, and the harness prints one nonce-framed result document to stdout (§4.2, §4.4, §7.3). Everything in the ADR's policy table is kept except `Init`, which is `false`: with `Init: true`, `docker-init` is a dumpable pid 1 of the sandbox's uid holding the container's stdout and stderr, so student code could write through `/proc/1/fd/1` and `/proc/1/fd/2`; the nonce keeps a forged result out, but over-cap or glued bytes would still turn every attempt of a run into an infrastructure failure and student text would reach `harnessLog`. With the non-dumpable harness as pid 1 nobody else holds those descriptors, and signals from inside the namespace are discarded, `SIGINT` going to a no-op handler (§4.4). What `docker-init` did, the harness takes over: its wait loop reaps orphans as they die, and it kills and reaps after every check (§4.3, §4.4, §11). ADR-0004 carries a one-line pointer to this document that names `Init: false`.
2. **Harness baked into the image, one harness for both languages.** The ADR uploaded the harness with the bundle and foresaw a harness per language. Baking it in binds harness and image into one digest; a Python harness with an R driver removes an R-side JSON and process-control implementation.
3. **Three check kinds.** `script` is added to the ADR's `stdio` and `call` so authors can write hidden tests that need more than one comparison without a test framework in the image. It is a convenience, not a control: its verdict is decided inside the student's process, so it is the weakest kind, and publication validation warns when a question's hidden checks are `script`-only (§3.1, §8.1, §11).
4. **Separate pg-boss schema and result queues.** The runner's role is confined to `pgboss_exec`, a second pg-boss schema that holds only `execution.run`, `execution.result` and the dead-letter queue `execution.failed`, so it can neither read nor enqueue the actor-bearing scoped jobs of P1-07 in `pgboss`. Outcomes travel back as `execution.result` messages consumed by the server worker through pg-boss's own work loop; infrastructure failures arrive as pg-boss dead letters, which carry the failed job's document with the failure in `sourceOutput`. The server never polls pg-boss tables and never joins them with its own: `queued`/`running`/`lost` are read-time lookups through `bossExec.getJobById`, and the server's only SQL against `pgboss_exec` is the count query on `pgboss_exec.job` behind `queuePosition` and the cap's lookup of job states by id (§2 step 3, §8.5), neither with a join. The trade-off accepted is a second `PgBoss` instance on the server, one more schema in the migration, and two standing exceptions to ADR-0002 recorded there with a pointer to §8.4: the scoped-payload rule (the `execution.*` queues carry no actor) and the scoped-table rule (`forOwnRows` counts a user's own `execution_jobs` across classes for the cap).
5. **Check `skipped` status, `errorKind`, `compileError`.** Added so compile errors, runtime errors, timeouts and memory kills are distinguishable as spec §11 requires.
6. **Order of items and test layout.** P3-14 (harness and image) precedes P3-13 (worker) so the A13 probes run against the real harness in CI; the `runner` CI job is created by P3-14 and extended by P3-13. The Docker suites live in their own vitest project `runner` rather than inside `integration` as ADR-0006's table has it, so the `integration` job never waits for an image build; the `integration` project excludes `**/*.docker.itest.ts`, because its include glob `apps/runner/test/**/*.itest.ts` would otherwise match them too and run them in a CI job that has Docker but not the image. P3-13 adds the one-line amendment to ADR-0006 when it creates the project.
7. **Sample-run reuse within an attempt.** Identical (attempt, question, code hash, grader version) public runs return the existing run of that attempt; runs are never shared across attempts or students, and a replay always runs.
8. **Priorities and cap scope.** The cap of two applies to sample runs only; grading runs are system work at lower priority than interactive runs.
9. **File visibility and the `full`-job rule.** Question files carry `hidden`; a `public` job contains no hidden file, a public check never sees one on disk, and a hidden check sees only the hidden files it declares; each check has a private temporary directory and is followed by a kill-and-reap and the sweep of §4.3 over every root it names. The driver never receives `expected`, so a `full` run's hidden expectations exist only in the harness's memory. Only a `public` job's outcome is free of hidden material; a `full` outcome, public checks included, reaches students only under the release policy.
