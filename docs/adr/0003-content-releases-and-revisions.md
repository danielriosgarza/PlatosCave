# ADR 0003 — Content releases, resource revisions and annotation anchors

**Status:** Accepted, 2026-09-30. Amended 2026-10-13 (P5-04, owner decisions in issue #559): conversion from a folder: identity, provenance and which side wins; see **Amendment: Conversion from a folder** below, which [docs/design/course-folder.md](../design/course-folder.md) refines.

## Context

A course holds reusable material; a class pins one immutable release (§1, §12, §13). Drafts autosave with revision-conflict detection; publication validates and snapshots; adoption shows changed resources and affected anchors; started tests stay pinned to their original question and grader revisions; removing a resource never deletes work submitted against it (§12). Annotations record the resource revision and a stable anchor; a new revision maps marks confidently or shows **Needs reattachment** with the original context (§8, A06). Slides remember position per deck revision and preserve old annotations until mapped (§7). Study positions are keyed by resource revision (§13).

## Decision

**Drafts are mutable, revisions and releases are immutable.**

- `topics` and `resources` are draft rows owned by a course. Each has an integer `revision` used for optimistic checks: mutations send `expectedRevision`; a mismatch returns 409 with the server copy so the editor can show a conflict view rather than overwrite (§12).
- Every content change to a resource inserts a `resource_revisions` row: `id`, `resource_id`, `type` (slides_pdf, slides_web, reading_native, reading_pdf, exercise, notebook, shiny, test), `content` (JSON: type-specific definition; for native readings the Markdown or HTML source, inline or as an uploaded object, and its image names; for tests the questions **including hidden checks**), `object_keys` (storage objects, content-addressed `courses/{courseId}/objects/{sha256}`), `derived` (conversion outputs and their `status`; for a native reading the sanitised `html`, `blockMap` and `figures`, for a PDF reading `pageCount` and `pages`, all written by the `reading.ingest` job), `accessible_alternative`, `provenance`, `content_hash`, `created_by`, `created_at`. `resources.head_revision_id` points at the newest. Revisions are never updated except `derived` (written by conversion jobs) and are never deleted while referenced.
- `course_releases` (`course_id`, `version` sequential per course, `created_by`, `validation_report`, `created_at`) with child tables `release_topics` (order, title, objective, prerequisites, completion rule, estimated time) and `release_resources` (`release_topic_id`, `resource_id`, `resource_revision_id`, tab, order, visibility, release date). A database trigger rejects `UPDATE`/`DELETE` on these three tables; archiving a release is a column on `courses`-level history, not a row change.
- `classes.release_id` is the adopted release; `class_release_history` records every adoption (actor, from, to, diff summary). Adoption diff = join of the two releases' `release_resources` by `resource_id`: added, removed, changed revision; plus counts of annotations and assignments referencing changed or removed revisions.
- `assignments` reference `release_resource_id` and `resource_revision_id`; `test_attempts` copy `question_revision_id` and `grader_version` at start, so later releases cannot alter an attempt (A16).
- Reads for a class always go `class → release → release_resources → resource_revisions`; class routes never see draft rows (A26), except through a `DraftPreviewScope`. Starting an instructor preview is a course `editor` route (`startPreview`, `db/preview.ts`) that also requires the caller to teach the class. Reads during the preview go only through the preview principal's class scope (ADR-0002), never the course scope: the scope resolver admits a draft preview only while its owner still owns or edits the course, and a class-scoped function narrows the scope with `isDraftPreview` (`DraftPreviewScope`) to read draft rows through `forDraftCourse` (`db/scoped.ts`, `db/content/releases.ts`).

**Publication** runs a validation report (broken references, missing accessible alternatives or transcripts, invalid grading rules, execution configuration outside server bounds, unconverted decks). Errors block; warnings are stored in the report. Publishing is an explicit `course:publisher` action recorded in `audit_events`.

**Anchors** are JSON values with a `kind` discriminator, validated by zod in `packages/contracts/src/anchors.ts`:

| kind | fields | produced by |
| --- | --- | --- |
| `text` | `blockId`, `start`, `end` (code-unit offsets in the block's text content), `quote`, `prefix`, `suffix` (≤ 32 chars each) | native readings, web slides |
| `pdf` | `page` (0-based), `rect` `{x,y,w,h}` normalised 0..1, optional `quote`, optional `strokes` (sketch on the page) | PDF readings and decks |
| `slide` | `page` | slide notes/discussion |
| `figure` | `figureId`, `strokes` (drawing) | sketches on native figures |
| `none` | — | general topic notes |

Reading ingestion (ADR-0001 pipeline) assigns every block element a stable `blockId` = first 12 hex of `sha256(normalisedText + ':' + occurrenceIndex)` recorded in `derived.blockMap`; unchanged paragraphs keep their id across revisions. A block whose text lies entirely in nested blocks (a blockquote or loose list item wrapping paragraphs) only wraps them and gets no id, so it never takes an occurrence from the paragraph it repeats. Block maps written before this rule may still carry ids on wrappers; an anchor on one has no matching block in the next revision and goes through quote matching, which places it in the wrapped paragraph that holds its quote or leaves it for reattachment. Zoom, reflow and Focus never touch anchors because anchors reference blocks and normalised page space, not pixels.

**Placement per revision.** `annotations` store the original `resource_revision_id` and `anchor`. `annotation_placements` (`annotation_id`, `resource_revision_id`, `anchor`, `status` ∈ mapped | needs_reattachment | manual, `confidence`) hold the anchor for each revision a class actually uses. When a class adopts a release with a changed revision, a job maps each annotation: exact `blockId` + quote match → `mapped` (1.0); else quote with prefix/suffix search across blocks, accepting a unique match with normalised similarity ≥ 0.9 → `mapped` with that confidence; else `needs_reattachment` retaining the original quote and context. PDF anchors map when the page count and page text hash match, otherwise need reattachment. A `manual` placement is set by the reader who may place the mark: only the author can reattach an annotation (private notes are never visible to instructors, spec §8 and §17), while a thread can be placed by an instructor, who can read it, or by its author; until then the original quote is shown (A06).

**Study positions** (`user_id`, `class_id`, `resource_revision_id`, tab, position JSON, layout) are upserted per resource revision; a new revision starts from the mapped block when available.

## Consequences

- Storage grows with every draft edit; objects are content-addressed so unchanged files are not duplicated, and a later retention job can prune unreferenced draft revisions.
- Hidden test content lives in revisions; student-facing contracts use response schemas without those fields (structural, tested in P3-16).
- Anchor mapping is heuristic; the threshold is a constant in one module with unit fixtures so it can be tuned.
- The immutability trigger makes mistakes loud: fixing a published typo means a new release, as the spec intends.

## Alternatives considered

- **Mutable releases with "last modified" stamps**: violates A16/A26 and makes anchors ambiguous.
- **Copy-on-publish of every file**: unnecessary with content addressing.
- **Character-offset anchors on the whole document**: break on any edit; block ids plus quote context are the standard (Hypothesis-style) approach.
- **Storing anchors only once and remapping on read**: too slow and non-deterministic; per-revision placements are explicit and auditable.

## Amendment: Conversion from a folder (P5-04, 2026-10-13)

**Context.** N4 and N5 (spec §13) ask that a folder of files becomes the material the editor produces, and that converting it again keeps notes, highlights and attempts attached. The owner's answers Q12 to Q16 (plan §8) say where conversion runs, where metadata and ids live and which side wins. This amendment adds a second way to write drafts. It reverses nothing in the Decision: drafts stay mutable, revisions and releases stay immutable, publication validates and snapshots, and adoption compares releases by `resource_id`.

**Folder.** A course folder holds `course.yaml` (the title, and whether the tree is public) and one folder per topic with `topic.yaml` and the five tab folders. `topic.yaml` holds what the editor records beside a file: the topic's position, title, objective, estimated time, prerequisites and completion rule, and each resource's file, title, visibility and accessible alternative. Content files carry no front matter, so the bytes stored are the file's bytes. An exercise or a test is a YAML file that is parsed to a JSON value and checked by `exerciseV1` or `testV1`; the schema's result is stored; a code file's content is read from the file beside the definition. No field, question kind or stored format is added.

**Identity.** Each topic and each resource has an `id` in `topic.yaml`, a UUID that `parallax check --write-ids` writes once on the author's machine; no other command writes into a course folder. The id belongs to the entry, so a rename, a move to another topic or a new order keeps it, and prerequisites and completion requirements name ids. A course is identified by the account that owns its instructor folder and the name of the course folder. Database ids follow by derivation, and nothing is stored to map them: `courses.id` is the version 5 UUID of `<owner account id>/<folder name>` in the namespace `0b6a98fa-33c2-51ab-9808-310d3f212845`, and `topics.id` and `resources.id` are the version 5 UUIDs of `topic:<id>` and `resource:<id>` in the namespace of the course's id. The same folder reaches the same rows on every conversion, a copied course folder reaches rows of its own, and a row with a version 5 id is one a folder made (the editor's ids are random). A missing id stops conversion, and an id used twice in a course stops it and names both places. A new id at the path that a resource the folder no longer lists last recorded stops it too, with the file and both ids named, unless the operator passes `--accept-new-ids`; then, as for every other new id, a new resource is made and the earlier one is archived. A resource never changes its type.

**Provenance.** A revision made from a folder records `provenance = { source: "folder", course, topic, resource, path, overlay, digest }`: the course folder's name, the two ids, the file's path from the course folder, whether it was read from the private overlay, and `digest`, the revision hash of its type, content, object keys and accessible alternative with provenance null. It holds no absolute path, host name or address. A head revision came from the folder exactly when its provenance has that source and its `digest` equals the digest of what the revision itself stores. A save in the editor carries the earlier provenance forward while it changes the content, so the two no longer match and the head counts as the editor's, also on a resource that conversion created; a save that puts the folder's content back matches again. A file that is only renamed or moved gets no revision, and its head keeps the earlier path.

**Which side wins.** The folder wins for what it declares: for a topic its title, objective, estimated time, prerequisites, completion rule and position; for a resource its topic, order, title, visibility, accessible alternative and content. An absent optional field declares the value the editor's empty form gives. The folder declares no release date, class, assignment or grant, and conversion does not rename an existing course. Topics and resources made in the editor are left as they are. A topic or resource that a folder made and no longer lists is archived, never deleted. Conversion stops before it writes a draft when it would replace or archive a head revision that came from the editor, and names each file; `--overwrite-editor` lets it go on, and the editor's revision stays in the history. The editor does not change.

**Conversion and publication.** `parallax sync` runs on the server's host, started by the operator, with no route, network caller or credential. It writes through the draft services under the owning account's `CourseScope` from `resolveActorScope`, queues the `reading.ingest` job, whose payload carries actor and scope, waits for it, and calls the publication above. Before it publishes it takes the course's lock and compares the drafts with what it wrote; a draft that changed meanwhile ends the run without a release. A validation error leaves the drafts written and no release, and the command prints the report with its codes and messages. Nothing is published when the drafts equal the newest release. Sync creates no account and no class, moves no class to a release and writes no audit event of its own.

**Hidden material.** In a tree that `course.yaml` declares public, every file under a topic's `exercises/` or `tests/` folder is read from the private overlay `private/`, a directory outside the tree with the same layout. A file under such a folder of the public tree, a definition in both places and, at level 1 and above, a missing definition stop the check, the level 0 build and the conversion, which name the file. What a level 0 build receives holds no definition and no hidden resource.

**Consequences.** No table or column is added, and P5-18 adds no migration. `createTopic` and `createResource` take an optional id that no route passes. `validate` moves unchanged to a module without database imports, so that the check and a level 0 build report with publication's codes and messages. A renamed course folder, or another address in `instructor.yaml`, is a different course. Each conversion that changes content adds revisions, as an editor's save does.

**Alternatives considered.** *A table from folder ids to rows:* stored state that can disagree with the folder, and a migration, for what a derivation gives. *Ids from file paths:* a rename would detach every note. *Front matter:* the stored bytes would differ from an upload, and PDFs and notebooks cannot carry it. *Telling the editor's head by the provenance source alone:* the editor's save carries provenance forward. *Letting sync write ids:* the folder on the server would differ from the author's copy.
