## Context

Spec §3 fixes the rule: one account, permissions per membership, and "every content read, media download, result export, and background job checks the relevant course or class scope on the server". §13 requires audience enforcement on annotation reads, private signed media access, and audit events. Scenarios A01, A02, A21 and A33 test that a student cannot reach instructor or classmate data, that one person holding two roles gets only each context's permissions, and that two cohorts of a course are mutually invisible. Because dozens of PRs will add routes, jobs and sockets, the enforcement must be structural: a route that forgets authorization must fail CI, not silently pass.

## Decision

**Principals and memberships.** `users` are identities. Permissions come only from rows in `class_memberships` (`role` ∈ {student, instructor}; boolean grants `manage_members`) and `course_memberships` (grants `owner`, `editor`, `publisher`). Course creation inserts an `owner` course membership. Inviting a class instructor inserts an `instructor` class membership and an `editor` course membership; `publisher` and `manage_members` are separate explicit grants (§3). A student enrolment code can only create `student` rows. **Preview as student** uses a shadow principal: a `users` row with `kind = 'preview'` and `owner_user_id`, holding a `student` membership flagged `is_preview`; its writes live in ordinary tables under that user id, so they can never touch a real student's record, and review/export queries exclude preview users.

**Every route declares a scope.** Contracts in `packages/contracts` require a `scope` field:

```ts
type Scope =
  | { kind: 'public' }                                        // health, sign-in link request
  | { kind: 'user' }                                          // signed-in, own records only
  | { kind: 'class';  role: 'student' | 'instructor' | 'any'; grant?: 'manage_members' }
  | { kind: 'course'; role: 'editor' | 'publisher' | 'owner' }
  | { kind: 'system' };                                       // internal, token-authenticated
```

`registerRoute(app, contract, handler)` is the only way to add an HTTP `/api/*` route, and `registerWebSocketRoute(app, contract, handler)` (P3-02a) the only way to add a WebSocket one: a contract with `websocket: true` (a `GET` without a body) is refused by `registerRoute`, and any other contract by `registerWebSocketRoute`. A Fastify `onRoute` hook throws at boot when a route under `/api/` lacks `config.scope`, so a hand-registered route fails every test that builds the app. Before the handler runs (for a WebSocket, before the upgrade, so a refusal is the usual HTTP answer and no socket is opened), the scope resolver reads `classId`/`courseId` from the path, loads the caller's membership in one query, and attaches a branded `ClassScope`/`CourseScope` object (`{ classId, releaseId, membership, role, grants, user }`) to the request. Non-members receive **404**, never 403, so unpublished or foreign resources disclose nothing (§2). Members lacking the role or grant receive 403. Handlers receive the scope object; data-access functions for class- or course-scoped tables accept **only** that branded type, not a raw id, so a handler cannot query another class by passing a string.

**Scoped tables.** Every table holding class data has `class_id NOT NULL` (annotations, threads, attempts, submissions, study positions, notebook sessions, grades, exports); course drafts and releases carry `course_id`. `apps/server/src/db/scoped.ts` lists both sets; a unit test introspects the drizzle schema and fails if a table with such a column is missing from the list or if a scoped table lacks the column. Repository helpers `forClass(scope)` / `forCourse(scope)` add the `WHERE class_id = …` predicate; direct `db.select()` on a scoped table outside `db/` is a lint error (Biome `noRestrictedImports` on the raw client from feature modules).

**User-owned tables.** A table whose rows belong to one person and to no class (`connectors`, `connector_pairings`, `notebook_connections`: a learner's paired computers and saved connections, connector design §10.2) carries `owner_user_id`, not `class_id`. `scoped.ts` lists them in `userOwnedTables`, and `forUser(scope: UserScope, table)` adds `WHERE owner_user_id = scope.user.id`, taking only the resolved `user` scope, never an id (P3-02). Its introspection test fails if a table other than `users` with `owner_user_id` is missing from the list (`users.owner_user_id` names a preview principal's instructor, ADR-0003, not a data owner); the raw-client lint covers these tables like the scoped ones. The browser routes over them (`/api/me/…`) declare `scope: { kind: 'user' }` and reach the tables through `forUser`, and a row that is not the caller's is a 404. The connector's own routes, `/api/connector/v1/*` (`pair`, `pair/poll`, `unpair` and the `link` WebSocket), are the exception: they declare `scope: { kind: 'public' }`, authenticate by the connector's signature or token, and address `connectors` by the id that credential proves (connector design §10.3, plan decision 33); likewise, deactivating an account revokes its connectors by user id. Three more paths reach `connector_pairings` rows that are not found through `forUser`, and they are the whole of it: `pair` spends a pairing row by the hash of the code the connector presents (`consumePairing` and `linkPairing` in `db/connectors/pairing.ts`; the code is the credential, and the row names the owner, so the new connector is created for that owner), and the maintenance job deletes used and expired pairings across all users (`purgePairings`, run by `jobs/maintenance.ts`); and closing an account (`closeAccount` in `db/lifecycle.ts`) deletes the pairings of the person and their preview principals by user id, so that a code issued earlier cannot start a pairing. Further paths reach `connectors` and `notebook_connections` rows without `forUser`: the maintenance job revokes the pending connectors of every user whose approval window has closed (`expirePendingConnectors(db, now)` without an owner, `db/connectors/registry.ts`), while pairing, listing and approving call it with one owner (the id of the spent pairing row, or `scope.user.id`); `createPendingConnector` (`db/connectors/registry.ts`) counts and locks that owner's pending connectors by the id the spent pairing row names (`countByStatus`, `lockOwner`), and it and `registerManagedConnector` (`db/connectors/managed.ts`) look a `connectors` row up by public-key fingerprint across all owners, so that one key is never registered twice, selecting only its id; `connectionForSession` (`db/connectors/connections.ts`) reads the caller's own connection and its connector from a resolved `ClassScope`, filtering on `scope.user.id` (`forUser` takes only a `UserScope`; see the sentence below on class-scoped rows); and `deleteNotebookCompute` (`db/lifecycle.ts`) reads and redacts the `connectors` of a person and their preview principals by user id (the rows stay, their ids being in the audit trail) and deletes or redacts their `notebook_connections`. It runs from `anonymiseIdentity`, that is when an account is closed in `delete` mode (`closeAccount`) and when the retention job (`applyRetention`, a system action across users, scheduled in `jobs/maintenance.ts`) anonymises an account deactivated past the grace period; closing in `deactivate` mode does not call it. A managed connector has a null owner, so `forUser` never returns it. Class-scoped rows that point at a user-owned one (a notebook session names a connection) keep `class_id` and check the owner as well.

The `biome.json` override exempts exactly `apps/server/src/db/**`, the composition root `main.ts` and test files (`**/*.test.ts`); every other server file, existing or new, is restricted. Data-access modules live under `db/` (for example `db/auth/`, `db/content/`, `db/annotations/`), and feature modules call them. A `db/` module may hold policy bound to its transactions, such as the `Outcome` mapping in `db/annotations/annotations.ts` or the release-availability checks in `db/content/*` (including the object-key prefix check in `db/content/media.ts`); the query and the rule that guards it then change together. From outside `db/`, a `db/` module imports only the scope types and helpers of `auth/scope.ts` and leaf modules that import nothing from `db/` (for example `auth/tokens.ts`, `outcome.ts`, `content/availability.ts`); feature modules that call into `db/` are never imported back. The rule is the import restriction plus the GritQL plugin `apps/server/lint/raw-db-query.grit`, whose header lists the forms it does not catch.

**Audience and privacy.** Annotation visibility is one rule, with one implementation: `visibleTo` in `db/annotations/visibility.ts`, the SQL form that every read, count, notification and export applies (there is no second, in-memory form). `private` → author only; `instructor` → author plus class instructors; `class` → class members; rows of a preview principal are seen by that principal only. `visiblePost` is not an audience form: inside a thread that `visibleTo` already admitted, it hides other people's preview posts. Private notes are never joined into instructor views (§17 default).

**Downloads.** Objects are keyed `courses/{courseId}/…` or `classes/{classId}/…`. A scoped route mints an HMAC content token `{ key, userId, scopeId, exp ≤ 5 min }` only if the key prefix matches its scope. The token is served on a separate **content origin** (`CONTENT_HOST`, e.g. `127.0.0.1` vs `localhost` in dev/e2e, `content.` subdomain in production) that has no cookies and no `/api`, so copied links expire and untrusted content (notebook HTML outputs and images, SVG, uploaded files) cannot read the app session. The exceptions are the three app-origin surfaces listed under **Readings on the app origin**, below.

**Readings on the app origin.** The Reading tab inserts a native reading's HTML into the app page, because block anchors, the saved place and the selection toolbar (§8, ADR-0003) need the reading's own DOM. Two sanitisers stand in for the origin boundary, and each alone must stop script: the ingestion job cleans the source with `readingSchema` (`apps/server/src/content/reading.ts`), and the browser cleans the stored result again with DOMPurify (`apps/web/src/reading/sanitize.ts`) before inserting it. Both use one allow-list, `packages/contracts/src/readingHtml.ts`: GitHub's sanitisation schema plus figures, captions, KaTeX's MathML and highlight classes; no `script`, `style`, `svg`, `iframe`, `object` or form fields other than a disabled task-list checkbox; no event handlers or `style` attributes; class names limited to the highlight, KaTeX, task-list and footnote classes; `href` limited to http(s), irc(s), mailto and xmpp, `src` and `cite` to http(s); ids, names and id references prefixed `user-content-`. Only the ingested HTML is served, and its images are content-origin URLs minted at read time. The uploaded Markdown/HTML source is never served while the reading converts or once it has converted; the one exception is the permitted source download of a failed conversion (§14), when the object route mints an attachment link to it on the content origin and the reading names its `sourceKey`. A unit test holds `readingSchema` to the shared list, and a fixture of hostile sources (HTML inside MathML `mtext`, namespace confusion, obfuscated `javascript:` URLs) is run through both layers and through the browser layer alone. Widening the list means changing both layers and the shared file together. **Three app-origin surfaces, one allow-list (owner decision, 2026-10-06, issue #383).** The same two-sanitiser rule covers every place HTML is inserted into the app page, and there are exactly three: (1) a native reading's ingested HTML; (2) a notebook's Markdown cells and its `text/markdown` and `text/latex` outputs (`apps/web/src/notebooks/NotebookView.tsx`, `Markdown`), which the server renders in `Builder.markdown` (`apps/server/src/content/notebook.ts`) with `renderReading` and so cleans with `readingSchema` at import, and which the live notebook (`apps/web/src/notebooks/live/LiveNotebook.tsx`) shows through the same `Markdown` component, for its cells and, through `Output`, for stored Markdown outputs; (3) web slides, the per-slide HTML of `slides_web` (`apps/web/src/slides/SlideViewer.tsx`), which `renderSlides` cuts from one `readingSchema` pass over the deck. All three are cleaned in the browser by `sanitizeReading` (`apps/web/src/reading/sanitize.ts`) before `dangerouslySetInnerHTML`, and all three are held to the one allow-list in `packages/contracts/src/readingHtml.ts`: widening it (both layers and the shared file together, as above) changes every surface at once. Readings need the page's own DOM for block anchors, the saved place and the selection toolbar. The owner decided that notebook Markdown and slides stay in the page too, so they can carry anchors and the margin in the same flow. Their HTML carries `data-block-id` attributes (slides also store a deck-wide `blockMap`). Web slides do anchor to block ids: the annotation contract accepts `text` anchors on `slides_web` (`packages/contracts/src/anchors.ts`) and the server remaps them through the deck's `blockMap`, by block id first and then by a unique fuzzy quote-and-context match (`apps/server/src/annotations/mapping.ts`). Block ids are content hashes made by one shared derivation, so that derivation must stay identical between ingestion and mapping; changing it breaks every stored slide anchor. The current UI (`SlideNotes.tsx`) anchors only by slide number. Notebooks are different: the contract accepts no text anchor on them (`anchorKindsByType.notebook` is `['none']`), whatever block ids their Markdown cells and Markdown/LaTeX outputs carry; each cell is rendered separately, so those ids are not unique across cells.

**Notebook outputs.** A notebook's simple inline table is not HTML on the page: the server stores its cells as text and the browser renders them as text. The notebook `outputSchema` (`apps/server/src/content/notebook.ts`) is a separate allow-list from `readingSchema`, and wider: GitHub's schema plus `style` elements, `class` and `style` attributes, `figure`, `figcaption`, `caption`, `colgroup` and `col`, `img` with `alt src title width height` plus the global attributes the `'*'` entry gives every element (`className`, `style` and GitHub's global ones), `data:` allowed for any `src`, and `script`, `iframe`, `object`, `embed`, `noscript`, `template`, `textarea`, `title` and `head` stripped. It sets `clobber: []`, so ids and names are not prefixed `user-content-`; the code's reason is that inside its own document an id cannot clobber anything of the app. It cleans a notebook's HTML outputs, which are stored as an object and served only on the content origin inside an iframe with `sandbox=""`; nothing it admits is inserted into the app page. A notebook's HTML outputs, PDFs, images, SVG and every other upload stay on the content origin. JavaScript outputs are never served: `Builder.bundle` never stores or runs the `application/javascript` representation, so such a bundle shows its next safe representation (table, image, Markdown, HTML with scripts removed, plain text, or `application/json` shown as text), or is shown as unsupported (spec §10.7).

**Jobs and sockets.** Every pg-boss payload carries `{ actorId, scope }`; `runScopedJob` re-resolves membership before touching data and rejects payloads without scope. WebSocket upgrades go through a scoped route; the resolved scope is stored on the socket, re-validated every 60 s and on any message naming a resource, and the socket closes on revocation (§14 "Permission revoked").

**Isolation matrix test (A01, A02, A21).** `apps/server/test/fixtures/world.ts` builds course *Statistical thinking* with classes A and B, owner Elena, instructor of B, students in each class, and a user who teaches A and studies in B. Every contract must supply `examples` (valid params/body). The matrix test iterates all registered contracts with `class`/`course` scope and asserts: foreign principal → 404; correct class but wrong role → 403; preview principal never reaches instructor routes. New routes are covered automatically; a route without examples fails the test. Scenario tests for A33 extend the same harness to notebook sessions and forwarding destinations (ADR-0005).

**Error replies.** Every failure body is `{ error, … }`: `error` is a short code (`class_archived`, `invite_revoked`, `invalid`), never an identifying detail, plus only the fields the contract declares. Statuses: **400** the request cannot be applied as written, by schema validation (Fastify's body, which also carries `message`) or by the service (`{ error: 'invalid', message }`, the sentence to show); **401** no session, or one too old for the change; **403** a missing role or grant, or a refusal the scope cannot decide (`not_instructor`, `invite_other_account`); **404** unknown, foreign or missing, one body (above); **409** the target's state refuses the change (a stale revision with the server copy per ADR-0003, an archived class, a busy job, an ownership rule); **410** something used up (a revoked or expired invitation); **413** a file over the limit; **422** only for a domain validation report the client renders (publishing, `{ error: 'validation_failed', report }`); **429** a rate limit; **503** a dependency not configured. A handler answers a failure only through `registerRoute`: `notFound()`, `settle(outcome)`, or the `fail(status, body)` it is handed, typed to the statuses and bodies its contract declares in `errors`. `errorResponses(contract)` adds the statuses the scope and parts imply (400 for params, query or body; 401 off public scopes; 403 for a role or grant; 404 and 503 always); OpenAPI lists exactly those plus the declared ones, and `registerRoute` answers 500 for any other 4xx a handler raises, so an undeclared status is a bug, not a silent reply. Transport errors Fastify raises before the route runs (415, 413 over the body limit) are not listed.

**Audit.** Membership and grant changes, publication, adoption, assignment changes, submissions, grade overrides, releases and exports append to `audit_events` (actor, target, scope, before/after summary). Sensitive membership changes require `auth_time` within 15 minutes (§3), enforced in the resolver via `scope.requireRecentAuth()`. `parallax apply` (P5-19) is the one caller that makes these changes without a session: run by the operator on the server's host, it issues enrolment invitations and gives instructors their class membership and course editing for the owning account, through the data-access functions under scopes from `resolveActorScope`, and it appends one `setup.apply` audit event for each class it changes. The routes keep `requireRecentAuth()`, which always throws on such a scope.

## Consequences

- Adding a feature means adding a contract with scope and examples; forgetting either breaks boot or the matrix test.
- 404-for-non-members hides existence but can confuse debugging; logs record the real reason at debug level only.
- The shadow preview user adds rows per instructor per class; it keeps every other table simple.
- Two hostnames are needed in every environment (dev: `localhost` + `127.0.0.1`; prod: two subnames); documented in Phase 0/P1-06.
- Postgres row-level security is not used initially; the schema keeps `class_id` on every scoped table so RLS policies can be added later as defence in depth without changing queries.

## Alternatives considered

- **Row-level security as the primary control**: strongest at the database, but policies per table, per-request `SET LOCAL`, bypass roles for jobs, and "why is my query empty" debugging are costly for agent-authored PRs. Deferred to hardening.
- **Ability libraries (CASL)**: flexible but encourages per-handler checks, which is precisely what can be forgotten.
- **Per-handler `assertMember()` calls**: no structural guarantee; rejected.
- **Presigned bucket URLs**: simpler streaming, but leaks long-lived links and couples the app to S3 semantics; token-gated streaming keeps `fs` and `s3` adapters identical.

## Amendment: Open site (level 0)

Added 2026-10-13 (P5-05) for requirement N6, on the owner's answers Q17 to Q21 (issue #559; plan §8). The Decision above is not changed. It stays the whole rule for every installation that has a server (levels 1 and 2): a scope on every route, 404 for non-members, content tokens on the content origin. Detailed design: [docs/design/open-site.md](../design/open-site.md).

**No server and no scope to resolve.** A level 0 site is what `parallax build` writes for a site whose configuration says `level: 0`: plain files for static hosting. It has no server, no `/api`, no database, no account, no session and no cookie. Nothing is read on a person's behalf, so there is no principal, no membership and no scope to resolve, and `registerRoute`, the scope resolver and the isolation matrix have nothing to guard there. They are not weakened or bypassed: no code of a level 0 site reaches them. What stands in for authorisation is omission when the site is built: a level 0 site holds only what anyone may read. The build reads course folders and nothing else. It reads no database and runs with `DATABASE_URL` unset. Moving a site to level 0 is a change of `level` and a rebuild from the folder; nothing is exported or published from a database. The viewer makes no request to `/api`, offers no sign-in, provider button or class control, shows no note, highlight, sketch or discussion control, and keeps nothing in the visitor's browser.

**What a build leaves out.** A level 0 build reads a course folder only through the reader's site entry (`readCourseForSite`) and writes its data only through the strict allow-list schemas of `packages/contracts/src/openSite.ts`: what is written is the result of parsing, so a key that a schema does not name is refused or dropped and never written. Neither has a place for any of these:

- every test definition: questions, checks (public and hidden), code files, rubrics and grading settings;
- every exercise definition: steps, answers, feedback, hints and solutions. Exercises are not checked in the browser, and no checking code is built;
- every resource that is not visible to students: the reader's site entry hands a build the visible ones only, and a build has no filter of its own;
- every resource whose release date is in the future, because a static host cannot enforce a date. A course folder states no release date today, so a build has none to compare, and none is added; the rule binds any later form of the folder that states one;
- the private overlay and every file under a topic's `exercises/` and `tests/` folders. The build opens none of them, and in a tree declared public a file there stops the build, as it stops `parallax check`;
- the uploaded Markdown or HTML source of a native reading (only its ingested HTML is written, as under **Readings on the app origin**), a web deck's Markdown, and a notebook's own `.ipynb` file with its stored output payloads, metadata and attachments (the download is composed without them, below). A notebook's data files are written only inside one zip object on the content host, beside the composed notebook file (amended 2026-10-21, below);
- completion rules, prerequisite locks, saved positions, notes, highlights, sketches, discussion, attempts, submissions, grades, accounts, memberships, classes, enrolment codes and audit events, and an instructor's address (the display name is written).

The Exercises and Tests tabs list titles, and no file is written for an exercise or a test.

**The equivalent of the content origin.** The build writes two trees for two host names: `site/` for `origins.app` and `content/` for `origins.content`. Untrusted content is notebook HTML outputs, images (notebook outputs, cell attachments, and images of readings and slides), SVG, uploads and PDFs, and with them the notebook file that the build composes for download. It is written only to `content/`, as content-addressed files `o/<sha256>.<extension>`, and the site names each one by its address on the configured content origin; a notebook's own `.ipynb` file is not written at all (above), and its data files only inside a zip. The extension comes from a fixed table of nine content types (PDF, notebook file, PNG, JPEG, GIF, WebP, SVG, HTML with its charset, and zip). A type outside the table stops the build, and the table has no JavaScript type. So the content host holds no page, script or data file of the site, and the site host holds no untrusted object: a document or image opened on the content host, in a frame or on its own, has another origin than the site. Conversion is the conversion of level 1 (`convertRevision` over the same renderers and limits): HTML outputs are cleaned with `outputSchema` and SVG with `sanitizeSvg`, and the viewer frames HTML outputs with `sandbox=""` as today. The three app-origin surfaces keep both sanitisers, each of which alone must stop script: `readingSchema` when the build converts, and DOMPurify (`sanitizeReading`) in the browser, held to the one allow-list. Their HTML travels in JSON data files on the site host, as it travels in API replies on the app origin at level 1. JavaScript outputs are never served: the notebook renderer never stores one, the build has no way to write one, and a test asserts on every emitted file that none holds one. A notebook's own `.ipynb` file, which can hold such a payload as text, is not written. The download is a notebook that the build composes from the rendered view: Markdown cells hold the sanitised rendered HTML with image addresses on the content origin, raw cells their text, and code cells their source with no execution count and no outputs; its metadata is empty except the language name. The page still shows the stored outputs. The composed file is written to `content/` and is never shown as a page or run.

**The rule that stops a build.** `parallax build` at level 0 stops, says why and leaves `dist/` as it was in two cases. (1) The host names of `origins.app` and `origins.content` are equal, compared in lower case without scheme, port or a trailing dot. The configuration schema refuses this, and the build checks again. (2) An untrusted object would land under `site/`. All output goes through one write path, in which only the compiled viewer and JSON that passed its schema can be written under `site/`. Before anything is put in place every file of the output is read again. Under `site/` a file must be a file of the compiled viewer, a copy of its `index.html` at an address, or a data file that still passes its schema; none may have the bytes of a course file or of an object; and every object address in a data file must be on the content origin. Under `content/` a file must be named by its own digest, with an extension of the table. A build also stops where conversion stops at level 1: on what the folder reader, the upload rules and publication's report refuse. A warning of that report stops no build, at level 0 as at level 1: a topic whose only resources are exercises and tests is built and listed, and a Shiny app on an origin that the configuration does not list is written with its external link and is not framed.

**What the build checks, and what it cannot.** The tool checks only what a build can know: these rules, on its own configuration and its own output. It contacts no host and checks no response header of a deployed host. A static host mints no token, so an object's address is permanent and public; that is sound only because a level 0 site holds nothing private. A static host also does not send what the content origin sends at level 1 (`Content-Security-Policy: sandbox`, `X-Content-Type-Options`, `Content-Disposition`) unless its operator adds them. The site host likewise does not send the policy header of the app origin (`script-src 'self'`, frames only from the content origin and the listed Shiny origins, `frame-ancestors 'none'`), and the viewer's `index.html` carries no policy in its place. What stands in at level 0 for those headers is the two host names, the `sandbox=""` frame around every HTML output, the cleaning of HTML outputs and SVG at conversion, and the two sanitisers of the three app-origin surfaces.

**A notebook's data files, and a notebook on the visitor's computer.** Amended 2026-10-21 (owner's requests in the project thread of that day; spec §13, "A notebook on one's own computer at level 0"; [open site design](../design/open-site.md) §4 and §14). A notebook that declares data files is also written as one zip object on the content host: a folder named as the notebook, holding the composed notebook file and each data file at its path. It is an object like the others, named by its digest, and is never shown as a page or opened by the viewer. A visitor may also run a notebook on their own computer: after they choose **Run on this computer**, the viewer talks to the connector's open mode on `http://127.0.0.1:47821` (ADR-0005, **Amendment: open mode**). That is the one request the viewer makes beyond its data files, and it reaches the visitor's own computer, not a server of the site: no principal, membership or scope is involved, and the connector serves only an origin the visitor allowed in its terminal. The connector itself downloads the zip from the content host and checks its digest. Live outputs never pass through the content host, which holds only what the build wrote; the viewer shows them by the rules of this amendment for untrusted content, without a second origin: a raster image or an SVG only as a `data:` address in an `img`, which runs no script; HTML only in a frame with `sandbox=""` and a `srcdoc` document that DOMPurify cleaned (no `meta`, `base`, `link`, `form`, frames, `object` or `embed`) and whose own policy loads nothing (`default-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src data:; form-action 'none'`), so it has an opaque origin, runs no script and fetches nothing; Markdown and LaTeX as their source text, since no server cleaned them for the app origin; JSON and text as text. JavaScript outputs and widgets are never run, as everywhere.

**Hosting requirements.** There are two. (1) Two host names: one serves `site/` at its root and the other serves `content/` at its root. Two paths of one host separate nothing, and a build for one host name stops. (2) For PDFs, the content host answers cross-origin range requests from the site: a `GET` that carries the site's `Origin`, with or without a `Range` header, is answered with `Access-Control-Allow-Origin` for that origin (or `*`); a ranged one with status 206 and `Content-Range`; `Content-Range`, `Accept-Ranges` and `Content-Length` are exposed; and the preflight that a `Range` header causes is answered. On hosting that does not, a PDF deck or reading says that it could not be loaded and keeps its download link, and everything else works. Every address of the site is a file, an `index.html` at that address, so no rewrite rule and no fallback page is asked for.

## Amendment: Identity providers

Added 2026-10-14 (P5-12) for requirement N7, on the owner's answers Q24 and Q25 (issue #559; plan §8). This section is the first commit of P5-12's pull request, before any of its code. The Decision above is not changed: a provider sign-in ends in the same kind of session that a link sign-in starts, and the scope resolver, the 404 for non-members and the content origin apply to it unchanged. Detailed design: the plan of run R4, [docs/plans/2026-10-14-design-sign-in-with-behind-identityprovi.md](../plans/2026-10-14-design-sign-in-with-behind-identityprovi.md).

**One interface, two kinds of provider.** The email link (`EmailLinkProvider`, unchanged) and OpenID Connect (`OidcProvider`, `apps/server/src/auth/oidc-provider.ts`) both implement `IdentityProvider` (`apps/server/src/auth/identity-provider.ts`). OpenID Connect is the only provider kind built, and it is generic: a university's issuer or Google is configured by its issuer URL, a client id and a client secret. GitHub and ORCID sign-in are not built; each stays a later item for the owner. Both kinds finish through `signInWithProof`: `userForVerifiedEmail` finds or creates the account, the session the browser held is ended and a new one starts with `auth_time` set to the time of the sign-in, a deactivated account is refused like a proof that did not work, and the destination is kept only as a same-origin path (`safeDestination`, else `defaultDestination` for the entrance).

**Accounts stay keyed by a verified address.** A provider sign-in reaches the account whose `users.email` is the lower-cased address of the ID token, the key a link sign-in uses, so `INSTRUCTOR_EMAILS` and invitations, which match that address, work unchanged. The address is used only when the ID token's `email` is an address and its `email_verified` is the boolean `true`. An ID token with no address, or with `email_verified` missing, false or anything else, is refused: no account is created or changed, no session starts, and the sign-in page explains that the provider confirmed no address. The issuer's subject identifier is not stored and no table of provider identities exists: two addresses are never joined into one account, and a person whose address at the issuer changes reaches the account of the new address. A sign-in that is waiting for the issuer is held in a cookie of the browser (below), so it has no table either, and this amendment adds no migration.

**The flow.** The OpenID Connect authorization code flow with PKCE (`S256`), a `state` and a `nonce`, through `openid-client` 6.8.8, whose exact version is recorded in ADR-0001's version table. The start route keeps the state, the nonce, the code verifier, the provider id, the destination and the time of the start in the cookie `pc_oidc`: signed with `SESSION_SECRET`, HttpOnly, `SameSite=Lax`, Secure when the app is served over https, sent only to `/api/auth/oidc` and kept ten minutes. That cookie binds the sign-in to the browser that started it, and the server keeps no pending state, so a restart during a sign-in loses nothing. The issuer returns the browser with a top-level `GET` to the callback (the query response mode, never `form_post`), which carries a `Lax` cookie. The callback clears the cookie on every answer and refuses when the cookie is missing, does not verify, names another provider or was set more than ten minutes earlier, when `state` differs, or when the issuer reports an error; the issuer accepts each code once. It exchanges the code at the issuer's token endpoint with the client secret (`client_secret_basic`), outside the sign-in transaction, and checks the ID token: its signature against the keys the issuer publishes at the `jwks_uri` of its discovery document (an unsigned token and a symmetric algorithm are refused), `iss` against the configured issuer, `aud` and `azp` against the client id, `exp`, `iat` and `nonce`. The provider button on the sign-in page is a link, not a form, because the app's `form-action 'self'` would block a form whose answer redirects to the issuer. Request logs drop the values of `code` and `state` as they drop `token`.

**Routes.** Three routes are added, each registered through `registerRoute` with a contract in `packages/contracts/src/routes/auth.ts` that declares `scope: { kind: 'public' }` and `examples`, and each listed on the reviewed `publicAllowlist` of the isolation matrix: `GET /api/auth/methods` (whether email links are offered, and the id and display name of each configured provider, never its issuer, client id or secret), `GET /api/auth/oidc/:provider/start` and `GET /api/auth/oidc/:provider/callback`, the last two answering with a redirect. A provider id that is not configured answers the shared 404. Start and callback are limited per client address with the budgets of the link routes, `AUTH_LINK_RATE_LIMIT` and `AUTH_VERIFY_RATE_LIMIT`. No route reads or returns a person's records; the callback writes only through `signInWithProof`.

**Configuration; mail is optional.** `OIDC_PROVIDERS` lists the providers as JSON (`id`, display `name`, an https `issuer`, `clientId`), and `OIDC_CLIENT_SECRETS` maps each id to its client secret. Client secrets are kept only in the git-ignored environment file; a listed provider without a secret, or a secret for an id that is not listed, stops the server at start-up with a message that names the id and never the secret. A provider's button appears only when that provider is configured. A mail sender is needed for email links only: `MAIL_TRANSPORT=none` configures none, and then `GET /api/auth/methods` says that email links are not offered, the sign-in page shows no email form, and `POST /api/auth/link` answers 503, never 202, and stores no link; `none` needs at least one provider. With no provider configured and `MAIL_TRANSPORT` as today (default `file`), every existing route, contract, default and screen behaves as before, `/api/auth/link`, `/api/auth/verify`, `/api/auth/signout` and `/signin` included. A site lists its providers in `signIn.providers` of `parallax.config.ts` ([docs/design/site.md](../design/site.md) §4). A level 0 site has no sign-in, and this amendment adds none.

**Left to the owner.** This amendment decides nothing beyond N7 and the answers to Q24 and Q25. Joining accounts of different addresses, signing in without a verified address or on an issuer's own claim in place of `email_verified`, limiting a provider to some address domains, GitHub and ORCID sign-in, sign-in at level 0, and a look of its own for a provider are not built; each is a later owner decision.

## Amendment: Decks converted from presentation files

Decided on 2026-10-20 (owner request; design [docs/design/slide-decks.md](../design/slide-decks.md)), for spec §7.

**Decision.** A presentation file (`.pptx`, `.odp`) in a course folder is untrusted course material that only the deck converter reads. The site tool runs the converter on the author's machine or the site host, never in the server or the worker: in a container with no network, a read-only image, no capabilities, no new privileges, a fixed non-root user, memory, process, CPU and time limits and its input on standard input only (the policy of ADR-0004 with a converter's sizes), or, for `parallax check` and a level 0 build on a machine without Docker, in the machine's own LibreOffice, which the tool names in its output. The converter opens the file with macros disabled and links not updated; on the slides and on the master pages they use, it fixes slide numbers, empties dates that would update, and removes links that are not `http`, `https` or `mailto`; and it empties the document properties before export, so that hidden slides, speaker notes, comments, the author's name and links to the author's files or programs are in no page. Its output, one PDF and the number of pages of each slide, is all that leaves it, and the tool treats that output as untrusted: it bounds the result line, the PDF's size and the error text, and refuses anything more. Only when Docker cannot be used at all does the tool fall back to the machine's LibreOffice, never after the container refused, failed on or was stopped over a file. Then: the server, a level 0 build and the browser receive a PDF deck file and treat it exactly as one (`courseFileCheck('pdf')`, the upload size limit, text extraction in a bounded thread, the content origin only). The presentation file is neither stored nor served, and no script is added on any origin.

**Consequences.** A flaw in LibreOffice reaches at most the converter's container, or, without Docker, the machine of the person who runs `check` or a level 0 build, the same risk as opening the folder's decks in a presentation program, which for a folder from someone else's repository is a risk the person takes on knowingly: the tool says, before the first conversion, that it is converting outside any container. The server image gains nothing. Hidden slides, speaker notes and comments of a deck never reach the server.

**Alternatives considered.** *LibreOffice in the worker:* the server would parse untrusted Office files, and its image would grow by several hundred megabytes. *LibreOffice's slideshow script in a sandboxed frame on the content origin:* it plays every effect, but serves script, which this ADR has never done for course material; the owner chose click steps without script.
