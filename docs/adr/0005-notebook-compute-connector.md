# ADR 0005 — Notebook compute connector and relay protocol

**Status:** Accepted, 2026-09-30. Amended 2026-10-15 (P5-20, owner's answer Q26 in issue #559): Colab over SSH, for paid Colab only, through one fixed proxy command built into the connector; see **Amendment: Colab over SSH** below, which [docs/design/connector.md](../design/connector.md) §5.7 refines. Amended 2026-10-21 (P6-05, owner request; PRODUCT.md N6): an `open` command serves pages of level 0 sites in the browser of the same computer, on loopback, with no Parallax server; see **Amendment: open mode for level 0 pages** at the end, which the [open site design](../design/open-site.md) §14 refines.

Refined by [docs/design/connector.md](../design/connector.md) (P3-01): wire schemas and fixtures in `connector/protocol/v1/`, pairing and link authentication (§3, §4.2), stage checks and the error catalogue (§5), the Jupyter allowlist, network scope and leases (§7–§9), the server's tables, endpoints and relay (§10), the OS matrix and MFA policy (§13, §5.3). Where it differs from the text below (paths under `/api/connector/v1`, the signed bytes, the message set, the allowlist, user-owned connections, the token in the environment or on standard input, asynchronous Test connection, no auto-approve flag), §17 of the design lists each change and the design wins.

## Context

Notebook cells execute on a computer the learner is authorised to use: this computer, a LAN/lab machine, or an SSH server, optionally via a jump host (§10). The browser speaks only HTTPS/WSS to Parallax; an authorised **compute connector** performs SSH, runtime start/attach and the tunnel to a loopback Jupyter server, and Parallax relays only the authorised notebook session, not a raw TCP proxy (§10.2). Pairing uses a short-lived code and explicit device approval; **Test connection** reports each stage separately; Ready appears only after the notebook service and kernel are verified (§10.3); execution requests are bound to notebook revision, cell, code hash, kernel and message id; reconnect must not re-execute; leases govern idle sessions (§10.4); credentials and tokens never reach documents, URLs, browser storage or logs (§10.6). Scenarios A27–A36. This ADR fixes enough to plan and to test in CI; item P3-01 refines the wire schema and OS matrix.

## Decision

**Connector.** `connector/` is a Go module producing `parallax-connector` for linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64. Commands: `pair --server URL --code XXXX-XXXX`, `run` (foreground service; `--allow-net CIDR` repeatable), `status`, `unpair`, `doctor`. State directory (`$XDG_CONFIG_HOME/parallax-connector`, `~/Library/Application Support/...`, `%APPDATA%\...`): `identity.key` (Ed25519, mode 0600), `config.json` (server, connector id, name), `known_hosts` (SSH trust store), `sessions.json` (leases, so limits are enforced even when the server is unreachable). SSH keys are referenced by path or taken from the local SSH agent; passphrases are prompted in the connector and never transmitted. Agent forwarding is off. The same binary in `--managed` mode (config from environment, secret store on disk) serves as the server-side connector for institutions later; it is not required for A27–A36.

**Pairing and authentication.** Web (`user` scope) → `POST /api/me/connectors/pairings` → `{ code, expiresAt }` (8 alphanumerics, 10 minutes, single use). CLI `pair` generates the key and calls `POST /connector/v1/pair { code, publicKey, name, os, arch, version }` → connector row `status = pending`. The web app lists the pending device (name, OS, key fingerprint) and the user clicks **Approve** → `active` (explicit device approval, §10.3). The link is `wss://…/connector/v1/link`: server sends `{ t: 'challenge', nonce }`; connector answers `{ t: 'auth', connectorId, ts, sig = Ed25519(nonce ‖ connectorId ‖ ts) }`; server verifies with `crypto.verify` against the stored public key and rejects `revoked`/`pending` connectors. Unpairing or account revocation closes the link and marks the row `revoked` (§10.6); it does not claim to revoke the person's SSH accounts.

**Wire protocol v1** (one WebSocket per connector; text frames are JSON control messages with `v: 1`, binary frames carry stream data prefixed by a 4-byte stream id and 1-byte flags):

| direction | message | purpose |
| --- | --- | --- |
| c→s | `hello { version, os, capabilities }` | after auth |
| s→c | `test_connection { requestId, target }` | stage checks, no side effects |
| c→s | `test_result { requestId, stages: [{ name, ok, detail, recovery? }] }` | stages: reachability, host_identity, ssh_auth, workspace, forwarding, runtime, notebook_auth, kernels |
| s→c | `open_session { sessionId, target, runtime, workspace, lease }` / `close_session { sessionId, stop }` | start or attach; detach vs stop |
| c→s | `session_state { sessionId, state, jupyterVersion, kernelspecs, lease, cause? }` | state ∈ starting, ready, running, disconnected, stopped; `cause` distinguishes sleep, VPN, SSH timeout, stopped service, expired allocation (A36) |
| s→c | `http { streamId, sessionId, method, path, headers }` + body stream; `ws_open { streamId, sessionId, path }`; `ws_close` | relayed Jupyter REST and kernel channels |
| c→s | `http_head { streamId, status, headers }` + body stream; `ws_event`; `stream_end`, `stream_reset` | |
| both | `ping`/`pong`, `heartbeat { sessions }` every 15 s | lease and link liveness |

`target` is `{ kind: 'local' }` or `{ kind: 'ssh', host, port, user, jump?: {host, port, user}, auth: { keyPath | agent }, workspace }`; no secrets travel from the server. The connector proxies only an allowlist of Jupyter paths for a session it opened: `/api/status`, `/api/kernelspecs`, `/api/sessions[/id]`, `/api/kernels[/id[/interrupt|restart|channels]]`, `/api/contents/<workspace>/…`. The server enforces the same allowlist before forwarding, so neither side alone can widen it (§10.2 "not an unrestricted TCP proxy").

**Runtime.** For `local`, the connector spawns `jupyter server --ServerApp.ip=127.0.0.1 --ServerApp.port=0 --IdentityProvider.token=<random>` (or attaches to a running server listed in `jupyter server list` when the user chooses attach) and keeps the token in memory. For `ssh`, it dials with `golang.org/x/crypto/ssh`, verifies the host key against `known_hosts` (unknown → stage `host_identity` returns the fingerprint for first-use confirmation; changed → hard stop, A30), optionally through a jump host (`ssh.Dial` over a channel of the first client), checks the workspace, starts or attaches Jupyter on the target via `exec`, and opens a local forward (`client.Dial("tcp", "127.0.0.1:<port>")`) per relayed request. `AllowTcpForwarding no`, missing Jupyter, or a bad token surface as their own failing stage and never reach Ready (A29). Sessions started by the connector are **owned**; attached ones are not, so `close_session{stop:true}` refuses to stop an unowned runtime (A32).

**Server relay (`apps/server` `relay` mode, `@fastify/websocket`).** `notebook_connections` (owner, connector id, non-secret target reference, trusted fingerprint, workspace, environment) and `notebook_sessions` (user, connection, class, resource revision, Jupyter session/kernel ids, state, lease expiry, last confirmed) are class-scoped rows (ADR-0002); a guessed session id is a 404 (A33). The browser connects to `/api/classes/:classId/notebook-sessions/:id/channels` (scoped route). For `execute_request`, the server assigns `msg_id`, records `cell_executions (session, cell_id, revision_id, code_hash, kernel_id, msg_id, state)`, then forwards; kernel messages are matched by `parent_header.msg_id`, and outputs for an unknown or superseded kernel are dropped and logged. The last 256 KiB of output per execution is buffered for replay on reconnect; beyond that the execution is marked `incomplete` and the UI offers rerun (A31). The relay never retries an `execute_request`.

**Leases.** Owned sessions carry `{ idleTimeoutMin: 30, gracePeriodMin: 5 }` shown before Connect; the connector enforces them from `sessions.json` even without the server; the server marks sessions `unconfirmed` when heartbeats stop, never `completed`.

**Testing.** Go unit tests spin an in-process `x/crypto/ssh` server and an `httptest` fake Jupyter, covering host-key states, jump routing, forwarding refusal and path allowlists without Docker. CI job `connector-e2e` (Phase 3) runs compose services `sshd-jupyter` (python:3.12-slim + openssh-server + jupyter-server 2.21.1 + ipykernel 7.4.0, one test user with an authorized key) and `jump` (openssh-server only), builds the connector, pairs it against the API with a test-only auto-approve flag, and drives A27/A28/A29/A30/A31 through Playwright.

## Consequences

- One binary, one protocol, three targets (local, SSH, SSH via jump); institution-managed connectors reuse it later.
- Ed25519 challenge auth avoids long-lived bearer tokens; losing the state directory means re-pairing.
- Kernel WebSocket traffic crosses two hops (browser→server→connector→Jupyter); latency is acceptable for interactive cells and the server sees message ids, which the binding requires.
- Windows/WSL routes, MFA (`keyboard-interactive`), HPC scheduler adapters and the managed-connector network policy were refined in P3-01 (`docs/design/connector.md` §5.3, §12, §13); scheduler adapters stay an extension.

## Alternatives considered

- **Browser-side SSH (WebAssembly)**: no way to reach LAN machines or hold keys safely.
- **Inbound tunnels / port forwarding on the learner's router**: rejected by §10.2; the connector always dials out.
- **Reverse proxying the whole Jupyter UI**: exposes an unrestricted surface and breaks the "Parallax keeps the notebook interface" requirement.
- **Connector in TypeScript**: see ADR-0001; single-binary distribution and `x/crypto/ssh` decide it.

## Amendment: Colab over SSH (P5-20, 2026-10-15)

**Context.** N8 (spec §13, Compute) makes Colab over SSH a connection option, for paid Colab only. Google's `colab` program has a command, `colab ssh --proxy-mode`, that carries SSH over a WebSocket and serves as an OpenSSH `ProxyCommand` (`docs/needed_specs.md` N8, findings of 2026-10-12). The connector dials `host:port` itself, and a Colab runtime exposes none, so the `ssh` target cannot reach one. The owner's answer Q26 (issue #559; plan §8) fixes the route: a fixed proxy command built into the connector, never a command sent by the server, on Linux and macOS and under WSL on Windows. The Decision above does not change: `local` and `ssh` behave as before, the relay still cannot make the connector run a command of its choosing, and notebook code still never runs on the server that serves the site.

**One fixed command.** A `colab` target is reached by running `colab ssh --proxy-mode`: the program `colab`, looked up on the `PATH` of the connector's own process, with exactly the arguments `ssh` and `--proxy-mode`, started without a shell. Its standard input and output carry the SSH connection that `x/crypto/ssh` otherwise makes over TCP. No message has a field for a program, a path to one, an argument or a `ProxyCommand`, and the schemas are strict, so the server cannot name what runs; the connector builds the argument list from constants and passes the program no value from a message. The program gets a minimal environment, no terminal and no shell; its standard error is drained into a bounded buffer, passed through `redact()` and the sanitiser and discarded, so the connector logs and sends only fixed text and the program's exit status; it ends with the SSH connection it carries. There is no general `ProxyCommand`.

**The target.** `{ kind: 'colab', user, auth, workspace, hostKeys? }`, with no host, port or jump host: the program chooses the runtime. Host identity, authentication (agent, then key file, then a second factor typed in the connector's own terminal), the workspace and forwarding checks, the start and attach of Jupyter, the tunnel to the fixed `127.0.0.1:<P>` over `direct-tcpip`, leases, `sessions.json` and the orphan sweep are those of the `ssh` target. The runtime's host key is kept, in the connector's `known_hosts` and in the connection's trusted keys, under the fixed name `colab.invalid` and port 22, which nothing resolves or dials. A key that differs from the trusted one stops the connection (A30), also when the person has started a new runtime; the person replaces it as for any host, after a recent sign-in. Google's credentials stay with the `colab` program on the person's computer, and the program carries only encrypted SSH packets, so nothing secret crosses Parallax.

**Paid Colab only.** The Colab FAQ disallows remote control such as SSH shells on runtimes without a compute-unit balance; a paid plan with a positive balance removes that restriction. Parallax states the condition where the option is offered and in the user documentation, and open-in-Colab-and-upload (spec §10.7, A10) stays the route for free Colab, unchanged. Neither the connector nor the server can see a person's plan or balance, so neither claims to check it; the `colab` program and Google's service apply Google's terms.

**Platforms.** The Linux and macOS connectors offer the `colab` target, the Linux connector inside WSL included, with the `colab` program installed in the same distribution. The native Windows connector does not list it in `hello.targets`.

**Protocol version.** The `colab` target is added to protocol v1 as a compatible extension, not as v2 (design §4.6), although connector-v0.1.0 has been released: a connector lists `colab` in `hello.targets` only from the version that implements it, and the server sends a `colab` target only to a connector whose live `hello` lists it. A connector that does not know the kind, connector-v0.1.0 included, never receives one, and no existing message, field, rule or code changes meaning.

**Consequences.** A connector that offers Colab runs one program that Parallax does not ship, with the person's rights, as OpenSSH runs a `ProxyCommand` the person configured; the connector's network scope does not cover the connections that program makes, and the forwarding destination stays fixed. Each new Colab runtime asks the person to trust or replace a key. Tests use a fake `colab` program and the in-process SSH server; whether the real program connects is the owner's one check on a paid plan (plan §7), which gates no item.

**Alternatives considered.** *A tunnel the person opens, reached as an `ssh` target on loopback:* untested, it needs a loopback scope (`--allow-net`), and Parallax could not tell that the target is Colab or state the paid-plan condition for it. *The connector inside the Colab runtime with a `local` target:* untested, not discussed with the owner, and a paired device identity in a short-lived runtime. *A general `ProxyCommand`:* a command chosen by configuration or by the server is what the connector design refuses the relay (§1 of the design). All three fall under the same Colab terms; the owner chose a fixed built-in form of the first (Q26).

## Amendment: open mode for level 0 pages (P6-05, 2026-10-21)

**Context.** PRODUCT.md N6, amended on the owner's request of 2026-10-21, lets a visitor of a level 0 site run a notebook on their own computer, with its processor, memory and Python, while the notebook stays on the course page (spec §13, "A notebook on one's own computer at level 0"; A57). A level 0 site is plain files: there is no server to pair a connector with or to relay through, so the Decision's "the browser speaks only HTTPS/WSS to Parallax" cannot carry a level 0 run. The Decision does not change for levels 1 and 2: `run`, pairing, the link, the relay, wire protocol v1 and its targets are untouched, and notebook code still never runs on a host that serves the site.

**Decision.** A command `parallax-connector open [--workspace DIR] [--python PATH] [--allow ORIGIN]...` runs in the foreground in a terminal and serves pages in the browser of the same computer:

- *Where it listens.* `127.0.0.1:47821` only, a fixed port the page knows. A request whose `Host` is not `127.0.0.1:47821` or `localhost:47821` is refused, so a name rebound to loopback reaches nothing. It dials only the Jupyter servers it starts and, once per session, the site's zip of the notebook's files.
- *Which pages.* A request carries an `Origin` that is `https`, or `http` on a loopback host (a site under test on this computer); any other, `null` included, is refused. Cross-origin answers name that origin, never `*`, and the preflight also answers `Access-Control-Allow-Private-Network`. No cookie is set or read.
- *Asking.* `POST /v1/pair { code }` asks in the terminal: the origin, the code the page shows, and "Answer y only if the page shows the code 1234-5678. Allow this page?". It asks for every page, also of a site allowed before, because any program on this computer can send a site's `Origin`: a yes is for the page that shows the code. No refuses the origin until the connector stops, without asking again, so a site cannot keep asking; one question at a time, for at most two minutes; without a terminal nothing is asked. `--allow ORIGIN` allows pages of an origin without asking (a computer with no terminal, CI); it trusts every program on this computer that sends that origin. A yes, or an origin of `--allow`, gets a key of 32 random bytes, bound to that origin and kept in memory by the connector and the page only, never on disk or in browser storage. Every later request carries it (`Authorization: Bearer`, or the `key` query of the kernel channel, since a WebSocket cannot send a header) from the same origin.
- *What a page can do.* Start a session (`POST /v1/sessions`), which starts Jupyter as the `local` target does in start mode, owned, with its token kept in the connector, in `<workspace>/<site>/<course folders>/<notebook>` (default workspace `~/Parallax`; in each name, a run of characters other than letters, digits, `.`, `_` and `-` becomes `-`; `http` sites under `local-<host>`). Then start, read, interrupt, restart and delete that session's kernels and open their channels, each checked by the Jupyter allowlist of the Decision (`CheckHTTP`, `CheckWS`, `CheckKernelStart`); nothing else of Jupyter, no contents and no terminals. Stop the session. At most three sessions and two kernels each; a session that no page has used or held a channel to for 30 minutes stops; Ctrl+C stops every one. The page learns the session id, the folder relative to the workspace, the Jupyter and Python versions and the kernelspecs, never a token, a port or a path outside the workspace.
- *The notebook's files.* A session may name the site's zip of the notebook (`https://<host>/o/<sha256>.zip`, or `http` on a loopback host). The connector downloads it with no redirect and no cookie, through the environment's proxy, checks its SHA-256 against its name, and extracts regular files only, below the session's folder, with no path that leaves it, and never replaces a file already there (256 MiB zip, 512 MiB and 2,000 files at most).
- *Executions.* The page binds its own executions by the relay's rules, which move to `packages/contracts/src/kernelMessages.ts` for both: a kernel message counts only when its parent is an `execute_request` the page sent on the current kernel and generation, nothing is ever sent again, and a dropped channel leaves what ran `unconfirmed`.

**Consequences.** Any page in the browser, and any program on this computer, can reach a loopback port, so the origin check, the terminal question with its code and the key are the whole defence: a page the person allowed can run code on this computer, which is what allowing it means. A program of another account on a shared computer can send an allowed site's `Origin`, which is why every page is asked about and only `--allow` skips the question; it can also hold the port before the connector starts, and a page would then talk to it, which gives it the cells a person runs but nothing of this computer. The site owner's own pages (N3) are pages of the site like the others. A level 0 content host holds no script (ADR-0002, **Amendment: Open site (level 0)**), and a frame with `sandbox=""` sends `Origin: null`, so neither untrusted objects nor live outputs can ask. Nothing is saved on the site or handed in; a level 0 run has no class, lease record or `sessions.json` entry, and closing the page stops its sessions. The Go tests use the fake Jupyter of the Decision; A57 also runs in a browser against the real `open` command and real Jupyter in the `open-site` workflow.

**Alternatives considered.** *Pairing through a server:* a level 0 site has none. *A page that talks to Jupyter directly:* the token would reach the browser, which ADR-0005 forbids. *A second loopback origin served by the connector for rich outputs:* a second port and origin to approve, where a `srcdoc` frame with `sandbox=""` already gives an opaque origin (ADR-0002, amendment of 2026-10-21). *An answer for a whole site, or kept on disk:* a yes that any program could then use by sending the site's `Origin`, or that outlives the terminal it was given in; `--allow` is that choice, made knowingly on a computer only its person uses.
